# KIRA OS — мастер-требования

Дата: 2026-11-11. Рабочая ветка: `v46/release-completion`.

Этот документ — единый ориентир для разработки. Перед каждым изменением сверяться с ним, `docs/HANDOFF.md`, `docs/PROGRESS.md`, `docs/RELEASE_GAPS.md`, `docs/DEPENDENCIES.md`, `ARCHITECTURE.md` и актуальным CI.

## Статусы и достоверность
Использовать статусы: подтверждено кодом и тестом; реализовано частично; не реализовано; не проверено на физическом оборудовании; историческое требование, нуждающееся в сверке. Не считать наличие файла/GUI/заглушки доказательством функции. Не объявлять PASS без реального запуска и результата. QEMU/Limbo не заменяют физические испытания.

## Цель
KIRA — самостоятельная ОС со своим ядром, ABI, системными службами, драйверной моделью, файловой системой, инструментарием и оболочкой. Это не Linux-дистрибутив и не оболочка поверх чужого ядра. Внешние инструменты разработки допустимы временно, но должны быть классифицированы как build-time/test-only и не попадать незаметно в конечную систему.

## Архитектура
- x86-64 и AArch64/ARM64 развиваются параллельно; общий код отделён от `arch/x86_64/` и `arch/aarch64/`.
- Целевая модель — адаптивная capability-ориентированная микроядерная архитектура. Идеи seL4 (capabilities, изоляция, проверяемые границы) использовать как исследовательскую основу, не копировать seL4 целиком.
- Аппаратные ресурсы обнаруживать через ACPI (x86) и Device Tree (ARM64), не зашивать адреса устройств.
- Ядро: SMP, вытесняющая многозадачность, безопасные адресные пространства, user-access, исключения, блокировки, таймеры, IPC, shared memory с явными правами.

## App Isolation и capabilities
Каждое приложение должно исполняться в отдельном защищённом пространстве/контейнере с CPU/память/IO-квотами, контролем файлов и сети, ограниченным IPC/SHM и управляемым жизненным циклом. Привилегии выдаются только через проверяемые capabilities; минимальные права по умолчанию. Обязательны отрицательные тесты на escape, повышение привилегий, утечки ресурсов и отказ брокера.

## KIRA Mind
Встроенная интеллектуальная подсистема управления/адаптации, не обычный чат-бот и не root-процесс. Взаимодействует с ядром через capability broker и ограниченные API. Все решения ограничены квотами, журналируются, имеют проверяемые причины и rollback. Сбой модели/обучения не должен ломать ядро. Запрещено автоматическое расширение полномочий. Проверять holdout-наборами, adversarial-тестами, регрессиями и длительными прогонами.

## KCC и self-hosting
Развивать собственные C frontend, IR, оптимизации, x86-64 и AArch64 backend, ELF/linker path, диагностику, WASM/WASI и сборку приложений внутри KIRA. Постепенно идти к self-hosting через дифференциальные тесты и корпус программ. Пока Clang/LLD/NASM/wasm-ld/llvm-objcopy нужны для полной сборки, KCC нельзя называть полной заменой toolchain.

## KIRA Driver Compatibility
Отдельные Driver Manager GUI и системная служба: обнаружение устройства; поиск исходников из разрешённых источников; проверка лицензии, происхождения и подписи издателя; ABI-адаптация; пересборка; статический анализ; sandbox-тестирование; установка после проверок; отзыв, карантин, обновление и rollback. Драйвер получает только необходимые MMIO/IRQ/DMA/PCI/network capabilities. Непроверенный код не запускается с правами ядра. SHA-256 доказывает целостность, но не издателя. Универсальная поддержка Linux .ko/Windows .sys не заявляется без реальной реализации. Без IOMMU недоверенные DMA-драйверы должны блокироваться или оставаться в безопасном режиме.

## Storage
Развивать KiraFS/VFS, crash consistency, journaling/CoW, content-addressed storage, Merkle integrity, snapshots и A/B recovery там, где это предусмотрено архитектурой. Разделять системные, пользовательские и sandbox данные. Проверять повреждение, переполнение, внезапное отключение питания, восстановление и враждебные входы. Не считать весь целевой набор реализованным без тестов.

## Secure boot, updates, supply chain
Собственная цепочка загрузки BIOS/UEFI x86 и ARM64; подписанные образы/пакеты; доверенные издатели; Ed25519 или обоснованный криптографический механизм; ротация и отзыв ключей; anti-rollback; проверка до переключения; A/B update и восстановление. Известный блокер — текущая зависимость x86 ISO от GRUB/Multiboot2. Не путать хеширование с аутентификацией.

## DMA и аппаратная безопасность
Поддержка Intel VT-d, AMD-Vi и ARM SMMU по мере реализации. Проверять DMA buffers, адресацию, cache coherency, interrupt remapping и lifecycle устройств. Без доказанной IOMMU-изоляции не запускать недоверенные DMA-capable драйверы привилегированно. QEMU не заменяет физические тесты.

## Сеть и криптография
Продолжать закрытие пробелов из актуального плана: протоколы, IPv6, TLS, сертификаты, отзыв доверия, сетевые службы. Нужны RFC-векторы, негативные тесты, безопасные defaults и проверка на обеих архитектурах. Источники драйверов и обновлений — только аутентифицированные каналы с проверкой подписей и хешей.

## GUI и приложения
Собственная отзывчивая оболочка, управление окнами/доком/панелью, файловый менеджер, мышь/клавиатура/сенсорный ввод, кириллица и русская локализация. Приложения Ring 3/WASM работают в sandbox и не получают лишних capabilities. Восстановление/диагностика должны быть доступны при отказе GUI.

## Полный security/CVE audit
Текущий `ci/dependency_audit.py` — статический inventory/provenance audit, не CVE scanner. Необходимо:
1. SBOM исходников, build inputs, ISO и KiraFS; версии, лицензии и происхождение.
2. Проверка OSV/NVD/GHSA и upstream advisories с оценкой реальной применимости.
3. CodeQL или эквивалент для C/C++/Python/Shell, static analysis, sanitizers, secret scanning.
4. Проверка GitHub Actions, permissions, supply-chain и provenance артефактов.
5. Fuzzing ELF/WASM, IPC/syscalls, KiraFS, сетевых парсеров, драйверных рецептов и update packages.
6. Аудит kernel attack surface, App Isolation, capability broker, KIRA Mind, драйверов/MMIO/IRQ/DMA, boot/update chain.
7. CVE triage: severity, applicability, affected component/version, evidence, remediation, regression test, status.
8. Release gate для применимых Critical/High вводить после достоверного baseline; не скрывать нерешённые находки и не блокировать по неотносящимся CVE.

## CI и доказательства
Каждое изменение: x86-64 и ARM64 build с -Werror, host tests, соответствующие QEMU-сценарии, негативные тесты безопасности. CI ускорять измеренным кэшированием/параллелизмом, не ослабляя coverage. Ошибка diff/classifier должна вести к full suite. Сохранять логи, summaries, образы, SBOM и security reports с commit SHA. Отдельно вести QEMU и физическую hardware qualification. По возможности не требовать от пользователя Termux/ПК: использовать GitHub и доступные удалённые среды.

## Известные ограничения из текущих документов
- x86 ISO зависит от GRUB/Multiboot2.
- KCC ещё не заменяет весь внешний toolchain.
- drvget поддерживает ограниченные BSD-style recipes; универсальная трансляция Linux/Windows драйверов не подтверждена.
- SHA-256 пакета не удостоверяет издателя.
- DMA isolation требует IOMMU; физическая проверка не заменяется QEMU.
- Полноценный CVE scanning/triage pipeline в репозитории пока не подтверждён.
Перед изменениями эти пункты сверять с HEAD: исторические документы могут отставать.

## Definition of Done
Полная готовность допускается только при выполнении требований или документированном исключении; отсутствии критических заглушек; полном CI обеих архитектур; тестах изоляции, secure boot/update, driver trust и DMA; SBOM/CVE triage; бинарном аудите ISO; rollback/recovery; физической квалификации аппаратуры. Если физические тесты недоступны, выпуск честно маркируется как не прошедший hardware qualification.

## Рабочая дисциплина
Не оставлять stubs/пустые функции/mock-only реализации. Сначала доказать причину, исправить минимально и добавить regression test. Не менять критические проверки ради зелёного CI. Каждое изменение — отдельный commit с SHA и фактическими результатами. Не сливать PR до проверок. Отчёты пользователю — только по завершении, предельно кратко.
