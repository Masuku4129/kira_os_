# Доверенная загрузка (Secure Boot и измеряемая загрузка)

Обновлено: 2026-11-17

Для кого: тот, кто выпускает образ Киры для комплекса, и тот, кто проверяет, что именно загрузилось. Пункт плана: [PLAN.md](PLAN.md), А2. Статус и проверки — в конце файла.

## Что это даёт простыми словами
Обычный образ грузится с любого носителя и запускает любое ядро, которое лежит рядом. В доверенном режиме три замка подряд, и каждый проверяет следующий:

1. **Прошивка компьютера** (UEFI с включённым Secure Boot) запускает только такой загрузчик `BOOTX64.EFI`, подпись которого сделана ключом из её списка доверенных (`db`). Подменили или испортили загрузчик — прошивка его не запустит, Кира даже не начнёт грузиться.
2. **Загрузчик Киры** читает подписанный список `KIRA.SIG`: какие файлы и какие у них отпечатки (SHA-256) выпустил владелец. Подпись списка проверяется ключом выпуска, который вшит в сам загрузчик. Ядро (и initrd, если он есть) не совпали с отпечатками — загрузчик пишет причину на экран и в COM1 и **не передаёт управление**. Обходного «ладно, всё равно запустим» нет.
3. **Ядро** получает от загрузчика сведения (Secure Boot включён или нет, подпись проверена, измерено ли в TPM) и печатает их в журнал строками `[KIRA BOOT] ...`. Ядро этим сведениям доверяет, потому что за них отвечает проверенный загрузчик.

Если на компьютере есть TPM 2.0, загрузчик ещё и **вносит** список, ядро и initrd в регистр PCR 9 и печатает его значение, прочитанное у самого TPM. По нему можно доказать (удалённо или потом), что загрузился именно этот выпуск.

## Два режима
| | Режим разработки (по умолчанию) | Доверенный режим |
|---|---|---|
| Как собирается | обычная `./build_clang.sh`, как раньше | `KIRA_SECURE=1` (см. ниже) |
| Подпись ядра | не проверяется | обязательна, иначе отказ |
| Командная строка из NVRAM | принимается | игнорируется (она никем не подписана) |
| Для чего | ежедневная работа, телефон, QEMU | комплексы и стационарные ПК |

Режим разработки остаётся таким же, каким был: загрузчик только сообщает состояние Secure Boot и ничего не блокирует.

## Как выпустить подписанный образ
Нужно на машине выпуска: `openssl`, `sbsigntool` (команда `sbsign`), `mtools`, `gnu-efi`, `python3`. Закрытые ключи хранятся **вне репозитория и вне образа**.

1. Ключ выпуска (Ed25519). Один раз:
   ```
   python3 tools/kirasig.py keygen /безопасное/место/release.pem release.pub
   ```
2. Ключ и сертификат db (RSA-2048), которыми подписывается загрузчик, — один раз:
   ```
   openssl req -x509 -newkey rsa:2048 -nodes -keyout db.key -out db.crt -subj "/CN=Моя организация db/" -days 3650 -sha256
   ```
3. Сборка и подпись. Ядро `kira.bin` уже собрано обычной сборкой:
   ```
   KIRA_SECURE=1 KIRA_BOOT_PUBKEY=release.pub KIRA_MIN_IMAGE_VERSION=1 ./build_uefi.sh /tmp/kira-secure-loader
   tools/sbsign_image.sh --loader /tmp/kira-secure-loader/EFI/BOOT/BOOTX64.EFI --kernel kira.bin \
       --release-key /безопасное/место/release.pem --version 3 \
       --db-key db.key --db-cert db.crt --out kira-secure.img
   ```
   То же одной командой: `KIRA_SECURE=1 KIRA_BOOT_PUBKEY=... KIRA_RELEASE_KEY=... KIRA_DB_KEY=... KIRA_DB_CERT=... ./build_clang.sh --no-run` соберёт ещё и `kira-secure.img`; обычный `kira.iso` при этом остаётся образом разработки.
4. Образ `kira-secure.img` записывается на носитель (GPT с разделом ESP). Подписанный образ нельзя менять: ни загрузчик, ни ядро, ни `KIRA.SIG`.

Параметры доверенного загрузчика (переменные окружения `build_uefi.sh`): `KIRA_BOOT_PUBKEY` — открытый ключ выпуска (обязателен); `KIRA_MIN_IMAGE_VERSION` — нижний порог номера выпуска, выпуски ниже отклоняются (защита от отката, задел для А3); `KIRA_REQUIRE_SB=0` — не требовать включённый Secure Boot (по умолчанию требуется); `KIRA_REQUIRE_TPM=1` — не загружаться, если загрузку не удалось измерить в TPM (по умолчанию не требуется).

## Как завести ключи в компьютер
Прошивка должна знать сертификат `db.crt` (иначе она не запустит ваш подписанный загрузчик) и иметь включённый Secure Boot.
- **QEMU/OVMF** (как в проверках): `virt-fw-vars --input OVMF_VARS_4M.fd --output vars.fd --set-pk GUID pk.crt --add-kek GUID kek.crt --add-db GUID db.crt --sb`; полный пример — `ci/sb_fixture.py`.
- **Настоящий ПК**: в меню настройки прошивки (раздел Secure Boot → Key Management) перевести её в Setup Mode (удалить PK) и добавить свои PK, KEK и db, либо добавить `db.crt` в `db` рядом с существующими ключами. Названия пунктов зависят от производителя. Этот путь в проекте на железе **не проверялся**.

Setup Mode (ключи платформы не заведены) ядро и загрузчик честно называют «подписи ничего не доказывают».

## Что в журнале
Загрузчик (экран: `KIRA BOOT: ...`, COM1: `[KIRA BOOT] ...`) и ядро (`[KIRA BOOT] ...`):
| Строка | Смысл |
|---|---|
| `Secure Boot: enabled (firmware verified the signature of this loader)` | прошивка проверила загрузчик |
| `Secure Boot: disabled` / `unknown` | первое звено цепочки отсутствует |
| `kernel KIRA.ELF: SHA-256 and size match the signed manifest` | ядро — то, что выпущено |
| `TPM: PCR 9 (SHA-256) = ...` | итог измерений, прочитан из TPM |
| `TRUSTED BOOT REFUSED: the kernel is NOT started` + `object` + `reason` + `fix` | отказ и его причина |
| `Image signature: verified by the loader (...), release N` (ядро) | ядро подтверждает, что подпись проверена, и называет выпуск |
| `Trusted boot: YES` (ядро) | Secure Boot включён, загрузчик принуждающий, подпись проверена |

Как проверить PCR 9 самому: он равен результату цепочки `p = 0 (32 байта); для каждого файла в порядке KIRA.SIG, KIRA.ELF, INITRD.IMG: p = SHA256(p || SHA256(файл))`. Расчёт — `pcr_extend` в `ci/sb_fixture.py`; сценарий `secureboot-measured` сверяет значение из эмулируемого TPM с этим расчётом.

## Защита от отката (простыми словами)
Подпись доказывает, что файл выпущен владельцем, но не что он свежий: злоумышленник может подложить старый, но по-настоящему подписанный образ или старую копию диска со старой уязвимостью. Против этого два «счётчика-свидетеля» в TPM (микросхеме безопасности), которые нельзя откатить назад:

- **Счётчик выпуска.** Загрузчик сверяет номер выпуска из подписанного списка со счётчиком в TPM. Номер меньше - строка `[KIRA BOOT] rollback: release 3 is older than the TPM counter 5 (rollback refused)` и ядро не стартует. Счётчик поднимает не загрузчик, а само ядро после того, как проработало 20 секунд и дошло до главного цикла (`good boot confirmed`): плохой выпуск не должен закрыть путь назад. Без TPM остаётся прежний нижний порог `KIRA_MIN_IMAGE_VERSION`, и загрузчик честно пишет, что счётчика нет.
- **Эпоха диска.** KiraFS считает «эпоху» (растёт на 1 при записи с изменениями), а TPM хранит якорь - последнюю эпоху, которую мы видели. Якорь пишется после записи эпохи на диск, не чаще раза в 900 секунд и при штатном выключении (запас по износу памяти TPM). Старую копию диска видно при монтировании: `[KIRA FS] rollback detected: disk epoch 2 is older than the TPM anchor 3 ...`. Том открывается только для чтения; оператор, убедившись, что копия законная (например, восстановление из резервной), вводит `fsanchor accept`. Состояние: `fsanchor`.
- **Подпись приложений.** В доверенном режиме приложения из `/bin` запускаются, только если подписан список `/etc/apps.manifest` (подпись `/etc/apps.sig`, Ed25519, ключ издателя). Подменённый список, отсутствие подписи и отозванный ключ (`drv revoke`) - отказ; ротация - сменой ключа со сроком действия старого. В режиме разработки всё как раньше (встроенный список SHA-256), подпись включается строкой ядра `kira.signedapps`.

Что остаётся открытым: откат самого загрузчика на ESP (нужен `dbx` или запечатывание по PCR), записи после последней синхронизации диска, чужой том с эпохой не ниже якоря, хранилище опыта вне KiraFS, ARM64 без TPM, реальное железо не проверялось. Альтернативы (RPMB, счётчик в прошивке, счётчик на каждую запись, ORDERLY, подъём счётчика в загрузчике) и причины выбора: [PLAN.md](PLAN.md), А3.

## Как устроена проверка манифеста
Формат `KIRA.SIG` описан в начале `bootsig.h`: заголовок, записи «имя, размер, SHA-256», подпись Ed25519 над доменным префиксом и телом. Подпись проверяется раньше разбора полей; изменение любого байта файла, подмена ядра, чужой ключ, усечение, ненулевые неизвестные флаги и номер выпуска ниже порога отклоняются (`tests/bootsig_test.c`). Ядро и initrd хэшируются по тому буферу, из которого потом загружаются: между проверкой и загрузкой файл не перечитывается. Initrd, которого нет в манифесте, и initrd, который есть в манифесте, но удалён, отклоняются.

## Выбор и отвергнутые альтернативы
Запись в [PLAN.md](PLAN.md), А2. Коротко:
- **Выбрано:** прошивка проверяет наш загрузчик (ключ `db`), загрузчик проверяет подписанный манифест (свой ключ выпуска Ed25519). Причины: загрузчик свой, чужой код в цепочке не нужен; ключ выпуска владелец меняет, не трогая ключи прошивки; один и тот же проверенный код Ed25519 и SHA-256 используется в ядре и загрузчике.
- **Shim** (готовый чужой загрузчик, подписанный Microsoft): меньше работы, но чужой код в цепочке доверия, зависимость от чужих ключей и их отзыва, и всё равно нужна проверка ядра на нашей стороне.
- **Подпись самого ядра в `db` прошивки** (ядро как PE-образ): ядро — ELF, пришлось бы менять формат и все сборки; любое обновление ядра требует доступа к ключу `db`, которым владелец прошивки, возможно, не хочет делиться; проверка идёт в прошивке, и мы не можем добавить номер выпуска и список файлов (initrd).
- **Только собственная проверка без Secure Boot:** первое звено (загрузчик) тогда можно подменить, и подмена не заметна. Поэтому доверенный загрузчик по умолчанию сам требует включённый Secure Boot.

## Что пока не защищено (честно)
- Реальное железо не проверялось: проверка в QEMU/OVMF и эмулируемом TPM (swtpm).
- Подпись ядра проверяет загрузчик; после передачи управления защиту держит само ядро (W^X, SMEP/SMAP; ранний W^X и KASLR — А4).
- Откат образа защищён счётчиком в TPM (А3) и нижним порогом `KIRA_MIN_IMAGE_VERSION`; без TPM только порогом. Откат диска и откат загрузчика: см. раздел «Защита от отката», окна описаны там.
- Приложения и драйверы проверяются своими подписями (kdrv, домены DRV и APPS), не этим манифестом.
- ARM64: цепочки доверия нет, загрузчик `bootaa64.c` не менялся.
- Ключи `db` и PK заводятся вручную; отзыв ключа выпуска — перевыпуском загрузчика с новым ключом (ротация и отзыв — А3).

## Как проверить в QEMU
Нужны `qemu-system-x86_64`, OVMF (`/usr/share/OVMF`), `swtpm`, `sbsigntool`, `virt-firmware` (`pip install virt-firmware`). Ключи для проверок создаются на лету в `ci-out/secureboot` (каталог в `.gitignore`).
```
python3 ci/kira_vm.py --scenario secureboot-ok --timeout-scale 3
```
Сценарии: `secureboot-ok` (подписанный образ грузится, ядро сообщает состояние), `secureboot-tamper-loader` (загрузчик изменён на 1 байт: отвергает прошивка), `secureboot-unsigned-loader` (без подписи: отвергает прошивка), `secureboot-tamper-kernel` (ядро изменено на 1 байт: отказывает загрузчик), `secureboot-no-manifest`, `secureboot-rollback`, `secureboot-required` (Secure Boot выключен при доверенном загрузчике), `secureboot-measured` (эмулируемый TPM, PCR 9). Откат и подмена (А3): `secureboot-rollback-tpm` (выпуск 5 грузится и поднимает счётчик, выпуск 3 с верной подписью отвергается, состояние swtpm в `ci-out/tpm-state-*` переживает перезапуск), `secureboot-rollback-no-tpm`, `fs-rollback-tpm` (подмена диска старой копией), `fs-anchor-no-tpm`, `apps-signed-ok`, `apps-signed-tampered`, `apps-signed-missing`, `apps-signed-revoked`, `apps-dev-mode`, `secureboot-apps`, `secureboot-apps-unsigned` (приложения; тестовая сборка `KIRA_TEST_TRUST=1`). Хост-тесты: `tests/bootsig_test.sh`, `tests/tpm2_test.c`, `tests/rollback_test.c`, `tests/tpm2_swtpm_test.sh`, `tests/kfs_epoch_test.c`, `tests/appman_test.sh`, `tests/a3_mutation_test.sh`, `tests/boottrust_test.c`, `tests/uefi_kbi_test.c`, `tests/bootinfo_test.c`.
