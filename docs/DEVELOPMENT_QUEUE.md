# KIRA OS — единая очередь разработки и интеграции

**Назначение:** единый порядок работ по исходному мастер-плану `docs/MASTER_DEVELOPMENT_PLAN.md`. Этот файл не заменяет мастер-план и реестр `docs/PROJECT_STATUS/`; он отвечает на вопрос «что делаем следующим и при каких условиях переходим дальше».

**Целевой продукт:** самостоятельная ОС KIRA OS (`independent_all`), не Linux-дистрибутив. Целевая архитектура: Hardware/Platform → HAL/Device Model/Drivers → KIRA Kernel → Security → KIRA Mind → System Services → Runtime → User Environment. KIRA Hypervisor — отдельный контур для целых гостевых ОС.

**Главный текущий приоритет:** закончить и реально подключить KIRA Spatial Minimal к штатному пути запуска/сборки. До этого новые крупные UI-функции не распыляем; остальные направления сохраняются в очереди и могут проходить независимый аудит/подготовку без преждевременного слияния.

## Правила очереди

1. Работа идёт по модулям и вертикальным срезам: код → сборка → тесты → интеграция → проверка в целевой среде.
2. Ветка или PR не считаются частью ОС, пока изменения не проверены, не включены в нужные build inputs и не интегрированы в выбранную базовую линию.
3. Не переносить ветки целиком вслепую. Сверять base/head SHA, diff, build lists, зависимости, тесты и файлы из других параллельных веток.
4. Никаких заглушек и фиктивной production-логики. Не объявлять PASS без фактического результата.
5. Для каждого модуля вести статусы: NOT_STARTED / IN_PROGRESS / BLOCKED / INTEGRATED / VERIFIED. INTEGRATED не означает VERIFIED.
6. Сборка x86-64/Limbo и ARM64/QEMU — разные проверки. Эмулятор не доказывает поддержку физического оборудования.
7. После каждого интеграционного шага обновлять этот файл, `docs/PROJECT_STATUS/01_READY.md`, `02_IN_PROGRESS.md`, `03_PLANNED.md` и manifest, когда меняется состав файлов/статус.
8. PR не сливать без отдельного разрешения владельца проекта.

## Подробный активный план: очередь 01 — подключение Spatial Minimal

Все PR ниже остаются отдельными источниками изменений. Номера — ориентиры для аудита, не разрешение автоматически сливать PR.

### UI-0. Инвентаризация и точка входа
- Проверить фактическую цепочку: boot → display_init → framebuffer/compositor → window manager → desktop/apps.
- Сопоставить `display.c`, `wm.c`, `gfxui.c`, `dock.c`, `apps.c`, `explorer.c`, `fm.c`, `input.c`, launcher и build scripts.
- Установить, где именно выбирается Legacy/Spatial, какой compile-time флаг включает Spatial и входит ли он в Android/Limbo build.
- Сверить build lists x86-64 и ARM64; проверить, что UI source/assets/tests реально попадают в образы.
- Сохранить Legacy startup как регрессионную конфигурацию.
- Источники: PR #138, #140, #142, #143, #144. Текущий статус: **IN_PROGRESS / UNVERIFIED** — наличие веток и описаний не доказывает подключение в собранный ISO.

### UI-1. Единый визуальный язык
- Перенести и проверить semantic design tokens: глубокая сине-фиолетовая палитра, поверхности, типографика, радиусы, отступы, состояния и motion policy.
- Применить токены не только к геометрии окон, но и ко всем встроенным приложениям/карточкам/кнопкам/панелям.
- Проверить, что Spatial Preview использует новую тему, а Legacy сохраняет прежнюю.
- Источник: PR #146 (`feat/spatial-visual-tokens-2026-11-13`). Статус: **IN_PROGRESS / NOT IN BASELINE**.

### UI-2. Базовый рабочий стол
- Свободная центральная область; слева только основные системные разделы.
- Снизу только закреплённые приложения; не дублировать список окон/вкладок в Dock.
- Компактная системная зона, переключение рабочих пространств, адаптивная навигация.
- Окна с единым Spatial chrome; Legacy оконная модель не должна регрессировать.
- Источник: PR #144 и его предшествующие Spatial изменения. Статус: **IN_PROGRESS / NOT IN BASELINE**.

### UI-3. Контекстные поверхности
- Launcher и поиск; каталог приложений и запуск через реальную системную очередь.
- Панель системного состояния открывается по запросу, показывает реальные CPU/RAM/Mind, сеть и звук.
- Уведомления и история не крадут фокус; рабочие пространства сохраняют состояние.
- KIRA AI — ненавязчивая точка вызова/реальное окно Mind, не фиктивный overlay и не постоянно занимающая экран панель.
- Источники: PR #142 и #143, Launcher/Spatial работы в PR #144. Проверить реальные API и источники telemetry.

### UI-4. Адаптация и доступность
- Компактные и широкие разрешения, DPI, масштабирование, кириллица/Unicode.
- Мышь, клавиатура и сенсорный ввод; видимый фокус и последовательная навигация.
- Контраст без зависимости от обоев/прозрачности; reduced motion.
- Не считать отдельный host geometry test доказательством корректной отрисовки в Limbo.

### UI-5. Регрессии и приёмка
- Host GUI tests: layout, hit-testing, window chrome, Dock pinning, launcher, notification lifecycle, input/focus.
- Сборка x86-64 release/Spatial и Legacy; ARM64 compile/VM отдельно.
- Запуск в Limbo: фактические кадры 1024×768 и 320×240; проверить запуск приложений, окна, ввод, Dock, Launcher, контекстную панель.
- Сравнить производительность полной и частичной перерисовки; не допустить регрессии frame time.
- Только после этого статус GUI может стать VERIFIED для конкретных тестовых сред. Физическое оборудование остаётся отдельной проверкой.

## Следующие модули после GUI

Порядок интеграции выбран по зависимостям, а не по привлекательности функций:

1. Архитектурные контракты/HAL — чтобы верхние уровни не зависели от CPU и конкретного устройства.
2. Ядро/процессы/IPC — фундамент безопасного запуска служб и приложений.
3. Безопасность памяти/исполнения — до расширения драйверов и runtime.
4. Device Model/драйверы — включая GUI Driver Manager и адаптацию исходников драйверов.
5. KiraFS/storage и сеть — системные ресурсы для приложений и служб.
6. System Services — стабильные API поверх ядра и драйверов.
7. KVR/WASM и Native Runtime — не заменять текущий WASM второй VM без ADR и измерений.
8. KCC/IR/toolchain — развивать как отдельный поток с согласованными ABI.
9. KIRA Mind — интегрировать через реальные метрики и ограниченные управляющие предложения.
10. Installer/updater/recovery и release pipeline.
11. x86-64/ARM64 аппаратная приёмка.
12. Linux/Windows compatibility runtime и отдельный KIRA Hypervisor.

## Что не объявлять готовым

- Наличие `display.c/wm.c` не означает, что Spatial UI подключён.
- Наличие Spatial ветки/PR не означает, что изменения попали в ISO.
- Компоновка окон без новых токенов не означает завершённый визуальный редизайн.
- Launcher, открывающий Mind application, не равнозначен отдельному KIRA AI assistant overlay.
- Текущий Driver Manager/drvget — ограниченная работа с проверяемыми source recipes, не универсальный переводчик бинарных драйверов Linux/Windows.
- Наличие `mind.c/mind_sys.c` не означает полностью автономный AI с безопасным управлением ядром.
- WASM — текущая основа переносимого KVR; KVM1/KVP0 остаётся экспериментом.
- QEMU/Limbo и компиляция ARM64 не доказывают поддержку физических плат.
- Успешная сборка не доказывает корректность всех функций или безопасность.

## Формат обновления этой очереди

Для каждой завершённой задачи добавить:
- ID и статус;
- точный branch/commit SHA;
- изменённые файлы и build inputs;
- команды и среду проверки;
- реальные результаты (PASS/FAIL/UNVERIFIED);
- оставшиеся ограничения и следующий ID.

**Текущий активный пункт:** `01 / UI-0 → UI-1 → UI-2 → UI-3 → UI-4 → UI-5`. До закрытия UI-5 основной интеграционный фокус — графическая оболочка.
