Собрано из решений владельца (память проекта), HANDOFF, RELEASE_GAPS и UNIFIED_RELEASE_PLAN. Порядок — по плану владельца.

## 0. Решение 2026-11-09: компилятор KCC входит в обновление как есть
Гонка за скоростью clang -O2 (среднее отставание ~13%, худший случай ~70%) НЕ блокирует выпуск. Скорость — отдельные патчи позже.

## 1. Компилятор (после выпуска, отдельными патчами)
- Скорость: аллокатор регистров с разбиением интервалов, режим всей программы, развёртка циклов, векторизация SSE2/AVX2 по набору команд машины.
- Язык: `long double`, `_Complex`, `_Thread_local`, computed goto; структуры с float по значению по SysV ABI.
- Инструменты: `kcc -c` для AArch64, ассемблер для .s-файлов ядра (сейчас nasm), компоновка нескольких объектов (klink, настоящая GOT).

## 2. Безопасность памяти (первый приоритет владельца после компилятора)
- Сделано (патч 1-2): ранний boot.s с NX выше образа. Осталось: ранние 2-МБ страницы самого образа RWX до vmm_enforce_wx; нет KASLR; страница AP-трамплина.
- Откат всего диска откатывает и защиту от отката: нужен TPM/RPMB/счётчик прошивки; второй ключ подписи не заведён.
- Приложения проверяются только SHA-256. (USB только для чтения по умолчанию - сделано, запись: `remount usbN rw`.)
- Сделано (патч 1-2): двойное освобождение стека потока, ловушка NULL на AArch64. Векторы MSI: утечки нет (слоты переиспользуются).

## 3. Драйверы, DMA, платформа
- Драйвер RTL8139 «с чистого листа» по публичной спецификации (issue #8).
- IOMMU: VT-d изолирует virtio-blk, virtio-net, virtio-rng, virtio-gpu, e1000, NVMe, xHCI, UHCI (каждый со своей проверкой принуждения и сценарием *-iommu); осталось: AHCI (проверка принуждения оставляет в модели AHCI QEMU «хвост»: контроллер позже пишет в уже освобождённую страницу, причина не найдена - пробовали команду в слоте 0 и FIS после COMRESET, оба раза сброс контроллера не помог), virtio-input (проверка по очереди состояния в QEMU не даёт отказа), HDA (QEMU не идёт за командой CORB в невыданную память - нужна проверка по потоку), AC97 (QEMU зацикливается на любой недоступной памяти AC97 и зависает - проверку принуждения в нём не сделать), SB16 (ISA DMA); нет перенаправления прерываний (issue #10).
- IOMMU на ARM64 (SMMUv3, первая стадия, 4 КБ; QEMU `-machine virt,iommu=smmuv3`): под SMMU изолированы все virtio-устройства ядра - virtio-blk, virtio-net, virtio-rng, virtio-gpu и virtio-input (клавиатура, планшет): у каждого свой домен, выдаются только кольца и буферы, принуждение подтверждается (событие SMMU F_TRANSLATION на невыданную память), при неподтверждении (нет iommu_platform) домен снимается и устройство остаётся сквозным с записью в журнал; без SMMU в дереве устройств поведение прежнее. Сценарии: arm64-smmu, arm64-smmu-all, arm64-smmu-fallback, arm64-smmu-nc. Дверной звонок MSI (GITS_TRANSLATER / MSI_SETSPI_NS) отображается в каждый домен окном MMIO (раньше SMMU молча останавливал все прерывания изолированного устройства: диск работал опросом). Осталось: e1000/NVMe/xHCI/AHCI/USB на ARM64 под SMMU не проверены (сценариев нет); перенаправления прерываний нет (устройство может поднять только свои векторы ITS по своему DeviceID, но SMMU этого не ограничивает); вторая стадия не используется (в QEMU 8.2 её нет); таблицы SMMU 4 КБ без блоков (дорого для больших буферов: кадр экрана 1280x800 - около 1000 страниц); проверка на железе (несколько SMMU, StreamID за пределами линейной таблицы в 256 записей, мосты PCIe, ATS/PRI) не выполнена.
- Некогерентный DMA на ARM64 (kira.dma=noncoherent, пул без кэша): в QEMU реально проверить нельзя - его DMA и обходчик SMMU согласованы с кэшем всегда. Проверено только поведение: при несогласованной платформе SMMU не включается (сообщение в журнале), устройства работают через пул (сценарии arm64-dma-nc, arm64-smmu-nc). Подтвердить на железе: (1) SMMU с IDR0.COHACC=1 видит таблицы ядра без очистки кэша - ядро пишет CR1 (write-back, внутренне общие), при COHACC=0 SMMU не включается; (2) для платы без согласованности нужны очистка кэша (dc cvac) после записи STE/CD/таблиц страниц и очередей SMMU либо их выделение из пула без кэша (пул не освобождается - потребуется свободный список); (3) настоящий отказ DMA устройства без согласованности (пул 32 МБ, буферы нужного размера) на Raspberry Pi 4 и аналогах.
- Подписи драйверов: каталог, ротация и отзыв ключей, drvget/mind_build с защитой от отката времени (issue #9).
- ACPI: интерпретатор AML, события SCI, кнопка питания, _PRT, батарея сделаны (см. REQUIRED_TECH_PLAN, раздел 5); осталось: проверка на настоящих ноутбуках (EC, батарея, крышка, температура проверены только на модели), сон S3/S4 и реакция на крышку, мосты со своим _PRT (INTx для GSI >= 16 и по правилу моста сделан: вектор из пула MSI, сценарии drv-bsd-* и drv-bsd-pcn-bridge), Load/LoadTable/DataTableRegion, ACPI на ARM64, IVRS; проверка некогерентного DMA на ARM.
- Драйверы в user space; приложение установки драйверов; слой совместимости: загрузка BSD-исходников и сборка на устройстве.

## 5. Разум (Mind) и ИИ
- ≥ +18 рычагов с большей самостоятельностью, обучение на GitHub; per-core порог перегрузки, плавная стабилизация.
- Шесть разделов панели («Состояние», «Прогнозы», «Обучение», «Решения», «Процессы», «Оборудование») только через опубликованный API; Mind не управляет окнами.
- Задания на сборку: проверить `build allow ИМЯ sig` в QEMU, разрешения после перезагрузки, квота времени сборки, потребитель результата зонда.
- Устранить лаги Разума и WASM (одно ядро, медленный образ).

## 6. Интерфейс (ждёт образцы владельца)
- Единый стиль по присланным референсам (тёмно-синий фон, неоновые акценты, верхняя панель, боковая панель иконок).
- Проводник в стиле mc (две панели), полноэкранный режим и сворачивание, кириллица, масштабирование, низкая память.

## 7. Большие направления
- Цех с боксами (параллельная сборка); язык инструкций для ИИ и человека + приложение.
- x86 и ARM64 в паритете; изоляция приложений в духе Qubes/seL4 (приложения в ВМ).
- Исследование выбора технологий: research/kira-architecture-selection-2026-11/ — по его итогам владелец решает, что переделывать.
- Автоподбор драйверов для дисков и звука (после сети). Сеть ставится на устройстве (drvget, каталог PCI-ID, рецепты BSD). ДИСКИ: канал готов - право CAP_BLKDEV (`KDRV_SYS_BLKDEV`, kdrv_blk.h): кольца запросов/ответов и буферы данных в общей памяти, регистрация в blk.c с проверкой границ, ожидание по прерыванию (KDRV_EV_BLK), DMA под VT-d только для буферов данных; эталонный драйвер virtio-blk `userland/drvvblk.c`, сценарий `drv-blk`, хост-тест `kdrv_blk_test` (docs/DRIVERS.md). Осталось по дискам: драйверы AHCI/NVMe в Ring 3 (встроенные в ядре продолжают работать), рецепты и каталог PCI-ID для дисков в drvget, SECTOR 4096 (сейчас только 512), системный диск на драйвере Ring 3 (загрузка идёт встроенными), ARM64-сценарий. ЗВУК пока без канала: нужны отдельное право, кольца и регистрация в audio.c (AC97/HDA), потом эталонный драйвер и сценарий. Встроенные драйверы ядра дисков и звука продолжают работать как раньше.
