# KIRA OS — автоматический сборочный цех

## Как работает

Полный прогон автоматически запускается при каждом push в ветки `work/**` и `factory/**`. Также полный прогон можно вручную запустить через GitHub → Actions → **kira** → **Run workflow**.

Один запуск выполняет независимые задачи параллельно:

1. Инвентаризация репозитория, аудит зависимостей и provenance.
2. Release-gate проверки.
3. Host/regression tests с sanitizers.
4. KCC compiler suite.
5. Driver installer end-to-end.
6. Сборка x86_64 и бинарный аудит ISO/KiraFS.
7. Сборка ARM64 и QEMU-сценарии ARM64.
8. Полная x86_64 QEMU-матрица — 10 параллельных shards.
9. Отдельные проверки Mind и GUI.
10. Сводный отчёт, затем упаковка обновления.

Матрица QEMU использует `fail-fast: false`: сбой одного shard не отменяет остальные, поэтому в отчёте остаются результаты всей партии. Сборка обновления запускается только после успешного завершения обязательных jobs. Дополнительно `ci/package_update.sh` запускает `ci/release_gate.py`; пока архитектурные блокеры в `docs/RELEASE_GAPS.md` не закрыты, архив намеренно не выпускается.

Pull request прогоняет проверки изменений, но полный QEMU matrix намеренно запускается на push в рабочую ветку или через Run workflow. Поэтому рабочий цикл: создать/обновить `work/<задача>` → push → дождаться полного прогона → проверить результаты.

## Настройка email

GitHub Actions не может отправить письмо на произвольный адрес без почтового провайдера. Для отправки завершённого отчёта настройте секреты репозитория:

GitHub → **Settings** → **Secrets and variables** → **Actions** → **New repository secret**.

Добавьте:

| Secret | Значение |
|---|---|
| `KIRA_SMTP_HOST` | SMTP-сервер вашего почтового провайдера |
| `KIRA_SMTP_PORT` | Обычно `587` (STARTTLS) или `465` (SSL) |
| `KIRA_SMTP_USERNAME` | Логин SMTP |
| `KIRA_SMTP_PASSWORD` | Пароль приложения или SMTP-пароль |
| `KIRA_SMTP_FROM` | Адрес отправителя; можно не задавать, если он совпадает с SMTP username |
| `KIRA_NOTIFY_EMAIL` | Адрес получателя уведомлений |

Секреты используются только в job уведомления. Пароли и адреса не записываются в репозиторий и не печатаются в логах. Если SMTP-секреты не заданы, сборка и тесты всё равно завершатся, а job уведомления сообщит в Actions Summary, какие настройки отсутствуют. Ошибка почтовой отправки не маскируется под успешную доставку.

Письмо отправляется после завершения сборочных jobs, сводного отчёта и упаковки. Оно содержит итоговый статус каждого этапа, commit SHA и прямую ссылку на запуск. При успешном выпуске архив и SHA-256 доступны в разделе **Artifacts** соответствующего запуска GitHub Actions.

## Как работать с результатами

После письма откройте ссылку на запуск и при необходимости скачайте артефакт. Затем отправьте в ChatGPT ссылку на запуск или короткое сообщение «Проверь сборку KIRA OS». Проверка должна включать итоговые статусы jobs, логи упавших этапов, содержимое QEMU result.json, отчёт бинарного аудита и соответствие архива точному commit SHA.

Ни один сбой не считается исправленным простым повторным запуском. Сначала определяется причина; затем исправление коммитится в рабочую ветку, после чего полный цех автоматически запускается заново.

## Границы автоматизации

GitHub Actions выполняет сборку и тесты независимо от открытого чата. Он не может поручить ChatGPT анализировать результаты или менять исходники после завершения workflow. Для этого нужно открыть чат и передать ссылку/уведомление. Физическое тестирование на реальном x86_64/ARM64 оборудовании не заменяется QEMU.
