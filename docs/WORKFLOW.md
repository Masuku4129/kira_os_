# Технология разработки и выпуска KIRA OS

## Обязательные правила
- Комментарии, пользовательские сообщения и отчёты — по-русски; системный журнал ядра `[KIRA ...]` — по-английски.
- Только реальные реализации: без заглушек, фиктивных тестовых результатов и молчаливых обходов. Неподдерживаемое оборудование должно получать явный отказ.
- Общий код не привязывать к одной архитектуре. Архитектурные операции проводить через интерфейсы `arch/<арх>/`.
- Не добавлять сторонние runtime-библиотеки в ОС. Build/test tools допустимы только как инструменты разработки; каждая зависимость в конечном ISO/KiraFS учитывается отдельно.
- Любое изменение проверять сборкой x86_64 и ARM64, host-тестами и затронутыми QEMU-сценариями. Результаты физического железа выделять отдельно.
- Не считать QEMU доказательством совместимости с реальными устройствами.
- Секреты, токены и ключи подписи не коммитить. Приватные ключи выпуска хранить вне репозитория.

## Рабочий процесс
1. Создать отдельную ветку от актуальной интеграционной базы и зафиксировать точный базовый SHA.
2. Ограничить изменение одной подсистемой или согласованной группой файлов.
3. Добавить тесты до/вместе с изменением; отрицательные сценарии обязательны для загрузчика, криптографии, драйверов и DMA.
4. Запустить сначала узкие тесты, затем `bash tests/run_host_tests.sh`, обе сборки с `-Werror`, релевантные QEMU-сценарии и полный CI.
5. Изучить логи упавших jobs; статус job сам по себе не является диагностикой.
6. Открыть PR с описанием причины, поведения до/после, тестов, ограничений и непроверенного физического оборудования.
7. Интегрировать только после проверки diff и зелёного обязательного CI. Не force-push поверх чужой работы.

## Ветки и релизы
- `main` — опубликованная база.
- `v45/overhaul` — текущая рабочая линия v45.
- `v46/release-completion` — интеграционная ветка закрытия архитектурных пробелов перед следующим общим выпуском.
- `ci-results*` — автоматически публикуемые результаты тестов; это не ветки исходного кода.
- Промежуточные артефакты не объявлять релизом. Следующий пользовательский архив выпускать только после общей интеграции, бинарного аудита ISO/KiraFS, контрольных сумм и итогового отчёта.

## Текущие release blockers
- Собственный BIOS/UEFI loader вместо GRUB/Multiboot2.
- KCC: измеримый путь к self-hosting; сейчас полный системный toolchain зависит от Clang/LLD/NASM/wasm-ld.
- RTL8139: заменить BSD-derived реализацию на чистую реализацию по спецификации.
- KDRV: end-to-end подпись Ed25519, доверенные ключи, срок действия и anti-rollback. SHA-256 сам по себе не аутентифицирует издателя.
- DMA: IOMMU-домены или безопасный отказ от bus mastering для недоверенных устройств.
- ACPI `_PRT`/legacy INTx, ARM64 non-coherent DMA и физическая проверка оборудования.
- GUI и Mind: продолжать регрессионные, длительные и fault-injection проверки; не объявлять host-модель реальным аппаратным тестом.

## Формат отчёта
Для каждого изменения указывать:
- что изменено и зачем;
- какие точные тесты выполнены и их результат;
- что осталось непроверенным и почему;
- известные ограничения и риск для релиза.
