# Время реакции: что меряем, какие границы держим

Обновлено: 2026-11-17

Это описание пункта плана А8 простыми словами. Код: `latency.c`, `latency.h` (счёт без зависимостей от ядра), `latency_k.c` (подключение к ядру, команда `latency`), политика границ `ci/latency_policy.json`, проверка `ci/latency_check.py`, сценарий QEMU `latency`.

## Зачем

Станок, насос или конвейер не прощают «иногда задумался». Среднее быстродействие здесь не важно: важно, как плохо бывает в худший час. Поэтому ядро само меряет, насколько система опаздывает, и мы записали верхние границы как требование: если после правки система стала опаздывать сильнее, проверка падает.

## Что меряется (три вида опозданий и две диагностики)

| Название в команде | Что это | Как меряется |
|---|---|---|
| `irq` | Задержка прерывания: от момента, когда таймер процессора должен был сработать, до первой строки обработчика | По счётчику самого таймера LAPIC (x86-64) или регистру сравнения CNTV (ARM64): «сколько тактов прошло с последнего срока». Если несколько сроков слиплись в одно прерывание, ядро помнит последний принятый срок и считает от первого непринятого |
| `isr` | Сколько обработчик аппаратного прерывания держит ядро | Два чтения счётчика времени вокруг вызова |
| `irqoff` | Как долго ядро сидит с выключенными прерываниями в одной критической секции (`irq_save` / `irq_restore`, спинлоки с irq) | Только если включено `latency irqoff on`; когда выключено, в каждой паре остаётся одна проверка слова в памяти |
| `spin` | Сколько ядро крутится в ожидании чужого замка (билетный спинлок с irq, замки планировщика) | Только на занятом замке: счётчик времени до и после ожидания |
| `sched-normal`, `sched-critical`, `sched-realtime` | Задержка планировщика: от «поток стал готовым» (его разбудили) до «поток получил процессор», по классам приоритета | Метка времени ставится при пробуждении, читается при запуске потока. Поток, вытесненный по концу кванта, не считается: он уступил процессор по правилам круговой очереди |
| `tick-part` | Из чего складывается время обработчика тика: часы, UART, чёрный ящик, сторож, планировщик | Диагностика: «кто виноват» в `isr` |

Всё считается на каждом ядре отдельно, без замков и без общих счётчиков в горячем пути: ядро пишет только в свою таблицу. Гистограмма логарифмическая: 4 корзины на каждую степень двойки, от 16 нс до 201 мс (всё, что дольше, лежит в последней корзине, а наибольшее значение хранится точно). Для каждого вида хранятся: число замеров, сумма, максимум и место максимума, число превышений порога и восемь «самых долгих мест» (где именно ядро задержалось).

## Команды

- `latency` - сводка по всем видам: число, среднее, p50, p99, p99.9, максимум, превышения, порог; гистограммы (строки `[LATH]`), самые долгие места (`[LATS]`), максимум по каждому ядру (`[LATC]`). `latency short` - то же без гистограмм.
- `latency reset` - обнулить гистограммы и счётчики превышений (пороги остаются). Сброс не обходит чужие ядра: он поднимает общую «эпоху», и каждое ядро обнуляет себя при следующей записи.
- `latency limit ИМЯ нс` - порог вида (0 - без порога); без аргументов - список порогов. Замер выше порога увеличивает счётчик превышений и пишет событие в чёрный ящик: `[KIRA LAT] irqoff: 14153165 нс при пороге 10000000, место K+0x2b6a4`. Запись делает не горячий путь, а тик таймера (не чаще 10 в секунду на вид, остальное только считается).
- `latency irqoff on|off` - замер критических секций.
- `latency bench` - цена пары `irq_save`/`irq_restore`: прежний код, новый код при выключенном замере, новый при включённом.
- `latency inject isr нс` - проверочная задержка обработчика таймера (каждый 64-й тик на каждом ядре). Нужна только для проверки границ мутацией: сценарий `latency-mutation` обязан упасть.

## Границы (требование)

Файл `ci/latency_policy.json`. Что в нём и откуда числа - в разделе «Стенд и границы» ниже. Стенд: QEMU в режиме TCG (программная эмуляция, без KVM). Он шумит: виртуальное ядро делит физические ядра хозяина с другими процессами, а любая остановка эмулятора ядро видит как «опоздание». Поэтому границы стенда - не обещание для железа, а порог «стало заметно хуже». На настоящем процессоре границы пересматриваются по тому же сценарию (команда та же), и цифры там должны быть на порядки меньше.

## Как проверить

```
python3 ci/kira_vm.py --scenario latency            # границы соблюдены
python3 ci/kira_vm.py --scenario latency-mutation   # искусственная задержка: проверка обязана УПАСТЬ (сценарий проходит именно из-за падения)
bash tests/run_host_tests.sh                         # хост-тесты счёта: корзины, пороги, сброс, слияние по ядрам
python3 -m unittest ci.test_latency_check            # разбор вывода и сравнение с границами
```
