# KIRA OS — целевая архитектура и обязательная базовая линия

Статус: целевое архитектурное решение, а не заявление о текущей готовности.
Дата: 2026-11-12.

## 1. Миссия и неизменяемые требования

KIRA OS — универсальная независимая ОС со своим ядром, собственными средами выполнения, интеллектуальным управлением, запуском приложений Windows и Linux через совместимые API/runtime, а также запуском целых гостевых ОС через аппаратную виртуализацию.

Ни одно направление не исключается из конечной цели:
- собственное ядро и системные службы;
- Native Runtime, WASM Runtime и собственная KIRA VM;
- отдельные среды совместимости приложений Linux и Windows;
- KIRA Hypervisor для полноценных гостевых ОС;
- KIRA Mind как интеллектуальный контур с ограниченными полномочиями;
- графическая среда и системные приложения;
- x86-64 и ARM64;
- драйверы, хранилище, сеть, установка, обновление и восстановление.

Главный принцип: независимость без изоляции подсистем друг от друга. Компоненты модульны, связаны формальными контрактами и не обходят общую модель безопасности.

## 2. Архитектурные принципы

1. Чёткие обязанности, владельцы данных и документированные интерфейсы.
2. Минимальное, но полноценное привилегированное ядро. В нём остаются механизмы управления памятью и адресными пространствами, планирование, прерывания, syscalls, базовые процессы/потоки, синхронизация и защищённый IPC. Политики и сложные службы по возможности работают в user space.
3. Единая модель идентичности, capabilities, изоляции, доверия, подписей, аудита и политик для приложений, служб, драйверов, VM и Mind.
4. Отказ службы не должен автоматически рушить ядро и несвязанные службы. Нужны health checks, watchdog, restart policy и восстановление состояния.
5. Версионированные ABI/API, правила совместимости и миграции.
6. x86-64 и ARM64 — обязательные цели; общая логика отделена от arch-specific кода через HAL.
7. Каждое архитектурное обещание имеет критерии, тест и среду доказательства.
8. Файл, прототип, успешная компиляция или запуск в эмуляторе не доказывают готовность функции.

## 3. Целевая модель уровней

### Уровень 8 — пользовательская среда
Desktop, compositor, Explorer, Settings, Terminal, GUI toolkit, accessibility и системные приложения.

### Уровень 7 — среды приложений
Native Runtime и KIRA Application ABI; WASM Runtime с verifier и sandbox; KIRA VM со спецификацией байткода, verifier и runtime; Compatibility Runtime для Windows/Linux.

### Уровень 6 — системные службы
Process/Service Manager, сеть, хранилище, графика, звук, ввод, пакеты, обновления, устройства и пользовательские сессии.

### Уровень 5 — интеллект и управление
KIRA Mind: телеметрия, диагностика, прогнозирование, рекомендации, ограниченная адаптация, контролируемые запросы и помощь восстановлению.

### Уровень 4 — безопасность
Capability authority, политики, sandbox, изоляция адресных пространств, secure boot, подписи, keyring и аудит.

### Уровень 3 — KIRA Kernel
Планировщик, память/виртуальная память, процессы и потоки, IPC, syscalls, прерывания, синхронизация, таймеры, SMP и ресурсы ядра.

### Уровень 2 — HAL и драйверы
Backend x86-64/ARM64, Device Model, PCI/PCIe, USB, GPU, NVMe, DMA/IOMMU, IRQ, ACPI/Device Tree и power management.

### Уровень 1 — аппаратная платформа
CPU, RAM, MMU, контроллеры, шины, устройства и firmware.

### Отдельная подсистема — KIRA Hypervisor
Аппаратная виртуализация и изоляция гостевых ОС. Это не runtime приложений. Гипервизор интегрируется с kernel, memory manager, interrupt routing, IOMMU и security policy.

### Сквозные компоненты
KiraFS/VFS, KCC/toolchain, Package Manager, Boot Manager, Installer, Update/Recovery, Service Manager, Event Bus, Resource Manager, Device Model, Power Manager, Crash Recovery, Observability, SDK и тестовая инфраструктура.

Уровни — логические границы, а не требование превращать каждый уровень в отдельный процесс. Размещение определяется безопасностью, производительностью и отказоустойчивостью.

## 4. Обязательные межкомпонентные контракты

Специфицировать и версионировать:
- Kernel syscall ABI и Application ABI для x86-64/AArch64: calling convention, версии, ошибки и структуры аргументов.
- IPC: типизированные сообщения, ownership endpoint, handles/capabilities, shared memory, отмена, таймауты, backpressure и отказ peer.
- Capability model: выдача минимальных полномочий, делегирование, отзыв, наследование и аудит.
- Process/thread model: lifecycle, address spaces, handles, события и exit status.
- Memory/DMA: page ownership, pinning, DMA mapping, IOMMU domains и освобождение.
- Device Model/Driver ABI: discovery, probe/bind/unbind, ресурсы, IRQ, DMA, power states, версии и безопасное удаление.
- Service contract: manifest, зависимости, запуск, readiness, health, restart, permissions и upgrade.
- Event Bus: схемы/версии событий, доставка, ordering, права публикации/подписки и backpressure.
- VFS/KiraFS: namespace, mount, file handles, durability и crash recovery.
- Package/update: manifest, подписи, зависимости, атомарное применение, rollback и сохранность пользовательских данных.
- Runtime host ABI: контролируемый доступ к FS, сети, графике, IPC и устройствам.
- Mind control API: декларативные запросы с областью, пределами, TTL, причиной и журналированием; получатель самостоятельно проверяет полномочия.

Для каждого контракта определить владельца, версии, ошибки, инварианты, негативные тесты и правила совместимости.

## 5. Запуск приложений Windows и Linux — отдельное требование

Это не заменяется виртуализацией целой ОС.

### Linux
Целевой путь: ELF loader → Linux-compatible process/runtime → Linux syscall ABI и нужные userspace ABI → адаптация к KIRA services. POSIX не равен полной Linux-совместимости. Отдельно анализировать Linux-специфичные syscalls, procfs/sysfs, namespaces, futex, signals, epoll, io_uring и библиотеки.

### Windows
Целевой путь: PE/COFF loader → Windows process/runtime → Win32 API и выбранная NT user-mode semantics → KIRA host services. Одного PE loader недостаточно. Учитывать DLL loading, threads, synchronization, virtual memory, files, registry semantics, processes, sockets, graphics, audio, fonts, locale и installers.

### Общие правила
- Раздельные Linux и Windows compatibility subsystems с общим нижним KIRA host interface. Не смешивать разные семантики в один универсальный API.
- Compatibility layer работает в user space, в sandbox и через capabilities.
- Никакого обхода security model и прямого произвольного доступа к ядру.
- ISA поддерживается явно: x86-64 на x86-64, ARM64 на ARM64. Cross-ISA translation — отдельная capability, не подразумеваемая автоматически.
- Вести API coverage matrix и список реальных приложений/версий/архитектур/зависимостей/сценариев.
- Не копировать чужие системные библиотеки без прав; проверять provenance и лицензии.
- Не обещать запуск произвольного приложения до тестирования конкретной версии и сценария.
- App sandbox/контейнеры — отдельная модель изоляции; они не являются Hypervisor.

Этапность: спецификации loader/ABI → минимальные ELF/PE loading paths → process/thread/memory/files/socket primitives → расширение syscall/API coverage по приоритетной матрице → графика/звук/ввод/installers → compatibility dashboard.

## 6. Четыре разных пути выполнения

- Native Runtime: приложения под KIRA ABI.
- WASM Runtime: валидированный WASM с явными импортами и sandbox.
- KIRA VM: собственный специфицированный bytecode, verifier и runtime.
- Windows/Linux Compatibility Runtime: соответствующие внешние ABI/API.
- KIRA Hypervisor: целые гостевые ОС с виртуальными CPU, памятью и устройствами.

У каждого пути свои форматы, loader/verifier, полномочия, lifecycle, диагностика и тестовая матрица. Не объединять их в одну неразличимую «виртуальную машину».

## 7. KIRA Mind — ограниченный управляющий контур

Mind получает телеметрию через документированные read-only интерфейсы и отправляет предложения через control API. Запрос содержит субъект, цель, область воздействия, ожидаемую пользу, пределы, TTL и причину. Служба-владелец ресурса проверяет полномочия и safety constraints. Критические действия требуют политики/подтверждения и журналируются. Mind не меняет page tables, scheduler internals, driver state или kernel memory напрямую.

## 8. Драйверы

Единый Device Model и версионированный Driver ABI. Driver Manager отвечает за discovery, provenance, лицензии, подписи, совместимость, установку, активацию, откат и диагностику. Драйверы по возможности изолированы; привилегированный код минимизирован. Автоадаптация допустима только для известных интерфейсов при законном происхождении, воспроизводимой сборке и успешных тестах. Успешная компиляция чужого драйвера не доказывает совместимость или безопасность.

## 9. Хранилище, обновление и восстановление

KiraFS/VFS, package manager, update и recovery проектируются совместно. Нужны целостность, crash consistency, атомарное переключение системной версии, rollback, сохранность пользовательских данных, проверка подписей и тесты внезапного отключения питания.

## 10. Обязательные системные службы и инфраструктура

Service Manager, Event Bus, Resource Manager, Device Model, Power Manager, Crash Recovery, Observability (structured logs/metrics/tracing), Compatibility API, Developer SDK, Package Manager, Update/Recovery и Installer. Компонент может быть логически объединён с другим, если его обязанности явно покрыты контрактом и тестами.

## 11. x86-64 и ARM64

Проверять calling conventions, atomics, memory ordering, page tables, interrupt controllers, timers, SMP, cache coherency, DMA/IOMMU, firmware handoff и virtualization extensions. Эмуляторные результаты и физическое оборудование фиксировать отдельно.

## 12. Критерии готовности

Компонент считается реализованным только если production implementation не является stub/mock; контракт документирован; есть позитивные, негативные и fault-injection тесты; тесты запущены на конкретном SHA и окружении; межподсистемная интеграция подтверждена; security review выполнен для привилегированных границ; ограничения и поддерживаемые ISA/API задокументированы.

Статусы: Реализовано / Частично / В разработке / Не начато / Не проверено / Заблокировано. «Собирается», «работает в QEMU», «работает в Limbo» и «проверено на физическом железе» — разные факты.

## 13. Приоритет

При конфликте быстрой функции с целостностью архитектуры приоритет у контракта, безопасности и проверяемости. Все направления могут исследоваться и развиваться параллельно, но интеграция идёт по зависимостям. Никакая целевая возможность не вычёркивается молча.
