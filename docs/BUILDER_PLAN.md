# Сборщик Киры (KCC + свой ассемблер + свой компоновщик): план этапов и критерии приёмки

Цель: сборщик, который живёт в Кире, собирает ядро и программы без clang, nasm и ld.lld и **не уступает clang -O2 по скорости и качеству итоговых программ**. Слова «не уступает» здесь заменены измеримыми порогами, иначе их нельзя проверить. Если пороги не выполнены, обновление выходит как PREVIEW, и это пишется прямо.

## Критерии приёмки (проверяет tests/kcc/bench)
Набор из 10+ программ: решето, матрицы, хеш, сортировка, SHA-256 из репозитория, разбор строк/memcpy-подобные циклы, связные списки/деревья (указатели), mind.c (вывод сети), крошечные функции с вызовами, битовые операции. Для каждой: время выполнения (минимум из 5), размер кода, время компиляции.
- Скорость кода: среднее геометрическое по набору не более +10% к clang -O2, худший случай не более +25%.
- Размер кода: не более +10% к clang -O2 (сейчас у ядра +78%).
- Время компиляции: не хуже clang -O0 на тех же файлах (сейчас в 11–22 раза быстрее; не терять).
- Корректность: tests/kcc/run.sh (464+ программ против clang), fuzz, selfhost (stage2 = stage3), ядро KCC грузится в QEMU, дифференциальные тесты каждого нового прохода (с флагом отключения для сверки).

## Этап 0. Замеры (сначала измеряем, потом оптимизируем)
tests/kcc/bench/*.c, раннер bench.sh с порогами выше. Без этого «быстрее clang» недоказуемо.

## Этап A. Качество кода (по одному проходу, каждый с замером и откатом, если не помогает)
- A1. Ширина целых без постоянной нормализации: значения 32 бит хранятся «грязными» в 64-битном регистре, 32-битные команды и сравнения, расширение только там, где нужен 64-битный контекст (индекс, вызов, преобразование). Убирает movsxd после каждой операции (видно в матрицах).
- A2. Развёртка простых счётных циклов (2–4 раза) с остатком, после понижения силы; свёртка редукций.
- A3. GVN/CSE и устранение лишних загрузок (store-to-load forwarding по слотам и глобалам, простой анализ псевдонимов: слот не уходит, разные глобалы не пересекаются).
- A4. Адреса глобалов: прямая адресация [abs32 + idx*s] в не-PIE режиме / RIP-относительная, вынос lea из циклов при наличии регистров.
- A5. Регистры: расширить пул (rsi, rdi, r11, caller-saved для интервалов без вызовов), раздельное сохранение callee-saved только используемых, листовые функции без кадра.
- A6. Встраивание: порог по размеру и числу вызовов, межпроцедурные константы.
- A7. Выбор команд: lea для сложения, test, cmov/setcc, кодирование короче, хвостовые вызовы.
- A8. Размер: удаление недостижимых функций на уровне функций (аналог --gc-sections), слияние одинаковых констант.
- A9. AArch64: те же проходы, `ror`, `-c`.
Числа с плавающей запятой (SSE2/NEON) — отдельным этапом после B, если понадобятся приложениям; для ядра не нужны.

## Этап B. Автономность (убрать nasm и ld.lld)
В ядре x86_64 всего 5 файлов .s (~850 строк в синтаксисе nasm) плюс загрузочные 16-битные stage1/stage2 (отдельный путь).
- B1. Ассемблер: подмножество nasm, реально используемое в этих файлах (проверяется по списку мнемоник), секции, метки, `%define`/`%macro` минимум, 64/32/16-битные режимы, данные. Тест: байт-в-байт с nasm на наших файлах.
- B2. Компоновщик: несколько ET_REL объектов, символы, перемещения (R_X86_64_PC32/32S/64/PLT32), сборка секций, подмножество скрипта (kernel.ld/user.ld), --gc-sections. Тест: ядро и userland собираются им и загружаются; сравнение поведения с ld.lld.
- B3. Режим «одна команда сборки»: kcc build собирает дерево по манифесту.

## Этап C. Цех с боксами (параллельная сборка)
- C1. Убрать глобальный KCtx: контекст на бокс, своя арена.
- C2. Планировщик заданий с приоритетами и типами боксов (сборщик, верификатор, оптимизатор-перебор). Нужен SMP в ядре и потоки пользователя.
- C3. Замер: параллельная сборка ядра против последовательной (ожидаем выигрыш только на многоядерных машинах).

## Этап D. ИИ + сборщик (параллельно, делает помощник)
Интерфейс «задание на сборку» с песочницей и квотами, метрики эффективности ИИ на существующем стенде, проверка человеком перед установкой собранного. Ни одного пути «ИИ сам себя перепрошивает» без подписи и подтверждения.

## Этап E. Безопасность памяти и итог
DMA-изоляция (VT-d/SMMU) — что реально есть и чего нет; ACPI _PRT; анти-откат драйверов; подписанный каталог. Затем сборка образов, манифест, SHA-256, архив PREVIEW.

## Порядок и честность
0 → A1 → A2/A3 → A4/A5 → замер → B1 → B2 → замер → (A6–A9 по результатам) → C. После каждого этапа — запись результатов в docs/KCC.md с реальными числами. Если порог не достигнут, пишем об этом, а не подгоняем.

## Этап D: состояние (измерено на хосте; на железе и в QEMU внутри Киры не проверялось)
**Стенд эффективности Разума** (`tests/mind_eff_test.c`): замкнутый детерминированный сценарий (передний план 40% ядра, фон из 4 потоков, три тяжёлых всплеска по 60/60/80 с и один безвредный на 5 с, 900 с, окна тактики 25 мс), один и тот же мир прогоняется с `MIND_OBSERVE` (это «без Разума») и `MIND_ACT`. Мир моделирует только процессорную причину опозданий, поэтому числа описывают поведение контроллера на этой модели, а не на железе. Метрики: доля опоздавших кадров, задержка реакции, секунды заметных опозданий, задержка снятия предела, ложные действия, цена для фона, дрожание предела (смен в минуту), Brier предвидения.
До/после (act, тот же стенд): опоздавшие кадры внутри всплесков 21 -> 5 промилле (без Разума 578), смен предела фона 236 -> 61 в минуту (вызовов set_limit 799 -> 216), секунд с опозданием >= 5% кадров 2 -> 0 из 200, реакция 175-200 мс (не изменилась), доля сохранённой работы фона 56% (не изменилась). Цена: фон возвращается медленнее после конца всплеска, задержка снятия предела 0,8-1,2 с -> 2,9-5,5 с. Причина слабого места: шаги снятия предела упирались в границу 79% на поток, давление возвращалось, предел снова ужимался (цикл 1,4 с). Исправление в `mind_tact_step`: если давление вернулось не позже чем через 3 с после шага снятия, выдержка перед следующим снятием удваивается (не больше чем в 4 раза, `MIND_REL_BACKOFF_MAX`), сбрасывается при полном снятии, укорачивается после 10 с без возврата. Зависимость от константы: 0 -> 236 смен/мин, 1 -> 119, 2 -> 61, 3 -> 33 (снятие до 11,5 с).
**Задание на сборку** (`mind_build*.c`, `buildcmd.c`, `userland/kcc.c`): шаблон (зонд, таблица) -> ворота исходника (без препроцессора и asm, число лексем) -> kcc с жёсткой ареной -> `elf_parse` -> песочница `/data/kcc` + запись «ожидает». Запуск возможен только после разрешения человека (первые 8+ знаков SHA-256 образа) или подписи (`kdrv_sig_verify`, `kdrv_trust_keys`); `mbj_check_grant` перечитывает образ и сверяет хеш в момент запуска.
*Подключено (проверено в QEMU, tests/mind_build_boot_test.sh):*
- Раскладка: `mind_build_core.c` (общее), `mind_build.c` (СБОРКА; линкуется в `/bin/kcc`, режим `@build`, процесс только с CAP_FS), `mind_build_grant.c` + `buildcmd.c` (РЕШЕНИЕ; в ядре). Сборка идёт отдельным процессом без прав; консоль ядра лишь ставит ему задачу (`prog_run_args("kcc", "@build ...")`), печатает отчёт и принимает решение человека.
- Консоль: `build probe N SEED`, `build table N MUL MOD`, `build list` (ядро само считает SHA-256 образа и сверяет с записью), `build allow ИМЯ ХЕШ` (8+ знаков, регистр не важен), `build allow ИМЯ sig` (подпись из `/data/kcc/ИМЯ.sig`), `build run ИМЯ`, `build drop ИМЯ`.
- Разрешения НЕ лежат в песочнице: сборщик (kcc) пишет в `/data/kcc` что угодно, поэтому `.ok` читается только из таблицы ядра (`mbj_grants_t`, 8 мест, в памяти). Файл `.ok`, подброшенный в песочницу, ядром игнорируется (проверено и на хосте, и в QEMU). После перезагрузки решение нужно дать заново.
- Запуск: `mbj_check_grant` возвращает проверенные байты, `prog_run_local_image` запускает ИМЕННО их (файл заново не читается: окна подмены между проверкой и запуском нет) как `local-ИМЯ` с caps = 0 и иммунной проверкой, как `runlocal`. Новых путей запуска без разрешения нет: образ с другим хешем, без `.ok` в таблице ядра или с изменённым размером не запускается.
- Разум: единственная связь - `build_mind_tick` из `mind_sys_tick` (правило `mind_build_propose` + `mbj_rate`: не чаще одного предложения за 10 минут, не больше 4 ожидающих). Печатает в serial строку «[BUILD] Разум предлагает задание ..., выполнить: build probe N SEED» и запоминает её для `build`. Не собирает, не разрешает, не запускает. `tests/mind_build_test.sh` проверяет по исходникам, что файлы Разума не называют allow/run/prog_run/песочницу `/data`, а вызовы выдачи разрешения и запуска образа есть только в `buildcmd.c`, `console.c` и определяющих файлах.
- Хранилище: put/get через VFS в `/data/kcc` (сборщик - через свою песочницу `k_file_*`, ядро - через `kfs_*`, имена `[A-Za-z0-9._-]`, не с точки, без `/`; имя образа `mb<шаблон><6 знаков хеша исходника>`, 9 знаков - лимит имени `runlocal`).
- Реальные, не условные: часы - `k_clock_ns` (сборка) и RTC ядра (срок подписи); арена - 1 МБ из `k_heap_grow` без роста; окно адресов - `proc_user_window()` (те же числа, что у `spawn`), сборщик использует то же окно и предел 64 страницы, а решающая проверка с настоящим пределом - в ядре при `allow` и `run`.
*Тесты:* `tests/mind_build_test.sh` (хост: шаблоны, ворота, квоты, мусорные исходники, разрешения, подпись настоящим tools/kdrvsign.py, окружение ядра с таблицей разрешений, подделка `.ok`, подмена образа и записи, запуск под kloader с эталоном хоста); `tests/mind_build_boot_test.sh` (QEMU, ввод через последовательную консоль, сценарии `mind-build` и `mind-build-propose` в ci/scenarios.py): build probe -> хеш в отчёте и в `build list` совпадают -> run без разрешения отказ -> allow с неверным и коротким префиксом отказ -> подброшенный `.ok` не действует -> allow с верным -> run без прав, код возврата = расчёт хоста (probe 50000/7 = 1153170643, table 64/37/1009 = 1000474) -> запись поверх образа -> run и allow отказ -> drop; предложение Разума появляется строкой и ничего не запускается.
*Чего нет / границы:* время сборки проверяется после неё (в kcc нет хука прерывания; сверху держат лексемы и размер, зависший процесс снимает `kill`; автоматического снятия по таймеру нет); подпись проверена на хосте с тестовым ключом (`KDRV_TEST_TRUST`), в QEMU путь `build allow ИМЯ sig` не гонялся (рабочий ключ издателя вне системы); сборщик остаётся доверенной частью: человек подтверждает хеш образа, а не его смысл (образ строится из шаблона, но подмену самого сборщика хеш не выявит; ограничение - права процесса и отсутствие запуска без решения); разрешения не переживают перезагрузку; у Разума нет потребителя результата зонда (измеренная скорость нигде не используется); на ARM64 режим `@build` собирается, но в QEMU не запускался; защита от отката времени подписи (kdrv_state) здесь не подключена; ввод `build ...` принимает любой источник консольных строк, включая `console_request` из окон Проводника (это ввод человека, но не отдельный канал подтверждения).

## Этап F. Как реально выиграть у clang (технология, а не подгонка проходов)
Честная постановка: в общем случае (любой код, раздельная компиляция, автовекторизация) LLVM с его десятилетиями настройки мы не обгоним, и заявлять так нельзя. Выигрывать можно там, где у clang связаны руки, а у нас нет. Факты, которыми мы владеем и clang нет:
1. **Закрытый мир.** Мы собираем всё ядро и весь userland разом и знаем всех вызывающих. Clang на раздельной компиляции вынужден соблюдать ABI для любой функции, видимой наружу.
2. **Бюджет времени.** Наш компилятор в 11–22 раза быстрее clang -O0, поэтому на горячие функции можно потратить время на перебор, который clang себе не позволяет.
3. **Знание машины.** Сборка идёт на той же машине, где код будет работать: набор команд известен точно (без «generic x86-64»).
4. **Реальные профили.** ОС сама видит, какие функции горячие (таймер, счётчики) и может пересобрать их.
5. **Факты о программе в IR.** Типы, границы, отсутствие пересечения указателей, ненулевые указатели мы можем нести в IR как проверенные факты, а не угадывать как LLVM.

Этапы (каждый с замером tests/kcc/bench и отключающим флагом; без чисел результат не считается):
- **F1. Режим всей программы** (`--whole`): вывод внутренней видимости, встраивание по графу вызовов (стоимость против числа вызовов), межпроцедурные константы, удаление неиспользуемых аргументов и функций, собственное соглашение о вызовах для внутренних функций (все регистры свободны, аргументы там, где их ждёт потребитель), замена косвенных вызовов через таблицы с известными целями. Ожидаемый выигрыш: тесты `calls` (сейчас хуже всего, 2.3–2.9 к clang), `sha256`, `mlp`.
- **F2. Циклы:** развёртка с остатком, распознавание идиом (popcount, ctz/clz, bswap, поворот, rep movs/stos), затем векторизация простых циклов в SSE2/AVX2 по известному набору команд машины. Цель: `bits`, `strscan`, `matmul`.
- **F3. Типизированный IR с фактами:** noalias (из `restrict` и анализа), nonnull, диапазоны значений, выравнивание; использовать в LVN, LICM и выборе команд. Каждый факт либо проверен компилятором, либо взят из явной аннотации программиста.
- **F4. Перебор с проверкой:** для горячих блоков — выбор команд по графу эквивалентностей (e-graph) или суперoптимизация малых последовательностей. Любая замена принимается только после проверки эквивалентности (полный перебор на малой разрядности + случайные 64-бит векторы + дифференциальный прогон), иначе отбрасывается. Отдельный флаг и бюджет времени.
- **F5. Непрерывный PGO:** профиль из таймера ОС → пересборка горячих функций в «цехе»; нужна готовность этапа C (контекст на бокс, планировщик).
- **F6. Свой язык для инструкций ИИ и пользователя:** только после F1–F4, компилируется в тот же IR, чтобы получал все оптимизации. Не раньше, чем будет измерен выигрыш на C.
Порядок: F1 → F2 → F3 → F4 → F5; после каждого — запись реальных чисел в docs/KCC.md. Если порог (среднее ≤ +10% к clang -O2, худший ≤ +25%) не достигнут, обновление остаётся PREVIEW.

## Этап G. Широта языка C (чтобы писать серьёзные программы)
Сейчас kcc честно отвергает (tests/kcc/unsup): float/double, VLA, `_Generic`, `_Alignas`, `_Thread_local`, широкие строки и универсальные имена символов, вычисляемый goto, `_Complex`, часть атрибутов и `__has_include`.
- G1. float/double (SSE2 / AArch64 FP; ядро без SSE остаётся без FP) — сделано (см. docs/KCC.md), long double и float в asm не поддержаны.
- G2. `_Generic`, `_Alignas`/`alignof`, `__has_include` — только фронтенд, небольшие.
- G3. VLA — сделано (см. docs/KCC.md).
- G4. Широкие строки и UCN сделаны; `_Thread_local` ждёт TLS в ядре и klink (PT_TLS, TPOFF); `long double` не поддержан.
- G5. Вычисляемый goto и `_Complex` — по необходимости, не раньше.
Каждый пункт: принятие/отклонение и значения сверяются с clang в tests/kcc, перенос файла из unsup/ в ok/ или run/.
