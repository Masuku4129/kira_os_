# KIRA OS — аудит узких мест и Mind vNext

Дата аудита: 2026-11-10. Основание: исходники ветки `autodrv`, тесты и CI. Подтверждённые дефекты/ограничения отделены от направлений исследования.

## 1. Подтверждённые узкие места

### P1. Снимок планировщика слишком дорог в горячем пути — исправляется в PR #74

- `mind_sys.c:tact_main()` запускает тактику примерно каждые 25 мс и каждый раз вызывает `sched_snapshot()`.
- Секундный сборщик `gather()` также вызывает `sched_snapshot()`.
- До исправления `sched.c:sched_snapshot()` для каждого потока перебирал все CPU, пока удерживал общий `sched_lock` и локально держал IRQ выключенными: O(потоки × CPU) в критической секции.
- Исправление PR #74 использует `on_cpu + last_cpu + percpu_table[last_cpu].current`, то есть O(1) поиск активного CPU на поток. Общая сложность обхода становится O(потоки + CPU).

Критерии: host scheduler test; полный CI; повторяемый стресс с ростом потоков и CPU; отсутствие регрессии CPU accounting и времени ожидания замка.

### P1. KCC не готов к параллельной сборке

Подтверждено исходниками:
- `kcc/main.c` использует глобальный контекст `K`.
- `kcc/pp.c` содержит изменяемое file-static состояние препроцессора: таблицу макросов, unity mode, include depth, once list и выходной список токенов.
- `kcc/parse.c` и `kcc/ir.c` также содержат изменяемое file-static состояние.

Следствие: два одновременных вызова компилятора не имеют независимых контекстов. Внутренний «цех с боксами» не может безопасно выполнять несколько KCC-компиляций параллельно.

Задачи:
1. Перенести всё изменяемое состояние в `KCtx`/подконтексты.
2. Убрать скрытые глобальные зависимости из препроцессора, парсера, IR и генераторов.
3. Сделать независимую арену и конфигурацию на каждую компиляцию.
4. Добавить тест двух компиляций одновременно с разными target/define/include и сравнить результаты с последовательными сборками.
5. Только после этого подключать параллельный scheduler сборки.

### P1. Разум имеет только одну обучаемую цель

Подтверждено:
- `mind_model_t` содержит одну `mnet_t net`.
- `mind.c:foresight()` обучает её только на бинарном исходе «экран опаздывал не менее 5% в следующую секунду».
- В базе аудита было 12 признаков: CPU, очередь, память, фон/фокус, IPC, диск, переключения, число программ, текущие опоздания, ожидание и анимация. PR #78 добавляет 13-й признак валидности замера диска; даже после него у модели остаётся только одна цель.
- Давление памяти, голодание, ошибки устройств, сеть и звук имеют отдельные реактивные правила/сигналы, но не отдельные прогнозные модели.

Следствие: нынешняя модель не может заранее предсказывать несколько независимых классов отказа. Это адаптивный контроллер, а не универсальный ИИ.
- PR #75 уже влит: статус trusted теперь требует precision ≥ 50% и recall ≥ 25%, чтобы не допускать вырожденный редкий алертинг. Это минимальный фильтр полезности, а не доказательство промышленного качества.

### P1. Обучение предиктора зависит от режима вмешательства

Подтверждено результатом текущего CI `mind-quality` на детерминированном синтетическом сценарии:
- В observe: Brier 0.0144 против baseline 0.1692; модель получила 899 примеров и 194 положительных исхода.
- В act: 899 примеров, 0 положительных исходов, модель осталась untrusted и не выдала прогнозов.

Это не доказывает поведение на физическом железе. Но показывает эффект отбора: собственные реактивные действия контроллера могут предотвращать целевой сбой, поэтому активная модель не получает положительных примеров и не может заслужить доверие. Это безопаснее ложного доверия, но ограничивает пользу прогнозирования.

Задачи: отдельный shadow-канал обучения; маркировка интервалов, изменённых действиями; оценка без вмешательства на безопасных окнах; сравнение с baseline; никакого искусственного повышения счётчиков доверия.

### P1. Нет полноценного контракта качества телеметрии

- В признаках `mind.c:features()` отсутствие операций диска превращается в нулевую задержку; `q16()` при нулевом знаменателе возвращает 0.
- PR #78 добавляет отдельный признак валидности disk latency: отсутствие операций диска больше не кодируется как нулевая задержка. Это первый частный фикс, не общий контракт.
- Для остальных источников модель всё ещё не получает общего признака валидности/свежести. «Нет измерения» может выглядеть как «измерено нулевое значение».
- Архитектурный документ v44 уже требует явных признаков отсутствующих измерений, но реализация ещё не доведена до общего контракта.

Задачи: validity mask, timestamp/age, качество источника, диапазоны и единицы; запрет обучения на невалидной цели/признаке.

### P2. Один глобальный замок планировщика остаётся потенциальным пределом

В `sched.c` все per-CPU run queues по-прежнему меняются под одним `sched_lock`. Уже есть счётчики ожидания/контенции (`sched_lock_stats`). Сначала собрать сопоставимые данные на 1/2/4/8 CPU и при разных числах потоков; только затем выбирать lock sharding, per-CPU очереди без глобальной блокировки или иной механизм. Не менять замок наугад.

### P2. Доменная изоляция приложений ещё не равна App Box

PR #56 добавляет владение приватными IPC/SHM объектами и проверку между процессами. Это важная граница, но не полноценный App Box: нужны стабильный box identity, группировка процессов, квоты RAM/CPU/потоков, файловые allowlist, сетевые правила, отзыв полномочий и lifecycle.

### P2. Драйверная совместимость ограничена проверяемым набором

Текущий drvget получает и проверяет отдельные исходники по рецептам, хешам и лицензиям. Это не универсальный преобразователь драйверов любого производителя. Следующий этап — capability-ограниченный ABI адаптера, анализ зависимостей/регистров/IRQ/DMA, аппаратные профили и проверка в изолированной VM до допуска к ядру.

## 2. Новая архитектура ИИ

Не смешивать два разных продукта:

### A. KIRA Mind — системный интеллект

Остаётся малым, предсказуемым и ограниченным по времени ядровым сервисом:
- собирает телеметрию;
- выявляет отклонения;
- прогнозирует конкретные измеримые события;
- предлагает только типизированные действия;
- действует через отдельную политику с пределами, TTL, журналом и откатом.

Никакой произвольной генерации кода или прямого доступа обучаемой модели к функциям ядра.

### B. KIRA Assistant — пользовательский помощник

Отдельная user-space служба, не часть ядра:
- естественный язык и диалог;
- поиск по локальной документации/справке/настройкам;
- объяснение состояния ОС и причин решений Mind;
- планирование пользовательских задач;
- вызов системных операций только через capability-API и подтверждаемые разрешения.

Это отдельная разработка. Не называть текущую логистическую регрессию языковой моделью. Сначала обеспечить надёжный системный API и безопасный исполнитель; затем подключать локальную языковую модель/движок подходящего размера.

## 3. Очерёдность Mind vNext

### M0 — качество данных (первый этап)
- Ввести версионированный telemetry contract: значение, единица, timestamp, valid/stale, source.
- Обновить признаки так, чтобы отсутствие датчика/операции не было нулевым значением.
- Добавить тесты на отсутствующие, устаревшие, переполненные и противоречивые данные.

### M1 — независимые прогнозные головы
Добавлять по одной, сначала observe/shadow:
1. UI responsiveness — существующая модель, сохранить совместимость.
2. Memory pressure — прогноз достижения порога свободной памяти на горизонте 3–5 секунд.
3. Scheduler starvation — прогноз нарушения latency budget готового потока.
4. Storage/device degradation — прогноз повторных ошибок/задержек, только при валидной телеметрии.
5. Audio/network queue health — только после появления измеряемых источников.

Каждая голова имеет отдельные веса, версию, горизонт, число примеров, базовую частоту, качество и статус доверия.

### M2 — доказательство полезности
- Хронологическое разделение train/holdout, не случайное перемешивание соседних секунд.
- Сравнение с простым baseline.
- Brier score, log loss, precision, recall, false-positive rate, калибровка и размер выборки.
- Отдельные сценарии дрейфа, смены CPU/RAM, пропущенных датчиков и вмешательства контроллера.
- Ни одна модель не получает право действовать по синтетическому тесту без VM/интеграционного подтверждения.

### M3 — арбитр действий
- Прогноз не равен разрешению.
- Типизированный allowlist действий; лимиты на процесс и систему; срок действия; журнал причины; rollback.
- При низком доверии, stale data или дрейфе — observe only.

### M4 — панель Разума
Показывать для каждой цели: прогноз/горизонт, доверие, число примеров, baseline, качество, входные причины, предложенное действие, результат и откат.

### M5 — KIRA Assistant
Отдельный user-space процесс в App Box. Начать с локального поиска/справки и структурированного планировщика команд; затем добавить inference backend. Ядро не загружает языковую модель и не исполняет её код.

## 4. Общие критерии приёмки

- Ни одной заглушки или фиктивного измерения.
- Новые модели по умолчанию работают в observe.
- Сохранение/миграция моделей проверяется на старых форматах и повреждённых файлах.
- Нагрузка Mind измеряется: CPU time, lock wait, snapshot duration, missed tactical deadlines.
- Все действия ограничены политикой и обратимы.
- x86-64 и ARM64 проверяются отдельно.
- Любой PASS подтверждается запуском теста/CI на текущем head.


## 5. Первый кандидат для KIRA Assistant inference

Для первого стенда выбран **Qwen3-0.6B** как кандидат, а не production-выбор:

- официальная карточка Qwen указывает Apache-2.0 и поддержку более 100 языков; русский входит в мультиязычную область, но качество на KIRA-задачах ещё не измерено;
- архитектура плотная causal transformer: 28 слоёв, 16 Q heads / 8 KV heads (GQA), контекст 32 768;
- официальный GGUF-каталог ggml-org содержит Q4_0 около 429 MB и Q8_0 около 805 MB;
- llama.cpp поддерживает Qwen3 GGUF и имеет CPU-пути для x86 AVX и ARM NEON; использовать его как независимый reference runner и контроль совместимости, а не автоматически встраивать в ядро.

Ограничения:
- 429 MB — только веса; KV-cache, активации, tokenizer и runtime требуют дополнительной RAM;
- до включения в KIRA нужны измерения peak RAM, prefill/decode tokens/s, энергопотребления и качества на фиксированном русском наборе задач;
- проверять лицензию именно выбранного checkpoint и quantization artifact, хеши и происхождение;
- Qwen3.5-0.8B не брать первым: его гибрид Gated DeltaNet + attention добавляет отдельные операторы и расширяет объём первого inference ядра.
