## 1. Решения по слоям

| Область | Решение | Основание и ограничения |
|---|---|---|
| Модель ядра | Сохраняем существующее монолитное ядро с отдельными адресными пространствами приложений и сервисами Ring 3 / EL0. | Уже существует рабочая база; переписывание в микроядро не доказало бы преимуществ. Применяем идеи capability-модели seL4, но не заявляем формальную верификацию. |
| Изоляция приложений | По умолчанию минимальные полномочия, приватные IPC-объекты, W^X и отдельная таблица дескрипторов процесса. | x86-64 QEMU проверяет адресные пространства, отказ неразрешённых syscall, IPC, потоки и состояние FPU. Отдельные VM-домены Qubes и полноценная capability-transfer модель пока отсутствуют. |
| Язык ядра | C остаётся основным языком ядра; Clang — основной эталонный компилятор. | Существующий код ядра — около 37,5 тыс. строк и 133 объекта. Переписывание ядра на Rust не обосновано измерениями. |
| KCC | Развиваем как собственный компилятор и путь self-hosting, но не назначаем единственным production-компилятором. | KCC компилирует примерно в 7 раз быстрее Clang -O2 и использует 2,1–2,7 МБ против примерно 91 МБ. Но выполнение медленнее на 13,5% по геомеану, `.text` больше на 39,5%; ABI структур с float/double по значению несовместим. |
| Rust | Кандидат для новых парсеров, обработки недоверенных данных и отдельных драйверных/userland-компонентов; не переписывать всё ядро. | В четырёх измеренных нагрузках скорость близка к C; тесты показали, что безопасный Rust предотвращает часть дефектов памяти на этапе компиляции. Ограничения: размер panic/runtime, интеграция с KCC и отсутствие полноценной ARM64-оценки. |
| C++ | Допустим для изолированных userland-компонентов без обязательного тяжёлого runtime; не вводить как новый общий язык ядра. | В исследованных freestanding-нагрузках clang C++ близок к C. |
| Go | Не использовать для freestanding-ядра и ранних системных компонентов. | Измерение было PARTIAL: стандартный runtime делает результат несопоставимым с freestanding. |
| Ассемблер | Только загрузка, переключение контекста, прерывания и узкие архитектурные участки, где есть измеримая необходимость. | KAS совпал с NASM на 11/11 объектных файлах. Ручной asm в исследованной нагрузке дал около 7% в одном шумном замере при росте объёма кода примерно в 17 раз. |
| Компоновщик | KLINK развиваем, но LLD сохраняем как обязательный fallback для крупных программ. | KLINK связывает ядро примерно в 2,2 раза быстрее и использует меньше памяти, но текущий тест — 53 PASS / 13 FAIL / 1 SKIP; крупные userland-программы с `R_X86_64_GOTPCREL` не собираются. |
| Объектный формат | ELF64 ET_REL остаётся общим объектным форматом. | Существующие компиляторы, ассемблеры и загрузчики уже работают с ELF. Альтернативный объектный формат не показал измеренного выигрыша. |
| Исполняемые файлы | ELF остаётся форматом программ и драйверного ELF payload. Для ARM64 сохраняется Linux Image-подобный 64-байтный заголовок загрузочного Image поверх собственного ELF. | KEX дал −9,5% на несжатых 26 программах, но преимущество почти исчезло после сжатия и не улучшило парсер, скорость или безопасность. Решение исследования — KEX не вводить. |
| Пакет драйвера | Сохраняем `.kdrv` + `.rec` + detached Ed25519 `.sig`. | Сквозной набор подписи и формата прошёл 12/12 тестов. Не сливаем эти данные в KEX ради экономии не более примерно 500 Б на пакет. |
| Форматы данных | Не вводим один универсальный формат: Fixed Binary — структуры ядра/диска; Varint+delta — последовательные журналы и телеметрия; Columnar+zstd — архивы/аналитика; CBOR или MessagePack — самоописываемый обмен; JSON — диагностика. | Data Format Lab измерил разные профили выигрыша. На синтетической телеметрии Varint+delta уменьшил объём примерно на 67% относительно Fixed Binary; Columnar лучше для архивного анализа, но дороже обновлять. Реальные наборы KIRA пока малы. |
| Сжатие | LZ4 или zstd-3 для быстрого чтения; zstd-19 или xz для холодных образов. Не сжимать хеши и подписи. | На образе KiraFS zstd-3 распаковывался примерно за 2,1 мс, lz4 — около 2,1 мс; xz лучше сжимает, но заметно медленнее. |
| WebAssembly | Сохраняем WASM как отдельную песочницу для переносимых приложений. | Модули уже собираются для x86/ARM64. WASI и внешняя VM уровня wasm3 в исследовании NOT RUN; не заявляем их готовыми. |
| Инструкции ИИ и человека | KIL — декларативный язык задач, политик, зависимостей, параллельного исполнения и критериев приёмки, а не новый C-подобный язык. | Общая компиляторная фронтенд-система не доказала преимущество. KIL сначала должен описывать существующий build factory и проверяемые действия; нативный код остаётся в C/Rust/KCC. |

## 2. Архитектурные решения по безопасности

1. **Capability-first:** приложение получает только полномочия из доверенного манифеста. Объявление разрешения в исходном коде или KIL не выдаёт его.
2. **Процессная изоляция:** отдельные адресные пространства, W^X, проверка пользовательских указателей и приватные IPC-объекты по умолчанию.
3. **DMA:** драйверы не должны получать произвольный доступ к памяти ядра. VT-d и ARM SMMUv3 должны стать реальными границами DMA, а не только парсерами таблиц и unit-тестами.
4. **Подлинность загрузки:** CRC32 BIOS обеспечивает обнаружение случайного повреждения, но не подлинность. Ядро и загрузочные образы пока не имеют единой обязательной криптографической цепочки доверия.
5. **Драйверы:** получать и адаптировать только исходный код с совместимой лицензией и проверяемым происхождением. Закрытые бинарники и драйверы с запрещающими лицензиями не обходить и не перепаковывать. Подпись пакета, проверка хеша и права должны оставаться обязательными.
6. **Граница утверждений:** успешная QEMU-изоляция не означает уровень Qubes/seL4; VT-d на одном QEMU-профиле не доказывает поддержку всех IOMMU; ARM64 TCG не заменяет испытания на реальной плате.

## 3. Обязательные технические блокеры

| Приоритет | Блокер | Критерий закрытия |
|---|---|---|
| P0 | KCC SysV AMD64 ABI для структур с float/double | 16/16 ABI-кейсов проходят при взаимном вызове KCC, Clang и GCC; отдельно проверяются аргументы и возвраты смешанных агрегатов. |
| P0 | KCC AArch64 object backend | `kcc -c -target aarch64` не падает; полноценные ET_REL, relocations, link и runtime parity. |
| P0 | KLINK GOTPCREL и полный linker regression | Все текущие тесты KLINK проходят; крупные приложения собираются и исполняются без LLD fallback. |
| P0 | Полный host regression | Все host tests проходят, включая PMM x86/ARM64, VMM, IOMMU models, KiraFS и IPC. |
| P0 | UEFI release gate | Собственный UEFI loader собирается из актуальных исходников и реально загружается через OVMF; ISO содержит BIOS и UEFI entry. |
| P1 | x86 VT-d end-to-end | QEMU с DMAR/VT-d проверяет реальные DMA domains, mapping, invalidation и негативные случаи на устройствах. |
| P1 | ARM64 SMMUv3 end-to-end | QEMU/плата проверяет stream tables, translation, invalidation, faults и изоляцию DMA. |
| P1 | Частные IPC-объекты | QEMU-тест подтверждает, что чужой PID не может открыть приватный port/SHM по имени, а публичный объект доступен только после явной публикации. |
| P1 | Подписанная загрузка | Единая проверка подписи ядра/образа для BIOS/UEFI/ARM64 с fail-closed и защитой от rollback. |
| P1 | KIL parser/validator | Parser, typed schema, action registry, policy validation, DAG checks и evidence verification; без произвольного shell. |
| P2 | Реальное железо ARM64 | Проверка хотя бы на одной физической плате: таймеры, GIC, PSCI, MMU, DMA и сетевой/накопительный драйвер. |

## 4. Порядок внедрения

1. Закрыть текущие регрессии и сделать полный CI зелёным.
2. Довести ABI KCC и KLINK до совместимости с эталонными компиляторами/линкерами.
3. Завершить capability-изоляцию и end-to-end DMA/IOMMU на x86-64.
4. Довести ARM64 до функционального паритета по системным вызовам, памяти, IPC, драйверам и тестовым сценариям.
5. Представить девять CI-боксов как KIL-план, сохранив все текущие проверки и release gates.
6. Только после этого расширять KIL executor и переводить на него новые системные задачи.

## 5. Что не принимаем без новых измерений

- Не заменяем ELF собственным KEX.
- Не объявляем KCC быстрее или качественнее Clang в общем случае.
- Не используем KLINK как единственный линкер до прохождения GOTPCREL и полного тестового набора.
- Не переписываем ядро на Rust ради самого языка.
- Не вводим универсальный формат данных.
- Не называем KIRA микроядром, гипервизором Qubes или формально верифицированной ОС.
- Не считаем QEMU/TCG проверкой реального ARM64-железа.
- Не выпускаем ISO/update package, пока release gate сообщает BLOCKED.
