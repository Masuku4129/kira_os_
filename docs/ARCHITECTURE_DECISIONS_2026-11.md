# KIRA OS — архитектурные решения по результатам исследования (2026-11)

Статусы доказательств: **[E]** измерено в исследовательском стенде; **[S]** подтверждено чтением исходников; **[X]** внешняя спецификация; **[H]** гипотеза. Исследование выполнено на x86-64 VM; ARM64 измерялся только в QEMU TCG. Эти решения не означают аппаратную сертификацию.

## Зафиксированные решения

| Область | Решение | Основание и ограничения |
|---|---|---|
| Общая архитектура | Гибридное ядро: минимально необходимые привилегированные механизмы в kernel, службы и драйверы — userland/Ring 3 или EL0 | Текущие границы KIRA подтверждены исходниками и QEMU; это не seL4 и не доказательство формальной изоляции [S/E] |
| Ядро | C остаётся основным языком; KCC — второй компилятор и путь самосборки; ASM только для входов/выходов и измеренных горячих участков | KCC собирает ядро, но .text в исследовании ×1.59 clang; C-код ядра уже существует. KAS совпал с NASM на 11/11 исследованных файлах [E/S] |
| Недоверенные парсеры и новые драйверные модули | Rust no_std — кандидат для выборочного внедрения, не переписывать ядро целиком | В четырёх общих нагрузках Rust близок к C; некоторые ошибки памяти отвергаются компилятором/проверками. Не проверены полная интеграция, размер runtime и реальная аппаратная работа [E/H] |
| Системные службы и приложения | C сейчас; допускается любой язык, который соблюдает проверенный KIRA C ABI | Совместимость ABI ограничена: структуры с FP-полями по значению в KCC сейчас некорректны [E/S] |
| Числовые ядра ИИ | Не использовать KCC как единственный компилятор горячих вычислительных циклов; C/C++ clang/gcc или Rust-кандидат | KCC отстаёт на матричных и FP-нагрузках; SIMD/GPU и квантизация не измерялись [E] |
| Компилятор KCC | Сохранять один typed IR и общий backend-путь; исправить ABI структур с float/double; развивать оптимизации по измеряемым нагрузкам | KCC быстро компилирует и потребляет мало памяти, но не достигает целевых показателей кода и имеет подтверждённый SysV AMD64 ABI-дефект [E] |
| Собственный язык KIRA / KIL | Отдельный фронтенд поверх KCC IR; не вводить второй backend и не исполнять естественный язык напрямую | Сам язык не реализован и не измерялся [H]. До реализации закрыть KCC ABI, тесты типов и целевых IR-проходов |
| Исполняемые форматы | Сохранить ELF для пользовательских программ, PE/COFF для UEFI, стандартный ARM64 Image; не вводить KEX в production | KEX дал около −9.5% несжатого размера, но преимущество почти исчезает после сжатия и не улучшает безопасность/скорость. ELF остаётся [E] |
| Модули приложений | Сохранять WASM как отдельный формат исполнения; не объявлять WASI поддержанным | Текущий KIRA WASM ABI собственный; WASI runtime не реализован [S/NOT RUN] |
| IPC и изоляция | Развивать раздельные адресные пространства, W^X, manifest capabilities, приватные IPC-объекты и SHM; следующий этап — безопасная передача capabilities и end-to-end атаки | Текущая изоляция — базовый уровень. Не заявлять эквивалент Qubes или seL4; VM-per-app и формальная верификация отсутствуют [S] |
| Архитектуры | x86-64 и AArch64 — равноправные цели; общие интерфейсы/ABI, раздельные входы ядра и аппаратные реализации | x86-64 функционально впереди; ARM64 требует отдельного gate для загрузки, исключений, памяти, SMP, userland, драйверов и IPC. QEMU TCG не доказывает работу на реальном ARM-железе [S/E] |
| Драйверы | KDRV Ring3: происхождение, лицензия, подпись, ограничения capability, проверка/откат; успешная компиляция не означает совместимость | Подпись и некоторые install-path тесты уже существуют; автоматическая адаптация драйвера остаётся отдельной исследовательской задачей [S/E/H] |
| Сборка | Параллельные независимые build/test boxes, каждый со своим checkout, журналом и артефактом | Цель — локализовать сбои по подсистемам; release gate остаётся общим и строгим |

## Обязательные блокеры перед расширением

1. KCC: корректная классификация SysV AMD64 aggregate arguments/returns с FP-полями; 16/16 текущих ABI-тестов и расширенный набор.
2. KLINK: поддержка/обработка R_X86_64_GOTPCREL или явное ограничение совместимого объектного профиля с проверкой на этапе link.
3. ARM64: kcc -target aarch64 -c не реализован (исследовательский тест SIGSEGV); нужны ELF ET_REL и полноценный link/load path.
4. Изоляция: проверить межпроцессные указатели, гонки закрытия/ожидания, lifecycle потоков и SHM mappings; добавить атакующие VM-сценарии.
5. IOMMU: не заявлять DMA-изоляцию на машине без DMAR/SMMU; тестировать fail-closed и реальные VT-d/SMMUv3 домены.
6. Boot trust: CRC32 BIOS не обеспечивает подлинность ядра; UEFI и GRUB должны иметь согласованную криптографическую проверку.
7. Аппаратная матрица: физические x86-64 и ARM64 платы пока не доступны; результаты QEMU помечать отдельно.

## Новые результаты проверки (10.11.2026)

- **x86-64 / KVM:** QEMU-сценарий isolation прошёл: раздельные адресные пространства, отклонение пользовательского указателя на память ядра, проверка capability-прав, отказ чужому процессу в открытии приватных IPC-порта и SHM; после отказа — 200 round trips, сценарий PASS.
- **AArch64 / QEMU TCG:** arm64-gicv3 прошёл тот же тест приватного IPC/SHM; 200 round trips, сценарий PASS. Это подтверждает одинаковую наблюдаемую семантику в этих сценариях, но не полную архитектурную эквивалентность.
- **SB16 / QEMU TCG:** DSP 4.5 обнаружен; 64-КБ DMA-кольцо размещено по 0x5D0000 и не пересекает 128-КБ границу; 224 блока подтверждены, 1 824 800 кадров забрано картой, 76 799 кадров смешано, underruns = 0. Физическая ISA-карта не тестировалась.
- **PMM ARM64 host regression:** тест, ранее требовавший конкретный повторный физический адрес 0x111000, исправлен на проверку инвариантов next-fit allocator; полный host-tests job PASS. Это исправление теста, а не изменение алгоритма выделения памяти.

## Внутренний KCC build factory (этапы C1–C3)

CI-боксы выше — параллельная проверка репозитория, а не внутренний планировщик сборки KIRA. Этап C из docs/BUILDER_PLAN.md остаётся отдельной задачей.

Аудит текущего KCC показал:

- KCtx хранится как глобальный объект K в kcc/util.c и объявлен через extern в kcc/kcc.h.
- Контекст читается напрямую в util, preprocessor, parser, IR, optimizer, ELF writer и обоих backends.
- У x86 backend есть собственное изменяемое статическое состояние (assembler, register pools, liveness/spill/fold arrays); у AArch64 backend и optimizer также есть состояние между вызовами.
- Поэтому простая замена KCtx на локальную переменную не делает компилятор reentrant и не разрешает безопасный запуск нескольких потоков в одном процессе.

Порядок реализации без ложной параллельности:

1. **C1 — KBox context:** выделить полный per-box state (arena, diagnostics/setjmp, preprocessing/parser/IR/optimizer/backend state), убрать разделяемые mutable globals; передавать контекст явно. Не использовать TLS как замену, пока TLS ABI/runtime не реализованы.
2. **C1 gate:** две одновременные компиляции разных targets в одном процессе; детерминированные object/diagnostic outputs; ThreadSanitizer без data races; независимое исчерпание/рост arena.
3. **C2 — scheduler:** DAG задач с типами builder/verifier/optimizer, приоритетами, квотами и отменой; worker slot привязан к отдельному KBox. Планировщик не выдаёт capability сверх манифеста.
4. **C3 — измерение:** сравнить последовательную сборку с 2/4/8 workers на одном дереве и одинаковом cache state; фиксировать wall time, CPU time, peak RAM, output hashes и причины отказа. Ускорение признавать только при одинаковых артефактах и повторяемом выигрыше.

До прохождения C1 gate внутренний KCC нельзя объявлять безопасным для параллельной компиляции в одном процессе. CI parallel boxes не заменяют эту работу.

## Правила принятия новых технологий

- Не заменять работающий компонент из-за моды или одного микробенчмарка.
- Для каждого кандидата: корректность → безопасность → интеграция → производительность → стоимость сопровождения.
- Сравнивать на одинаковых входных данных, с повторениями и эталоном; различия меньше шума не считать выигрышем.
- Результат TCG, host test или build-only не выдавать за физическое аппаратное подтверждение.
- Новый формат/ABI/язык допускается только при измеримом преимуществе и полном наборе миграционных/совместимых тестов.
