# KIRA AI: разделение системного Разума и пользовательского ИИ-сервиса

## Подтверждённое состояние репозитория

В текущем `autodrv` есть встроенный `mind` (`mind.c`, `mindnet.c`, `mind_sys.c`): он собирает телеметрию, учит нормы машины, управляет ограниченным набором параметров ОС и содержит одну логистическую модель из 12 признаков. Эта модель прогнозирует риск опоздания кадров на следующей секунде.

В дереве исходников нет tokenizer, transformer runtime, LLM inference engine, chat/session service, embedding index или tool broker. Следовательно, сейчас в ОС нет полноценного разговорного ИИ-помощника. Называть существующий Mind таким помощником технически неверно.

## Архитектурное решение

Развивать два связанных, но строго разделённых контура.

### 1. System Mind — интеллект управления ОС

Остаётся малым системным контроллером:
- телеметрия, статистические нормы и обнаружение аномалий;
- несколько независимых прогнозов вместо одной модели «на всё»;
- измерение качества на временных holdout-окнах и сравнение с простыми baseline;
- решения только через типизированную политику и белый список действий;
- observe/shadow по умолчанию для новых прогнозов;
- лимиты CPU/RAM, журнал, таймауты и гарантированный откат.

Никакая обучаемая модель не получает произвольный доступ к функциям ядра. Прогноз сам по себе не является разрешением на действие.

### 2. KIRA Assistant — пользовательский ИИ

Новая служба Ring 3, размещённая в изолированном App Box. Не исполнять LLM внутри ядра: это увеличивает доверенную вычислительную базу, делает сбой модели системным сбоем и смешивает вероятностное планирование с критическими механизмами ОС.

Состав службы:

1. **Inference runtime**
   - валидатор и загрузчик выбранного формата модели;
   - tokenizer и detokenizer;
   - реальное выполнение transformer-операций, KV-cache и quantized matrix kernels;
   - CPU fallback для x86-64 и ARM64; SIMD — только после проверки эквивалентности;
   - проверка размера, версии, лицензии и происхождения модели до установки.
2. **Inference scheduler**
   - отдельные квоты RAM/CPU и предел времени ответа;
   - отмена запроса, приоритет интерактивного диалога, ограничение KV-cache;
   - остановка/сброс фонового вывода при давлении памяти;
   - никакого вытеснения критических потоков ядра.
3. **Context and memory**
   - история сессий, явные границы между пользователями/приложениями;
   - поиск по локальным документам и системной справке;
   - раздельное хранение краткого контекста и долговременной памяти;
   - удаление/экспорт данных и контроль пользователя над сохранением.
4. **Tool broker**
   - типизированный реестр инструментов: файлы, настройки, приложения, сборка, драйверы, диагностика;
   - права выдаются отдельно на каждый инструмент и объект;
   - операции чтения отделены от записи; опасные действия требуют подтверждения;
   - журнал аргументов, результата и отказа; отзыв разрешения.
5. **Planner**
   - разбивка запроса на шаги;
   - вызов инструментов только через broker;
   - проверка результата по фактическому состоянию ОС;
   - повтор/откат при ошибке; запрет объявлять действие успешным без подтверждения.
6. **UI**
   - отдельное приложение «KIRA Assistant» и интерфейс в терминале;
   - потоковый ответ, отмена, отображение используемых инструментов и разрешений.

## План реализации

### A0 — зафиксировать целевую модель и тестовую базу
- Выбрать архитектуру модели и формат весов после сравнения размера, лицензии, RAM, скорости и переносимости.
- Создать независимый host reference runner для проверки математической точности и ожидаемых ответов.
- Зафиксировать набор русскоязычных задач: системная диагностика, инструкции, объяснение ошибок, работа с локальной документацией и программирование.
- Снять baseline: качество, latency, tokens/s, peak RAM, CPU time, размер пакета.

### A1 — реальный tokenizer и inference core
- Реализовать tokenizer выбранной модели и тесты encode/decode, Unicode, длинных входов и malformed input.
- Реализовать необходимые tensor kernels и transformer blocks; сравнивать промежуточные тензоры с reference runner.
- Не добавлять пустые backend-функции и «демо-ответы» вместо inference.
- Проверить одинаковую семантику x86-64/ARM64 на одинаковых входах.

### A2 — запуск в изолированной службе
- Запускать inference только в Ring 3/App Box.
- Выделить квоты памяти и процессорного времени; протестировать отказ выделения, отмену и перезапуск.
- Модель открывается как read-only артефакт; исполняемый код и веса проходят независимую проверку целостности.

### A3 — контекст и инструменты
- Добавить сессионную память и поиск по локальной документации.
- Реализовать tool broker с deny-by-default, аудитом и отзывом прав.
- Сначала read-only инструменты; запись/сборка/установка драйверов — отдельные права и подтверждения.

### A4 — пользовательский интерфейс
- Чат с потоковой генерацией, историей, отменой, настройкой памяти и отображением вызовов инструментов.
- Нагрузочные тесты одновременно с GUI, компилятором, диском и обычными приложениями.

### A5 — системная интеграция
- Mind может сообщать Assistant о доступном бюджете ресурсов, но не передаёт ему привилегии ядра.
- Assistant может запрашивать диагностику через broker, а не читать внутренние структуры ядра.
- Службы сборки и драйверов предоставляют ограниченные API, а не произвольный shell/root-доступ.

## Критерии готовности

- Реальные токены и реальные вычисления модели; нет заглушек, фиксированных ответов и имитации inference.
- Точность вычислений сравнена с reference runner на фиксированных тестовых входах.
- Русскоязычный benchmark публикует результаты и baseline; качество не оценивается только субъективно.
- Память и CPU ограничены и измерены; система остаётся отзывчивой при нехватке ресурсов.
- По умолчанию у службы нет привилегий ядра, доступа к сети и записи в системные каталоги.
- Каждый tool call проверяет capability; запрещённые операции действительно отклоняются.
- x86-64 и ARM64 проходят одинаковые функциональные тесты.
- Установка модели проверяет лицензию, формат, размер и целостность; неизвестный формат отклоняется.

## Первые независимые задачи

1. Завершить текущую надёжность System Mind: качество прогноза, полнота, калибровка, дрейф и безопасная политика.
2. Провести измеримое сравнение inference-архитектур и выбрать минимальный реальный model target под доступные RAM/CPU.
3. Реализовать tokenizer выбранной архитектуры как первую проверяемую часть пользовательского ИИ.
4. Параллельно продолжать оптимизацию планировщика, памяти, IPC и изоляции, чтобы inference не стал новым системным узким местом.


## Предварительный модельный кандидат для первого стенда (не финальный выбор)

Для первого реального inference PoC выбран кандидат **Qwen3-0.6B**, а не более сложный гибридный Qwen3.5-0.8B:

- официальная карточка указывает Apache-2.0 и поддержку более 100 языков; русский входит в мультиязычную область, но качество на наших задачах ещё предстоит измерить;
- архитектура — плотная causal transformer: 28 слоёв, 16 Q heads / 8 KV heads (GQA), контекст 32 768;
- опубликованный GGUF Q4_0 от ggml-org — около 429 MB; Q8_0 — около 805 MB;
- llama.cpp уже публикует GGUF-конверсию и поддержку этого семейства; его CPU backend имеет оптимизации x86 AVX и ARM NEON.

Почему это только кандидат:
- 429 MB — только файл весов, не полный runtime footprint: KV-cache, рабочие тензоры, tokenizer и контекст требуют дополнительной памяти;
- заявленная поддержка языков не заменяет собственный русский benchmark;
- перед включением в KIRA надо проверить точную лицензию выбранного checkpoint и quantization artifact, воспроизводимость SHA-256, память и скорость на x86-64/ARM64;
- llama.cpp используется как независимый reference runner/сравнение, а не автоматически встраивается в ядро или принимается как готовая реализация KIRA.

Qwen3.5-0.8B пока не выбран для первого ядра: его модельная карточка описывает гибрид Gated DeltaNet + attention, что добавляет отдельный класс операторов и увеличивает объём первого этапа. К нему можно вернуться после работающего базового transformer runtime.

Источники для повторной проверки:

- ggml-org Q4_0 GGUF artifact: https://huggingface.co/ggml-org/Qwen3-0.6B-GGUF
- GGUF specification: https://github.com/ggml-org/ggml/blob/master/docs/gguf.md
- llama.cpp CPU backends and supported architectures: https://github.com/ggml-org/llama.cpp
