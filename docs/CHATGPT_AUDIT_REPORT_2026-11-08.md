## 2. Реестр находок и необходимые действия

### AUD-KCC-01 — P1: усечение 64-битного коэффициента в strength reduction

**Файл:** `kcc/opt.c`  
**Проверенные места:** около строк 442, 471, 484; blob SHA `4b9e69ef0dcef98ad91404ae9b59c8b4b74bab78`.

В `op_sr` коэффициенты исходно имеют тип `int64_t`, но таблица накопителей объявлена как `int tc[12]`. При поиске и сохранении коэффициент сужается к `int`. Разные 64-битные коэффициенты с одинаковыми младшими 32 битами могут быть ошибочно объединены. Тогда умножение одной индукционной переменной на второй коэффициент заменяется накопителем первого коэффициента — оптимизация меняет результат программы.

**Предлагаемая регрессия:**

```c
int main(void) {
    long sum = 0;
    for (long i = 1; i <= 3; ++i) {
        long a = i * 4294967297L;
        long b = i * 8589934593L;
        sum += a + b;
    }
    return (int)((sum >> 32) & 255);
}
```

Для корректной арифметики ожидается код возврата 18; при описанной ошибочной подмене — 12. Это ожидаемый результат анализа, а не результат фактического запуска.

**Исправление и приёмка:**
1. Хранить коэффициенты без сужения, например в `int64_t tc[12]`, и сравнивать в полном разряде.
2. Добавить regression case в KCC suite.
3. Сравнить обычный режим, `-fno-sr` и эталонный clang/gcc.
4. Прогнать весь KCC suite, selfhost и object tests; приложить команды, exit codes, CI run URL.

### AUD-BIOS-01 — P1: ELF entry не связан с реально загруженным исполняемым PT_LOAD

**Файл:** `arch/x86_64/bios/stage2.asm`  
**Проверенные места:** около строк 440, 506–511; blob SHA `5a3d6c18bb9a6f49d1dcc0b33ff869ecd636546f`.

`n_load` обнуляется, но в просмотренном цикле PT_LOAD не обнаружено его увеличения и последующей проверки, что найден хотя бы один сегмент. Проверка `e_entry` ограничивается общим диапазоном 1–16 МиБ; принадлежность entry реально загруженному PT_LOAD с флагом PF_X не проверяется. Также не подтверждена проверка старшей половины `e_entry`.

Это позволяет некорректному ELF — например, без PT_LOAD или с entry вне исполняемого сегмента — пройти показанную часть валидации и передать управление по незагруженному/неподходящему адресу.

**Проверки, которых не хватает:**
1. Отклонять ELF без PT_LOAD.
2. Проверять полный 64-битный `e_entry` и его попадание внутрь реально загруженного исполняемого PT_LOAD.
3. Проверять переполнения и согласованность `p_vaddr`/`p_paddr` с фактической схемой копирования.
4. Добавить malformed ELF cases: ноль PT_LOAD, entry вне сегмента, entry в неисполняемом сегменте, переполнение адресного диапазона.
5. Подключить отдельный SeaBIOS/QEMU BIOS boot job в CI. Наличие UEFI/OVMF job не является тестом BIOS.

Файл `tests/bios_boot_test.sh` существует, но рассмотренный `tests/run_host_tests.sh` и CI workflow не запускали этот BIOS test.

### AUD-KDRV-01 — P1: продвижение anti-rollback floor не атомарно

**Файл:** `drivers/kdrv/kdrv_trust.c`, API в KDRV trust header.

Операция чтения текущего floor, сравнения и записи нового значения разделена на отдельные вызовы. Без сериализации два параллельных вызова могут прочитать одно старое значение, а затем записать новые значения в обратном порядке. В результате успешное продвижение до более высокой версии может быть перезаписано меньшей.

**Исправление и приёмка:**
1. Ввести атомарный compare-and-max либо явный lock/transaction contract в trust storage API.
2. Определить поведение при ошибке записи и при конкурентном обновлении.
3. Добавить тест с детерминированным interleaving двух продвижений, например 4→7 и 4→6; итог не должен стать 6 после успешного продвижения до 7.
4. Документировать ограничение модели угроз: floor в обычной файловой системе сам по себе не защищает от отката всего диска без аппаратного/внешнего trust anchor.

### AUD-KDRV-02 — P1/P2: неполная транзакционность операций менеджера драйверов

**Файл:** `drivers/kdrv/kdrv_manager.c`.

Статический анализ выявил несколько опасных окон ошибок:
- `stage_payload` может частично создать временные данные и вернуть ошибку до того, как вызывающий код пометит пакет как staged; cleanup тогда может не выполниться.
- После commit флаг staged сбрасывается до записи состояния INSTALLED; если запись состояния падает, данные уже зафиксированы, но функция сообщает ошибку.
- Activate/remove могут изменить runtime-состояние, после чего запись persistent state может завершиться ошибкой и оставить runtime и disk state несогласованными.

Production callback adapter и конкретное наличие orphan files не подтверждены; это риски control flow, требующие тестов.

**Исправление и приёмка:**
1. Сделать staging cleanup обязательным при любом частичном отказе.
2. Определить явные точки commit/rollback и восстановление после ошибки записи состояния.
3. Добавить failure injection на каждом шаге stage/commit/activate/remove.
4. Включить `kdrv_manager.c` в host tests; текущая проверенная конфигурация host suite не подтверждала полноценное тестирование manager.

### AUD-IOMMU-01 — P1: VT-d write-only mapping получает read permission

**Файл:** `drivers/iommu/vtd_domain.c`; API: `drivers/iommu/vtd_domain.h`; тест: `tests/vtd_domain_test.c`.

В leaf flags безусловно добавляется `VTD_ENTRY_PRESENT`, который в текущем коде совпадает с `VTD_ENTRY_READ` (бит 0). Поэтому запрос `KIRA_VTD_MAP_WRITE` формирует leaf с R=1 и W=1. Для VT-d second-level PTE валидность задаётся наличием R и/или W; отдельного Present-бита в этом формате нет.

**Воздействие:** устройство получает DMA-read, хотя вызывающий код просил только DMA-write.

**Исправление и приёмка:**
1. В leaf записывать только запрошенные R/W permissions.
2. Проверять валидность leaf по маске READ|WRITE.
3. Не переносить эту семантику механически на intermediate entries — их правила отдельно сверить со спецификацией.
4. Добавить тесты READ-only, WRITE-only и READ|WRITE с точными проверками битов. Текущая модель не покрывала write-only.

### AUD-DRVCOMPAT-01 — P2: чтение за границами короткой URI-строки

**Файл:** `userland/drvcompat.c`, функция `uri_https_safe`, около строк 24–30.

После проверки `str_ok(s, 1024)` код сравнивает `s[0]`…`s[7]` с префиксом `https://`, не проверив длину строки. Для короткого корректно завершённого массива, например `char uri[] = "h";`, обращения к поздним индексам выходят за границы объекта — undefined behavior.

**Исправление и приёмка:**
1. Сначала безопасно определить длину строки.
2. Отклонять длину меньше 8 до проверки префикса.
3. Добавить случаи длины 1–7 и запускать их под ASan/UBSan.

### AUD-MIND-01 — P1: параллельные сохранения могут повредить архив снимков

**Файл:** `mind_sys.c`; ключевые места около строк 393–396, 448–515, 526–567, 681–687.

`mind_sys_save()` копирует модель под `mmx`, отпускает mutex, затем пишет основную модель и вызывает `archive_write()`. Системный tick и пользовательская команда save могут вызвать сохранение параллельно. `archive_write()` использует общие изменяемые статические данные `archive_items`, `archive_count`, `archive_generation` и общий static record. Отдельная блокировка всей операции сохранения не обнаружена.

Возможные последствия: одинаковые generation/имена файлов, гонка на общем record buffer, перезапись результатов archive scan и ошибочное удаление снимков при quota eviction. Это вывод из совместного использования mutable state; фактическое повреждение файловой системы в runtime не воспроизводилось.

**Исправление и приёмка:**
1. Сериализовать полную операцию save — primary write, archive scan/write и eviction — отдельным save mutex/lock.
2. Не удерживать `mmx` во время дисковых операций.
3. Добавить concurrency и failure-injection тесты с параллельными снимками.
4. Доказать отсутствие дублирующихся generation, повреждённых записей и удаления последнего корректного recovery snapshot.

**Вывод:** по просмотренным участкам подтверждённого дефекта не найдено; это не означает, что весь UEFI boot path принят.

## 4. ARM SMMU и границы аппаратной готовности

В `drivers/iommu/arm_smmu_domain.c` сохраняются StreamID и таблицы при неуспешной invalidation, что предотвращает преждевременное освобождение ресурсов при неопределённом состоянии оборудования. Но неполный Context Descriptor остаётся известным разрывом. Наличие host-side модели не доказывает полноценную ARM SMMU аппаратную трансляцию или DMA-изоляцию.

**Требуется:** закончить Context Descriptor и register/queue programming по применимой версии спецификации, добавить аппаратно-ориентированные тесты и чётко маркировать unsupported paths как недоступные, а не как успешно изолированные.

## 5. Обязательный формат ответа Claude

Для каждого AUD-ID вернуть:

1. **Статус:** подтверждено / исправлено / опровергнуто / частично / отложено.
2. Актуальный путь и номера строк после изменений.
3. SHA коммита с исправлением.
4. Добавленный regression test и точную команду запуска.
5. Результат: exit code и краткий вывод.
6. Ссылку на конкретный CI run/job/log.
7. Отдельно — что проверено только в QEMU/OVMF, что на host model, а что действительно на физическом оборудовании.

Не считать задачу закрытой только по изменению исходника. Закрытие требует регрессионного теста и подтверждённого результата CI. Не называть host model доказательством аппаратной изоляции.
