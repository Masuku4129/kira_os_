## Этап 1 - сделано
- Композитор на всех ядрах: изменённые места - плитки 64x64, полосы собираются помощниками `kpar` и сразу
  выводятся на экран (было: одна охватывающая рамка, один поток). Вызывающий ждёт помощников сном, а не вращением.
- Темп кадров программ по экрану: present ждёт, пока прошлый кадр заберут; копия кадра - без выключения прерываний.
- Допуск запусков (бюджет Разума): одинаковых и всего в секунду - по ядрам и здоровью системы.
- Тактический Разум (~40 Гц, поток `mind-tact`): при опоздании кадров или ожидании переднего плана фон ужимается до
  предела загрузки ядер (по умолчанию 50%, `ai cap N`), после 400 мс спокойствия пределы плавно снимаются.
- Очереди готовых потоков у каждого ядра: выбор потока не обходит всю таблицу; поток ставится на ядро, где пойдёт
  сразу (прежнее - первым), более важный на чужом ядре вытесняет межъядерным прерыванием; простаивающее ядро
  и ядро в конце кванта забирают дольше всех ждущий поток с других ядер (доли равны, проверено на 2-256 ядрах).
- Тик без общих замков: время - сравнением-обменом, планировщик берёт замок только когда есть что решать.
- Сторож: остановка всей машины (хозяин приостановил ВМ) не считается зависанием, но пишется с местом, где ядро
  застал первый тик (если это был код с выключенными прерываниями - видно, какой).
- Аварийный дамп: где стоит каждое ядро (NMI), цепочка вызовов (ядро собрано с указателями кадров), состояние
  замков; символы ядра публикуются стендом (`latest/vm-symbols/kira.sym`).

- Последовательный порт без ожидания (кольцо 64 КБ, FIFO): раньше медленный порт держал ядро с выключенными
  прерываниями до 0,8 с (нашёл сторож по месту остановки).

## Этап 2 (трёхуровневый Разум) - сделано
- Стратегия: модель предвидения `mindnet` - логистическая регрессия на 12 признаках (загрузка, очередь, память,
  фон, фокус, обмен, диск, переключения, число программ, опоздания, ожидание, анимация), учится каждую секунду на
  исходе следующей секунды, веса хранятся на диске (`/var/mind.dat` v2, опыт v1 поднимается). Доверие - только
  когда её предупреждения сбываются (точность >= 50%); тогда тактика ужимает фон заранее, до опоздания.
  Секунды с упреждением модель не учат (исход нечестный), каждая десятая опасная секунда - проверочная.
  `ai` - риск и качество, `ai model` - веса. Проверка на хосте: находит действующие признаки (6,6 и 4,8 при
  истинных 7 и 5), калибровка p(опасно) 0,989 при истинной 0,993.
- Тактика ~40 Гц и предел загрузки ядер - этап 1.
- Рефлекс в планировщике: вес потока - политика Разума (фокус 6, голодающий 8, обычный 4); проснувшийся более
  тяжёлый поток вытесняет более лёгкий того же класса сразу (на своём ядре - флагом, на чужом - межъядерным
  прерыванием), вытесненный идёт следующим с остатком кванта.

  Разум включает темп фоновых окон, композитор переходит на одно ядро, 60 кадров/с, отклик консоли в норме.

## Этап 3 (arch/ и ARM64) - начато
- `arch/x86_64/`: код, зависящий от процессора, отделён (вход в ядро, прерывания, GDT/IDT, APIC, ядра, FPU,
  системные вызовы, исключения, компоновка). Общие части - в корне.
- `fdt.c`: разбор дерева устройств (общий, проверен на хосте, в том числе испорченные блобы).
- `arch/aarch64/` (`./build_arm64.sh` -> `kira-arm64.img`): образ ARM64 с заголовком загрузки (QEMU -kernel,
  U-Boot booti), позиционно-независимый (сам применяет перемещения), вход с EL3/EL2/EL1, вектора исключений с
  дампом, MMU с тождественной картой по узлам памяти из дерева, GICv2 и GICv3, общий таймер, остальные ядра через
  PSCI (hvc или smc - как сказано в дереве). Стенд: 4 машины QEMU virt - GICv3/4 ядра/EL1, GICv2/2 ядра/Cortex-A53,
  EL2/8 ядер/3 ГБ, ошибка доступа -> дамп. Адресов железа в коде нет.
- ARM64, этап 2: на ARM64 работает то же общее ядро, что и на x86-64 (`sched.c`, `heap.c`, `kmutex.c`, `percpu.c`,
  `scale.c`): менеджер страниц по узлам памяти из дерева, куча, планировщик с очередями ядер, переключение
  контекста с SIMD/FP, стеки потоков с пустотой ниже (окно 4 КБ-страниц), межъядерные SGI (GICv2 и GICv3),
  выключение тика простаивающих ядер. Команда `test`: потоки на каждом ядре, спин-замок (100000 из 100000),
  вытеснение по кванту, мьютекс ядра со сном (8000 из 8000), точность сна (ошибка 2 мс) - PASS на всех машинах.
  Планировщик и данные ядра больше не содержат x86-кода (заголовки архитектуры: cpu.h, arch_percpu.h, arch_sched.h).
- ARM64, этап 3: PCI Express (ECAM, назначение BAR по окнам из дерева), те же драйверы virtio-blk/NVMe/AHCI,
  KiraFS, опыт, журнал, Разум со всеми уровнями, сторож; консоль с командами файлов и ai.
- ARM64, этап 4: программы в EL0 - пространство процесса (L0 со ссылками на таблицы ядра, ASID, nG), вызовы SVC
  через общий syscall.c, копирование только LDTR/STTR, PAN (если есть), рост стека, сбой программы завершает только
  её, синхронизация кэша команд. Программы mt, ipc, burn собраны для ARM64 из тех же исходников (kira.h для обеих
  архитектур). Стенд: mt - 80000 из 80000 за 20 мс, PASS; ipc - 200 обменов, разделяемая память - PASS.
- Дальше на ARM64: экран (ramfb/virtio-gpu) и окна программ, USB xHCI, общая консоль, враждебные программы.

## Найдено стендом и исправлено (31.10)
- ACPI при 2+ ГБ ОЗУ: таблицы у верхней границы памяти не читались -> система работала на 1 ядре из 8.
- AHCI: порядок запуска порта (FRE до ожидания BSY) - на q35 порт навсегда «занят», загрузка вставала.

  программа (plasma, burn, fpu) погибала на ПК с AMD; до исправления входа с GS это было рекурсией исключений
  и переполнением стека ядра (двойная ошибка, которую поймала защитная пустота стека).
- Вход в ядро: GS проверяется по GS_BASE для любого прерванного кода ядра; RFLAGS.AC сбрасывается (обход SMAP).
- Допуск запусков работает: из 20 запусков plasma за секунду 12 не допущены, система отвечает за 0,04 с.

## Диски на прерываниях и рычаг «ядро фокуса» (31.10)

## Пакет G: DMA на платах без согласованности кэша (01.11)
- ARM64: если в дереве устройств нет `dma-coherent` (корень или узел хоста PCI), буферы устройств (virtio, USB xHCI) берутся из пула без кэша (до 32 МБ, верх ОЗУ ядра, блоки 2 МБ, MAIR 3 = 0x44). Параметр загрузки `kira.dma=noncoherent|coherent` переопределяет решение.
- ПРОВЕРЕНО стендом: arm64-dma-nc (virtio-gpu, input, blk, net, HDA, xHCI поверх пула; все прочие сценарии зелёные, 38 из 38). НЕ проверено: настоящая некогерентная плата (QEMU всегда когерентен); атомарные операции в памяти без кэша на кремнии.

## Пакет D: TLS (01.11)
- Ed25519 (RFC 8032) в `pk.c`; X.509: подписи и ключи Ed25519 (RFC 8410), RSA-PSS (параметры хэша, MGF1, соли) в подписи и ключ id-RSASSA-PSS с ограничениями; схемы CertificateVerify 0x0807, 0x0809-0x080b.
- AES-128 без таблиц: S-блок считается (x^254 в GF(2^8) + аффинное преобразование) в битовой нарезке, без индексов и ветвей по секрету. Цена: ~2,3 МиБ/с против ~9,6 на хосте (GHASH - тоже побитовый). SHA-1 добавлен только для CertID в OCSP.
- OCSP stapling: `status_request`, ответ из записи листа; `x509_ocsp` проверяет подпись издателя или уполномоченного ответчика (EKU OCSPSigning), CertID, срок. `tls_t`: `ocsp_stapled`, `ocsp`, `ocsp_why`. Нет ответа - не ошибка; revoked, подделка, чужой сертификат - отказ; устарел/unknown/ошибка ответчика - ocsp=0 с причиной.
- Сессии: NewSessionTicket -> PSK (`resumption_master_secret`), `psk_dhe_ke`, binder; билет `tls_ticket_t` в `tls_t.ticket`, `tls_connect(..., const tls_ticket_t*)`; билет только для того же имени и до конца срока; отказ сервера - полное рукопожатие. `fetch -r` повторяет запрос по билету.
- Проверено на хосте (`tests/run_host_tests.sh`): векторы RFC 8032 и сверка 240 подписей Ed25519 / 360 RSA-PSS с python cryptography; AES против прежней табличной версии на 2000 случайных ключах; цепочки Ed25519 и RSA-PSS, ответы OCSP (good, уполномоченный, revoked, unknown, stale, forged, other) и резюмирование - против Python ssl и `openssl s_server`.
