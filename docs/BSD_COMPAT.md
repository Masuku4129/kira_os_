# Слой совместимости BSD («автодрайверы»): основание

Цель: Кира сама находит драйвер устройства в открытых BSD-деревьях, скачивает его, собирает KCC на устройстве и запускает как драйвер Ring 3,
без рецептов под конкретное устройство. Пробный запуск и откат — до постоянной установки; постоянная установка — только после подтверждения человека
(защиты DMA для большинства устройств пока нет, подписей у чужих исходников нет).

## Что нужно драйверу BSD
Стандартный драйвер OpenBSD (`sys/dev/pci/if_*.c`, `sys/dev/ic/*.c`) ждёт ядро OpenBSD: `sys/param.h`, `sys/systm.h`, `sys/device.h` (autoconf, softc),
`sys/mbuf.h` (цепочки пакетов), `net/if.h` (ifnet, ifq), `net/if_media.h` (ifmedia), `dev/mii/*` (PHY), `machine/bus.h` (bus_space, bus_dma),
`dev/pci/*` (pci_mapreg_map, pci_intr_*), `sys/timeout.h`, `sys/malloc.h`. Измерение на `ne2k` (QEMU ne2k_pci): около 50 разных вызовов на ~2100 строк.

## Устройство слоя (дорожка B)
- `kcc/include/bsd/...` — заголовки с именами BSD (`<sys/param.h>`, `<net/if.h>`, `<machine/bus.h>` ...). Это НАШ код, BSD-лицензия, чужого кода в нём нет.
- `userland/bsd_rt.c` — рантайм в процессе драйвера: mbuf, ifnet/ifq поверх колец netdev (`kdrv_bsd.h`), timeout, autoconf-обвязка (`struct device`, softc),
  ifmedia, bus_space (порты и память), основной цикл (прерывание/опрос → `*_intr`, таймеры, передача `if_start`).
- `tools/bsd_pcidevs.py` (позже `drvget`) — `pcidevs.h` ТОЛЬКО из тех PCI_VENDOR_*/PCI_PRODUCT_*, что упомянуты в исходниках драйвера, значения из `pcidevs` дерева.
- Поиск драйвера по ID (vendor:device): `pcidevs` → символ `PCI_PRODUCT_*` → драйвер, где символ упомянут в таблице устройств.
- Лицензия и подозрительные файлы проверяются как у `drvget` (BSD/MIT/ISC; без GPL и бинарников).

## Корпус и счётчик совместимости
`drivers/bsdcorpus/manifest.txt` закрепляет коммит OpenBSD и SHA-256 каждого файла; `tools/bsd_corpus.py fetch` скачивает в `build-bsd/corpus` (в репозиторий чужой код не кладём).
`tests/bsd/meter.sh` собирает каждый набор слоем и пишет «собирается / не собирается» с первой ошибкой. Порядок наборов — по возможности проверки в QEMU:
1. `ne2k` (ne2k_pci: порты, без DMA, без PHY-цепочки) — основание слоя: mbuf, ifnet, bus_space, timeout, autoconf.
2. `pcn` (AMD PCnet: DMA, кольца) — bus_dma.
3. `fxp` (Intel 82557/8/9: MII, DMA) — MII/ifmedia.
4. `dc` / `tulip`, затем остальные из pcidevs.

## Что остаётся честным ограничением
Прерывания: INTx и MSI доступны драйверам Ring 3 с правом `irq` (INTx - через IOAPIC, общие линии, маскирование самого устройства битом INTX_OFF), без права - опрос раз в 10 мс.
DMA: драйвер видит только блоки `kdrv_dma_alloc` (при VT-d - свой домен). bus_dma в слое - копирование через промежуточные блоки, кластеры mbuf берутся из
памяти DMA (копий нет); DMA когерентный, на ARM64 слой DMA пока не годится. Один сетевой адаптер на стек. Общий PHY IEEE 802.3 вместо отдельных phy-драйверов OpenBSD.
Хранилища firmware нет (`loadfirmware` даёт ENOENT): драйверы, которым микрокод необязателен, работают без него.

## Состояние (ne2k)

Работает на QEMU `-device ne2k_pci` без правок исходников OpenBSD: `if_ne_pci.c + ne2000.c + dp8390.c + rtl80x9.c` из закреплённого корпуса,
`tools/bsd_build.sh` собирает ELF, пакет `bsdne` (права MMIO, PCIDEV, NETDEV) запускается менеджером драйверов, ядро получает карту,
DHCP и ping идут через неё (сценарий `drv-bsd-ne2k`). Порты - системный вызов `KDRV_SYS_IO` (сценарий `drv-io`).
`tests/bsd/meter.sh` - счётчик: сколько файлов корпуса компилируется через слой.
Уроки счётчика: без `BYTE_ORDER/LITTLE_ENDIAN` в слое `#if BYTE_ORDER == BIG_ENDIAN` молча истинно - драйвер переставлял байты.
Не сделано: сборка этого драйвера компилятором KCC (пока clang), автоматический поиск по ID в drvget (есть `tools/bsd_pcidevs.py find/ids`),
набор dc; таблица групповых адресов ядра не передаётся (принимаются все).

## DMA и прерывания (pcn, fxp)

- `pcn` (AMD PCnet, QEMU `-device pcnet`): работает на q35 с VT-d (`-device intel-iommu,aw-bits=48`) и с прерываниями INTx; сценарий `drv-bsd-pcn`
  проверяет собственный домен VT-d для карты, DHCP, ping, счётчик `irq` > 0 без шторма. Исключение слоя: QEMU отдаёт APROM (MAC) в 32-битном режиме только
  двойными словами, поэтому байтовое чтение APROM у 1022:2000 выполняется как dword.
- `fxp` (Intel 82559, `-device i82559er`): DHCP и ping работают с прерываниями INTx (сценарий `drv-bsd-fxp`). Зависание приёма было ошибкой ядра: уровневая линия гасилась после первого срабатывания без владельца; теперь - только при шторме (2000 подряд).
- `dc` (DEC 21143, `-device tulip`): работает на q35 с VT-d и INTx (сценарий `drv-bsd-dc`): DHCP, ping. Причина прежнего «не идёт»: настоящий 21143 сам опрашивает кольца
  дескрипторов (автоопрос TAP в CSR0, драйвер на него и рассчитывает), а модель tulip в QEMU опрашивает только по записи в CSR1/CSR2. Оболочка для семейства
  DEC 21143 (1011:0019/0009/0014/0002) подаёт запрос опроса передачи, пока в кольце есть ожидающие кадры, и приёма после каждого прерывания (на живом чипе это
  безвредно; запрос при пустом кольце не подавать - получится прерывание «нет буфера» и цикл). Сообщение «failed to force tx to idle state» остаётся: QEMU не
  выставляет бит «передатчик остановлен», на работу это не влияет.
- Автоустановка драйвера с DMA (сценарий `drvget-bsd-fxp`, пройден): fxp скачивается по TLS, собирается встроенным kcc на устройстве, ставится после
  подтверждения хешем и работает на q35 под VT-d. Для этого в kcc добавлен `offsetof(T, a[i])` с неконстантным индексом (расширение GNU, тест
  `tests/kcc/run/offsetof_dyn.c`). `pcn` через drvget не ставится: в `if_pcn.c` рекламная оговорка (BSD с 4 пунктами), сканер лицензий её отклоняет -
  это действующая политика, менять её - решение владельца проекта.
- Ограничение формата: пакет драйвера (`kdrv_header_t`) вмещает 8 идентификаторов PCI (`KDRV_MATCH_MAX`). Формат не менялся (подписанные пакеты остаются годными):
  у fxp 47 идентификаторов, и `tools/bsd_recipe.py` делит рецепт на части по 8 (fxp, fxp2 ... fxp6, проверенный 8086:1209 в первой). Каталог содержит все 47 строк,
  каждая указывает на свою часть; собирается и ставится только часть с найденной картой. Проверено на сборке рецептов (47 строк, 6 частей); сценарий QEMU
  проходит только первую часть (8086:1209), остальные карты в QEMU не эмулируются.
- Уроки: ревизия PCI берётся из настоящего регистра класса (иначе fxp принимает карту за i82557); буфер, в который устройство и драйвер пишут одновременно
  (дескриптор приёма внутри кластера fxp), нельзя копировать через промежуточный блок - поэтому кластеры лежат в памяти DMA; счётчик совместимости считает
  неявное объявление функции ошибкой.

## Автоустановка по идентификатору (сценарий drvget-bsd, пройден)

Цепочка на устройстве: рецепт и файлы OpenBSD по TLS -> SHA-256 каждого файла и сверка лицензий -> сборка встроенным kcc одним модулем
(`#pragma kcc unity`, файл `kdmain.c` подключает файлы драйвера и `bsd_rt.c`) -> установка в /drv после подтверждения хешем -> при загрузке
драйвер находит карту по PCI-ID, даёт ядру DHCP и ping. Рецепты создаёт `tools/bsd_recipe.py` из индекса `drivers/bsdcorpus/index.txt`
(`tools/bsd_index.py`: 60 PCI-сетевых драйверов OpenBSD, ID -> файлы). Индекс и рецепты - из CI, не с устройства: у raw.githubusercontent.com нет
списка каталогов. `tools/bsd_meter.py` показывает счёт по файлам (clang -fsyntax-only): на 2026-11-15 целиком компилируется 11 из 60 драйверов индекса
(остальным нужны `if_rxring`, `kstat.h`, `sys/pool.h`, `net80211` и др.); это счёт без проверки компоновки и без запрета неявных объявлений. Лицензии: сканер drvget принимает BSD/MIT/ISC и, отдельным решением, точный текст лицензии
Гринмана (dp8390, ne2000); отменить - убрать блок в `dg_scan_source`.

## Аудит каталога драйверов (2026-11-15)

В `drivers/index.txt` один драйвер (`rl`, собственный). Причина - не нехватка кода, а три независимых запрета; ни один из них не ослаблялся.
Корпус - коммит из `manifest.txt`, все цифры получены на нём (`tools/bsd_recipe.py`, сканер `dg_scan_source`, kcc, clang+lld).

1. Лицензия (`classify_license` в `tools/bsd_recipe.py`; закрывается при любом сомнении). Из 60 драйверов индекса разрешены 21: age, alc, ale, cas, epic_pci,
   gem_pci, hme_pci, iavf, ice, ix, ixgb, ixl, ixv, jme, lii, mtd_pci, oce, sf_pci, stge, txp, vte. Отклонены:
   - BSD с рекламной оговоркой (4 пункта, семейство Билла Пола): bge, ep_pci, lge, msk, nge, pcn, se, sis, sk, ste, ti_pci, tl, vge, vr, wb, xge, а также
     dc, rl, xl и de (их нет в индексе, см. ниже). Поэтому классические rl/sis/vr/xl/tl/dc **не могут** войти в каталог.
   - текст лицензии не распознан: bnxt, dwqe_pci, em, mcx, myx, nep, nfe, ngbe, nxe, pgt_pci, re_pci, rge, tht, vic, vmx, wi_pci;
   - неполный текст BSD-3: aq_pci, bce, bnx, et; в одном рецепте несколько лицензий (формат допускает одну): fxp_pci (BSD-2 + BSD-3 в rcvbundl.h), igc, ne_pci
     (там же лицензия Гринмана; сам текст `dp8390.c` разбит на строки с « * » и строгая проверка Python его не узнаёт, хотя C-сканер drvget узнаёт).
   Проверено: если убрать украшения комментариев перед проверкой, разрешённый набор НЕ меняется (ни один запрещённый драйвер не открывается), так что
   это не скрытая ошибка, мешающая каталогу. Практический вывод: уже проверенные в QEMU ne2k, pcn, fxp сегодня рецепт получить не могут.
2. Проверка DMA (`DMA_OK` в `tools/bsd_recipe.py`): рецепт с bus_dma выпускается только для драйверов, прошедших сценарий `drv-bsd-*` в QEMU. Почти все карты используют bus_dma.
   Слой собран для sf, vte, lii, mtd (ниже), но для этих чипов нет модели в QEMU, а железа нет, поэтому в `DMA_OK` они не внесены и в каталог не попали.
   Когда драйвер проверен на железе: добавить имя в `DMA_OK`, выполнить `python3 tools/bsd_recipe.py SYS INDEX PCIDEVS ИМЯ КОММИТ ВЫХОД`, положить
   выход в репозиторий, дописать строки в `drivers/index.txt` с URL на коммит, где лежат файлы рецепта (SHA-256 строки каталога - хеш `drvget.rec`).
3. Ёмкость каталога на устройстве (`userland/drvget_core.h`): `DG_INDEX_MAX` 4096 байт и `DG_INDEX_ENTRIES` 32 строки; строка с URL около 230 знаков, то есть
   реально помещается около 17 строк (одна строка на PCI-идентификатор). Каталог fxp из 47 строк (см. выше) в него не поместится: нужно поднять лимиты или группировать.

Сборка слоем (строго: единая единица встроенным kcc + clang+lld + запрет неявных объявлений; на устройстве/в QEMU НЕ запускались):
- собираются: sf_pci (Starfire, 9004:6915), vte (RDC R6040, 17f3:6040, Vortex86), lii (Atheros L2, 1969:2048), mtd_pci (Myson, 1516:0800/0803/0891) - все 10/100, лицензия BSD-2-Clause;
  наборы внесены в `manifest.txt`, их проверяет `tests/bsd/meter.sh`. Для них слой дополнен: `vlan.h`, `sys/sockio.h`, `sys/atomic.h`, `pci_mapreg_type`, `pci_get_capability`,
  `pci_vpd_read` (MAC lii читается из VPD), `pci_intr_map_msi` (честно «нет»: линию выбирает ядро), `m_copydata`, флаги ifmedia/IFCAP/контрольных сумм, `pa_flags`.
- собираются, но использовать нельзя: age, jme (гигабитные; общий PHY слоя не знает 1000BASE-T: регистры 0x09/0x0a/0x0f, скорость MAC и режим PHY могут разойтись).
- не собираются: stge (нужен `mii_bitbang`, гигабит), alc/ale (гигабит, PCIe-регистры, `net/if_llc.h`), epic_pci (внутренности MII: экземпляры PHY), cas/gem_pci/hme_pci
  (`if_rxring`, оборудование Sun), ix/ixgb/ixl/ice/iavf/ixv/oce (10G: `kstat.h`, `sys/pool.h`, `sys/rwlock.h`, `sys/proc.h`, `netinet/ip.h`), txp (нужен микрокод, `loadfirmware` даёт ENOENT).
- индекс `tools/bsd_index.py` не видит драйверы, у которых исходник `dev/ic` подключён только через `*reg.h` (dc, rl, xl): они все равно закрыты лицензией.

## drvget auto: план (не реализовано)

Автоподбор уже есть в окне «Драйверы» и в `drvman do scan` (`act_scan` в `userland/drvman.c`): список PCI только для чтения (`KDRV_SYS_PCILIST`, право
`CAP_PCILIST`), устройства без владельца и без пакета ищутся в `/etc/ssl/drivers.index` по `vendor:device`, первый кандидат скачивается в песочницу и показывается
(лицензия, хеши, права). Установка (`drvget confirm ИМЯ ХЕШ`) - отдельное действие человека, как и сейчас; ничего не ставится молча.
Команду `drvget auto` как отдельную правку в `drvget.c` делать нельзя без изменения модели прав: у `drvget` нет `CAP_PCILIST` (`caps.c`, проверяется `tests/fsrv_test.c`:
право есть только у `drvman`), а у программы с `CAP_NET` его выдавать не стоит без решения владельца. Предлагаемый порядок:
1. `drvget auto` = только вывод: перечень устройств PCI без владельца с совпадением в каталоге и точные команды `drvget install ИМЯ` / `drvget confirm ИМЯ ХЕШ`;
   список устройств берётся у `drvman` (`drvman do scan`), а не прямым вызовом ядра; либо отдельное решение о праве `CAP_PCILIST` для `drvget` (тогда обновить `tests/fsrv_test.c`).
2. Без параметров ничего не скачивает; `drvget auto ИМЯ|VVVV:DDDD` скачивает и проверяет (как `install`) и печатает хеш для `confirm`; `confirm` обязателен.
3. Повторы и ошибки: драйвер уже установлен или запущен - пропуск; несколько кандидатов - все в перечне, скачивается только названный; каталог повреждён - остановка.
4. Тест: хост-тест `drvget_test` на разбор, сценарий drvget-bsd на цепочку auto -> install -> confirm (в QEMU, в этой сессии не запускался).
