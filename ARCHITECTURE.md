# Kira OS — архитектура «без тупика старых технологий»

Принцип: каждый слой ядра говорит с железом через узкий интерфейс, который можно
заменить современной реализацией, не трогая верхние слои.

| Слой | Сейчас | Куда расти (без переписывания верхних слоёв) |
|---|---|---|
| Загрузка | Multiboot2 + GRUB (BIOS), 1024x768x32 | UEFI/GOP: тот же MB2-тег фреймбуфера, ядро не меняется |
| Описание машины | ACPI (RSDP/XSDT/MADT/HPET/MCFG) разбирается и проверяется | IOAPIC/HPET/PCIe ECAM из тех же таблиц, SMP по MADT |
| Прерывания | PIC + PIT, LAPIC калибруется | LAPIC-таймер как тик, IOAPIC, PIC отключается (`pic_disable`) |
| Ввод | Слой событий `input.h`; PS/2 — один из драйверов | USB HID / virtio-input кладут те же события |
| Память | PMM, 4-уровневый VMM, NX/WP, NULL-guard | higher-half, W^X по секциям, адресные пространства процессов |
| Планировщик | вытесняющий, приоритеты, FXSAVE на поток | per-CPU очереди для SMP |
| Экран | фреймбуфер + damage-tracking, 2D/3D | драйвер GPU подменяет `fb_*`, GUI/игры видят тот же API |
| Безопасность | SHA-256 самоконтроль, антитела, карантин | подпись модулей, SMEP/SMAP при входе в Ring 3 |

## Что закрыто в v6
- Экран: grub.cfg больше не фиксирует режим через `keep` (причина «no framebuffer»); ядро печатает режим и маски тегов.
- Ввод: декодер PS/2 (Shift/Caps/Ctrl/стрелки/F-клавиши) вынесен в `input.c`, IRQ только кладёт байт в кольцо; консоль читает события — команды работают с окна QEMU/VNC.
- ACPI: разбор с проверкой контрольных сумм и границ; тесты на порченые таблицы.
- syscall: `sys_write(buf,len)` проверяет каждую страницу буфера, а не разыменовывает слепо.

## Добавлено в v7
- Ring 3: у каждого процесса свой PML4 (общая только нижняя половина ядра без бита USER), код R-X, данные/стек RW-NX, SMEP при поддержке CPU. SYSCALL/SYSRET включены (write, exit, ticks, sleep, yield, getpid), указатели пользователя проверяются по битам USER/WRITE на каждом уровне таблиц.
- Исключение в Ring 3 убивает процесс, а не ядро; адресное пространство уничтожается, страницы возвращаются в PMM.
- Диск: блочный интерфейс `blk_dev_t` + ATA PIO; опыт (норма нагрузки, число загрузок, карантин иммунитета) хранится в двух ячейках с поколениями и CRC32.

## Добавлено в v8
- Окна: композитор `wm.c` (z-порядок, перетаскивание за заголовок, кнопка закрытия, панель задач, курсор, перерисовка только изменившихся областей). Консоль, панель организма и 3D — панели оболочки (см. v10).
- Мышь PS/2: декодер пакетов (хост-тест), общий обработчик IRQ1/IRQ12 по биту AUX.
- Современные прерывания: IOAPIC + таймер LAPIC 100 Гц. Включаются только после живой проверки (RTC -> IOAPIC -> LAPIC, затем счёт тиков LAPIC против TSC); при сбое остаётся PIC+PIT.

## Добавлено в v9
- API Ring 3 для графики: `gfx_create/present/event` (userland/kira.h). Программа получает поверхность, общую с ядром (страницы помечены SHARED, процесс их не освобождает), рисует напрямую, события мыши/клавиатуры приходят очередью. Окном и перерисовкой занимается один поток дисплея.
- Прикладные программы пишутся на C (userland/*.c), собираются clang+lld в плоский бинарник и встраиваются в ядро: plasma и paint.

## Добавлено в v10: оболочка «Кира»
- Никаких оконных рамок с квадратными кнопками: `wm.c` рисует скруглённые панели (цветная полоска, круглые кнопки «свернуть / на весь экран / закрыть»), закреплённую панель «Организм» (кольца гомеостаза, стресса, усталости и любопытства + полосы показателей, `hud.c`), верхнюю полосу состояния и док с круглыми иконками. Фон (звёзды, сетка) рисуется один раз.
- Полный экран: содержимое растягивается в целое число раз по центру, мышь пересчитывается в координаты приложения; кнопки появляются, когда курсор у верхнего края. F11 - полный экран, F10 - свернуть на фон (клавиши забирает `input_take_hotkey`, приложение их не видит). Свёрнутое приложение продолжает работать, иконка дока возвращает его; иконка без окна запускает программу Ring 3.
- `gfxui.c`: сглаженные скруглённые прямоугольники, круги, кольца, дуги и прозрачность на целых числах (угол - по таблице арктангенса, ошибка не больше 0,5°).
- Тесты: `ui_test`, `wm_test` (док, полный экран, закрепление, ввод), прогон потока дисплея с кадрами `screen/full/min/apps.ppm`.

## Добавлено в v11
- Командная строка: ввод накапливается и выполняется по Enter (Backspace, Ctrl+U/C/L, история стрелками); `help` строится из таблицы команд; `clear` и Ctrl+L очищают экран через управляющий символ в журнале (порядок вывода сохраняется), опасные тесты (`crash-*`, `starve`) вызываются только полным именем.
- Построчная телеметрия идёт только в serial (`telemetry on` возвращает её на экран): те же цифры постоянно видны в панели «Организм», где каждое значение показано один раз (кольца с подписями, полосы CPU и памяти).
- Размер панелей меняется уголком справа внизу: консоль получает больше/меньше строк и колонок (шаг - знакоместо, во весь экран - столько, сколько у экрана), панель организма перерисовывается под ширину, окна приложений масштабируются (50%-400%, прилипание к 100%/200%), мышь пересчитывается.

## Что НЕ закрыто (честно)
- Один процессор: при SMP нужны per-CPU TSS/стек SYSCALL и блокировки.
- ATA PIO — запасной драйвер за тем же интерфейсом; основной с v13a - virtio-blk (NVMe - следующий).
- IPC: прежний ipc.c (очередь без замка и без адресата, нигде не вызывалась) удалён в v21f как заглушка; настоящие каналы с ёмкостями (capabilities) - в v22.
- Higher-half, W^X по секциям, IOAPIC/LAPIC-тик, PCI-перечисление, диск и хранение опыта между перезапусками.
- Транслятор Linux-драйверов — заготовка (этап 4).
- Ничего из этого не запускалось в QEMU в моей среде: проверены хост-тесты, сборка и дизассемблирование.

## v12a: файловая система KiraFS (kfs.c, fscmd.c)

- Область диска с LBA 16 (сектора 0–15 - хранилище опыта). Блок 4 КБ, инод 128 байт с CRC32, запись каталога 64 байта (имя до 59 байт), файл до ~4 МБ (12 прямых + 1 косвенный блок), каталог до 12 блоков.
- Без журнала: метаданные меняются записью одного сектора, данные нового файла пишутся в свободные блоки и сбрасываются на диск ДО переключения инода. После обрыва файл целиком старый или целиком новый.
- Карта блоков в памяти: строится при монтировании по инодам; заодно убираются потерянные иноды, перекрёстные блоки и записи каталога с битыми ссылками (`repaired` в `df`).
- Консоль: `ls [путь]`, `cat`, `write путь текст`, `mkdir`, `rm`, `df`, `format yes`. При загрузке диск без KiraFS не трогается - создаётся только по `format yes`.
- Допущения: сектор пишется целиком или не пишется; `flush` - барьер порядка записи; вызовы ФС сериализованы (всё идёт из основного потока ядра, блокировок пока нет).
- Тест tests/kfs_test.c: обрыв питания на каждой записи 5 операций (85 сценариев) с проверкой «старое или новое», идемпотентность fsck и работа после восстановления; 400 случаев порчи метаданных.

## v13a: PCI и virtio-blk (pci.c, virtio.c, virtio_blk.c, blk.c)

- pci.c: перечисление шин через порты 0xCF8/0xCFC с обходом мостов, размеры и тип BAR (порты, 32/64 бит), список capabilities, отображение BAR в адресное пространство ядра без кэширования (`pci_map_bar`). Консоль: `lspci`, `disk`.
- virtio.c: только современный virtio 1.0 (capabilities + MMIO BAR, без старого интерфейса на портах): сброс, ACK/DRIVER, согласование признаков (обязателен VERSION_1), FEATURES_OK, очередь split-ring, DRIVER_OK. Обмен синхронный, без прерываний (INTx отключён), с таймаутом; при таймауте устройство сбрасывается и отключается.
- virtio_blk.c: заявки по 64 КБ через собственный DMA-буфер (вызывающий не обязан знать о физической памяти); учитываются size_max, RO, FLUSH.
- blk.c выбирает диск: virtio-blk, иначе ATA PIO. Формат диска тот же (опыт в LBA 0-1, KiraFS с LBA 16): старый kira.disk работает на любом драйвере.
- run_qemu.sh по умолчанию подключает `virtio-blk-pci,disable-legacy=on`; `--ata` возвращает ATA.
- Тест tests/virtio_test.c: модель шины PCI (мост, многофункциональное устройство, 64-битный BAR) и модель virtio-устройства, которая проверяет порядок инициализации по спецификации и разбирает заявки из колец в памяти; разные размеры, size_max, RO, отказ согласования, молчащее устройство, KiraFS поверх virtio.

## v13b: граница ядра и программ, иммунитет над программами, жизнь организма в файловой системе

- Программы Ring 3 (plasma, paint, demo, atk-*) больше не вшиты в ядро (удалены user_apps.s, user_programs.s). Сборка делает из них ELF, а `tools/kfstool` кладёт их в /bin на kira.disk (тот же kfs.c, что в ядре). Остальные данные на диске не затрагиваются.
- elf.c: строгая проверка ELF (ET_EXEC x86-64, сегменты по границам страниц в окне 0x8000000000..0x8000200000, W^X, без пересечений, вход в исполняемом сегменте, исполняемый стек запрещён, все смещения проверяются). proc_spawn_elf отображает код R-X, константы R--NX, данные RW-NX.
- Доверие: сборка вшивает в ядро манифест имя->SHA-256 (manifest.h, создаётся kfstool). progs.c перед запуском читает /bin/<имя>, считает SHA-256 и сверяет (trust.c). Совпало - программа «своя». Не совпало или нет в манифесте - immune_classify заносит в карантин (он сохраняется в опыте), образ затирается, запуск отклонён, событие в журнал.
- life.c: журнал /var/life.log (последние ~2 КБ) и профили /var/prog/<имя> (запуски, аварийные завершения, отказы). События ставятся в очередь из любого контекста (в том числе при завершении процесса с выключенными прерываниями), а на диск их пишет только основной поток ядра (life_tick); так диск остаётся однопоточным. Дисплей не читает диск сам: иконки дока вызывают prog_request, запуск делает prog_poll.
- Консоль: `run имя`, `progs` (вердикт доверия по каждому файлу), `life`.
- Ещё в ядре, но не должно: окно 3D (gfx3d, SSE в ядре), fputest, нагрузочные потоки burn. Их вынос - следующий шаг (v14), для него нужны системные вызовы файлов и графики для программ.
- Тесты: tests/prog_test.c (разбор ELF: ~30 случаев отказа, 20000 случайных порч - принятое всегда безопасно; сверка реальных ELF с манифестом; журнал и профили в KiraFS, перезагрузка, переполнение очереди и журнала).

## v14a: файлы для программ (fsrv.c)

- Системный вызов 10 (`SYS_FS`): чтение, запись, размер, список, удаление. У каждой программы одна песочница `/data/<имя>`; файлы называются коротким именем без '/' и '..', выйти за песочницу нельзя по построению. Имя программы ядро берёт из проверенного запуска (хеш по манифесту), а не со слов программы. Файл до 64 КБ, не больше 32 файлов, запись заменяет файл атомарно.
- Диск по-прежнему трогает только основной поток: системный вызов копирует запрос из памяти процесса в слот, ждёт (sleep), а `fsrv_poll` выполняет его и возвращает результат. Подозрительные имена пишутся в журнал организма (`deny-fs`).
- ELF-загрузчик понимает сегмент данных RW (.data/.bss, хвост без файла - нули); предел страниц на программу 48.
- Paint: `s` сохраняет рисунок в /data/paint/picture.kpnt (RLE, формат проверяется полностью при загрузке), `l` загружает.
- Тесты: tests/fsrv_test.c (имена, изоляция, квота, пределы), tests/paint_test.c (настоящий код Paint против настоящего сервиса: круг сохранение-загрузка, порченые файлы, слишком сложный рисунок), все команды консоли из help выполняются.

## v15: диагностика на реальном железе (bootmap.c, mbinfo.c, earlycon.c, crashdump.c)

- Найденная по коду причина чёрного экрана на UEFI: GRUB может положить Multiboot2-структуру выше 1 ГБ, а ядро отображает 1:1 только первый ГБ. PMM отказывал («outside the mapped region»), ядро паниковало, а панику видел только serial. Теперь `mbinfo_relocate` отображает структуру через окно и копирует её в статический буфер ядра (до 64 КБ); дальше все модули работают с копией.
- `bootmap`: раннее окно PML4[511] -> статический PDPT -> статический PD, 512 страниц по 2 МБ, адреса от 0xFFFFFF8000000000, бита USER нет, при включённом NXE страницы NX. Видеопамять и MMIO - некэшируемо (UC-). `vmm_space_create` копирует PML4[511] в каждый процесс, так что вывод журнала безопасен при любом активном CR3.
- `earlycon`: журнал (то же, что идёт в UART) рисуется прямо в видеопамять с первой строки: линейный буфер 32 бита (порядок каналов берётся из тега, поэтому RGB и BGR оба видны) или текстовый VGA 80x25 (тег EGA или отсутствие тега). Экран пишется кольцом: новая строка затирает самую старую, под последней рисуется черта. Кириллица - глифами в графическом режиме, `?` в текстовом. Паника и фатальное исключение - красным.
- Передача экрана: перед `display_init` ранняя консоль останавливается и снимает окно (два отображения одной видеопамяти с разными типами кэша не допускаются). Если графическая оболочка не поднялась, ранняя консоль включается снова и показывает весь журнал: чёрного экрана больше нет.
- Дамп при фатальном исключении: `interrupts.s` передаёт кадр целиком; печатаются RAX..R15, RIP, RFLAGS, CS, SS, CR0/CR2/CR3/CR4 и 8 слов стека ядра (если RSP внутри identity-карты). `kernel_panic` печатает адрес вызова.
- Первый тик таймера ждётся без `hlt` и с пределом (4*10^9 тактов TSC): если IRQ0 не доставляется, ядро пишет причину и паникует, а не засыпает.
- Не решено (честно): таблицы ACPI на UEFI часто лежат выше 1 ГБ, `acpi_init` их не видит (MADT/HPET/MCFG пусты, ядро идёт на PIC/PIT); формат пикселей не 0x00RRGGBB (RGB-порядок) принимает только ранняя консоль, графическая оболочка откажется и ядро останется на текстовой консоли; PMM управляет только первым гигабайтом ОЗУ. Всё это входит в фазу B плана.
- Тесты: tests/bootmap_test.c (содержимое таблиц, повторное использование, пределы окна), tests/early_test.c (перенос структуры выше 1 ГБ и через границу, отказы, RGB/BGR, масштаб, UTF-8, перенос строк и кольцо, текстовый режим, тег EGA, повтор журнала, дамп регистров).

## Реальное железо: что сейчас мешает (оценка по коду, не по запуску)

- Многоядерность не причина провала загрузки: из MADT читается только число процессоров, остальные ядра (AP) не запускаются и стоят в ожидании, ядро работает на одном (BSP). Для SMP не хватает: запуска AP (INIT-SIPI-SIPI, трамплин 16->64 бит), своих GDT/TSS/IDT/стеков на ядро, очередей планировщика на ядро или блокировок (сегодня защита - только выключение прерываний, на нескольких ядрах её недостаточно), рассылки сброса TLB.
- Видео: берётся только линейный буфер кадра от GRUB (Multiboot2, 32 бита). Если GRUB не смог включить графический режим (тип не 1), ядро молчит на экране и пишет только в serial. Дисплей поднимается ПОСЛЕ опроса дисков, поэтому зависание на любом раннем шаге выглядит как чёрный экран.
- Ввод: только PS/2. На современных ноутбуках клавиатура и мышь по USB (xHCI), у ядра нет USB.
- Диск: virtio-blk и ATA PIO (старый IDE-порт). У реальных машин SATA в режиме AHCI или NVMe: диска нет, опыт и файловая система не подключаются.
- Следующий шаг для реального железа (v15): ранний вывод журнала на экран и на текстовый VGA, затем AHCI и NVMe, USB xHCI HID, затем SMP, затем собственный драйвер GPU (для виртуальных машин - virtio-gpu).

## v16 / v14b: параллелизм-основа и вынос 3D, fpu, burn из ядра

- Билетные блокировки (spinlock.h) вместо голого cli в uart, klog, earlycon, heap, pmm, proc, fsrv, life, progs. Порядок: uart -> klog, uart -> earlycon. Паника отменяет замки (spin_bust). Тест на реальных потоках под ThreadSanitizer.
- Системные вызовы выполняются с включёнными прерываниями (interrupts.s): обработчик вытесняем.
- SYS_HEAP (11): куча программы от UHEAP_VA, квота 1024 страниц, запас 4 МБ свободной ОЗУ, отказ пишется в журнал жизни как "deny-hp".
- 3D-лаборатория (программа cube3d), fpu (3 процесса) и burn стали программами в /bin. gfx3d.c/h и fputest.c/h удалены. Ядро полностью без SSE (0 команд xmm в kira.bin); SSE2 разрешён только программам.
- Известный предел: тест spinlock гоняется по числу ядер (билетный замок при перегрузке ядер теряет время на вытесненном держателе; для ядра это значит, что под SMP потоки с замком не должны вытесняться, и они не вытесняются: прерывания выключены).

## v18: профиль железа и пределы от машины

- hwprofile.c: CPUID (производитель, семейство, модель, SSE2, NX, страницы 1 ГБ, XSAVE и размер области, AVX/AVX2/AVX-512F, PCID, SMEP, SMAP, RDRAND, RDSEED, x2APIC, TSC-deadline, инвариантный TSC, разрядность адресов, признак виртуальной машины), число ядер из ACPI MADT, ОЗУ из менеджера страниц, частота TSC (измерена по PIT в kernel.c, заявленная процессором - CPUID 0x15, если есть). Разбор CPUID - чистая функция, проверена на синтетических Intel, AMD, ВМ и пустых листах. Команда `hw` и строки `[KIRA HW]` в журнале загрузки.

## v18e: исправление ранней консоли (ошибка v15)

- В v15 окно bootmap устанавливалось только в mbinfo_relocate, то есть когда Multiboot2-структура лежит выше 1 ГБ. При обычной загрузке (структура ниже 1 ГБ) окно не ставилось, ранняя консоль писала «Cannot map video memory» и экран оставался пустым до display_init. Найдено по журналу пользователя в QEMU (BIOS и UEFI). Хост-тест не поймал, потому что заглушка bootmap_map отображала всегда; теперь заглушка ведёт себя как настоящий модуль (без bootmap_init отображения нет), и тест это проверяет.
- earlycon_init сама вызывает bootmap_init. Теперь PML4[511] занята при любой загрузке, и vmm_space_create копирует её в каждый процесс (без бита USER) - это впервые работает вне UEFI-случая.
- Запуск под UEFI (OVMF, `./run_qemu.sh --uefi`) подтверждён пользователем: GRUB EFI загружает ядро, видеопамять по адресу 0x80000000.

## v19: менеджер страниц на всю ОЗУ

- Битовые карты PMM (занята / не освобождать) больше не статические на 1 ГБ: размер выбирается по карте памяти (1/16 байта на страницу), хранятся в ОЗУ первого гигабайта после ядра и Multiboot2-структуры и сами резервируются. Предел управляемой памяти 512 ГБ (identity-карта живёт в PML4[0]).
- Старт: всё занято и зарезервировано, свободным становится только то, что карта памяти называет доступным. Дыры, MMIO и неотображённые страницы выдать или «освободить» нельзя.
- Память выше 1 ГБ запоминается списком (до 32 слитых диапазонов) и не выдаётся, пока `ramext_init` не отобразит её 2-МБ страницами (RW+NX) в общий PDPT и не вызовет `pmm_add_high`. Края диапазонов, не кратные 2 МБ, теряются (логируются). Если PD уже занят чужой записью, отображение останавливается на ней.
- Выдача идёт «низкие адреса первыми» (буферы под DMA остаются ниже 4 ГБ, пока есть место); зон нет. 1-ГБ страницы пока не используются (оптимизация TLB, позже).
- v19b: области ACPI (reclaimable/NVS) выше 1 ГБ менеджер запоминает отдельно, не выдаёт, а `ramext_map_read` отображает их по требованию (только если таблица целиком лежит в такой области), через хук `acpi_set_map_hook`. Раньше при ОЗУ больше ~3,5 ГБ таблицы ACPI были недоступны (код 5, нет IOAPIC, 1 ядро).
- Границы, которые остались на 1 ГБ: BAR в PCI, чтение стека в crash-дампе (сознательно консервативно).
- Проверено хост-тестами: pmm_test (динамические карты, высокая ОЗУ, повторное добавление, выход за диапазон), ramext_test (края, нехватка памяти под PD, чужие записи). Не проверено: запуск в QEMU с `MEM=4G`/`8G`.

## v20b: тики по времени, а не по числу прерываний

- `timer_handler` после калибровки TSC выводит тики из часов TSC (`tick = якорь + ns / период`), поэтому потерянные эмулятором или нагрузкой прерывания не замедляют сон потоков, кванты по времени, «жизнь» и watchdog. Раньше потеря прерываний = часы шли медленнее.
- Проверка LAPIC-таймера считает именно прерывания (`timer_get_irqs`), допускает потерю до половины (нагруженный эмулятор) и до +25 % сверху; отказ по-прежнему возвращает на PIC+PIT с сообщением.
- Причина правки: на телефоне при 1000 Гц проверка LAPIC не прошла (в верхней панели стало «PIC» вместо «IOAPIC»). Частота снижена до 500 Гц.
- Не проверено в QEMU: после патча в верхней панели должно быть «IOAPIC • активен».

## v20c: дешёвая сборка кадра

## v21a: данные на процессор (GS) и swapgs

- `percpu_t` (percpu.h): self, стеки SYSCALL, номер и APIC ID процессора, текущий и холостой потоки. Адрес лежит в IA32_GS_BASE, `this_cpu()` - одна команда `mov %gs:0`. `sched.c` берёт `current` и `idle_thread` оттуда, `proc_arch_switch` кладёт стек SYSCALL в `percpu`, вход SYSCALL читает его через `gs:`. Глобальные `syscall_kernel_rsp/user_rsp` удалены.
- Безопасность: программа в Ring 3 может сбросить базу GS командой `mov gs, ax`. Без swapgs следующий SYSCALL записал бы по адресу 8 в ядре. Поэтому: в режиме ядра GS_BASE = percpu, в KERNEL_GS_BASE значение процесса (0). Вход из Ring 3 (исключения, IRQ, SYSCALL) делает swapgs, выход в Ring 3 (iretq, SYSRET, enter_user) - тоже. Флаг "swapgs сделан" лежит под сохранёнными регистрами в кадре прерывания (два слова, стек остаётся выровненным; C-обработчики видят прежний кадр).
- NMI, #DF и #MC могут прийти в окне между SYSCALL и swapgs: для них решение по значению GS_BASE (0 - ещё GS процесса), а не по CS.
- Новый тест `atk-gs` (команда `atk-gs`): процесс перезагружает GS, потом вызывает ядро (getpid, sleep). Ожидается "kernel GS intact after the attack (PASS)".
- Проверено: сборка, хост-тесты (планировщик и реальное переключение контекста с percpu), дизассемблирование входа SYSCALL. Не проверено в QEMU: весь путь swapgs (нужны запуски burn, cube3d, atk-mem, atk-gs).

## v21b: запуск остальных ядер (AP)

- ap_tramp.s: трамплин реального режима, копируется на физ. 0x8000 (SIPI vector 0x08); реальный → защищённый → long mode на CR3 BSP, EFER LME|NXE, свой стек на каждое ядро, вход в smp_ap_main(idx).
- Инициализация AP: GS_BASE=percpu, свои GDT/TSS и IST-стеки (gdt_init_ap), общая IDT (idt_load_this_cpu), FPU, SYSCALL, CR0.WP/SMEP/PAT (vmm_cpu_init_ap), LAPIC; затем online=1 и цикл sti;hlt.
- Последовательность: INIT, 10 мс, deassert, SIPI (до 2 раз, пауза 300 мкс), ожидание online до 500 мс. Затем IPI-пинг (вектор 0xF0), счётчик percpu.ipi_count.
- Выбор AP: чистая функция smp_plan (исключает BSP, дубли, лимит). Команда консоли smp показывает состояние ядер.
- Проверено: хост-тесты (smp_plan, ICR-команды, таблица percpu), сборка ядра, байты трамплина (objdump). НЕ проверено: реальный запуск ядер в QEMU (нужно SMP=4 ./run_qemu.sh --vnc).
- Планировщик по-прежнему работает на одном ядре; AP простаивают (v21c).
- Исправление после первого запуска в QEMU (SMP=4): все 4 ядра поднялись, но первый межъядерный пинг падал с #PF по адресу 0: gdt_init_ap загружал селектор в %gs уже после percpu_set_gs, и GS_BASE обнулялся. Теперь percpu_set_gs вызывается после gdt_init_ap.

## v21c: планировщик на нескольких ядрах

- Одна очередь готовности и таблица потоков под общим билетным замком (sched_lock). Замок держится на время выбора и переключения и отпускается уже новым потоком (finish_switch): прежний поток помечен on_cpu, пока его стек не сохранён, поэтому он не может оказаться на двух ядрах сразу.
- У каждого ядра свои: текущий и холостой поток, need_resched, учёт времени, число переключений, TSS, загруженный CR3 (всё в percpu_t).
- Потоки имеют маску ядер (affinity). sched_create/sched_create_proc ставят только загрузочное ядро: подсистемы ядра (ipc, vmm, ввод, kfs, blk) ещё без замков для работы с нескольких ядер. Остальные ядра исполняют только потоки, созданные через sched_create_on с явной маской.
- Каждое доп. ядро после инициализации вызывает sched_attach_cpu (его стек запуска становится холостым потоком idleN) и запускает свой таймер LAPIC с тем же счётом, что у загрузочного. Время (тики) и watchdog ведёт только загрузочное ядро; тик остальных учитывает кванты и пробуждения.
- Команда smp показывает у каждого ядра число переключений и занятость. Команда smptest запускает рабочие потоки на всех доп. ядрах: свёртка с заранее известным результатом, спор за замок (потери обновлений видны), проверка, что поток не покинул своё ядро, и проверка вытеснения по тику на доп. ядре (второй поток ядра стартует, только если тик вытеснит первый, не отдающий ядро).
- Не сделано: TLB shootdown (нужен, когда на доп. ядрах появятся потоки процессов или изменяемые общие отображения), замки подсистем, миграция и балансировка нагрузки. Пока потоки ядер не мигрируют.
- Проверено: хост-тесты (маски, независимость ядер, on_cpu, учёт), сборка ядра. Не проверено в QEMU: smptest и smp на SMP=4.

## v21d: потоки и программы на любом ядре (ядра равнозначны)

- Маска ядер по умолчанию - любое (SCHED_AFFINITY_ALL), включая процессы Ring 3 и потоки core и дисплея. Очередь готовых общая, поэтому свободное ядро берёт готовый поток само: нагрузка делится без отдельной миграции. Холостые потоки ядер привязаны к своим ядрам.
- Ядро вступает в планирование, только если у него есть тик LAPIC (без тика не было бы ни вытеснения, ни пробуждения спящих). Простаивающее ядро будится межъядерным прерыванием 0xF1 (smp_kick_idle), а не ждёт своего тика (до 2 мс).
- Время: каждое ядро получает тик своего таймера и обновляет общее время под замком (оно выводится из TSC и только растёт). Watchdog считает срок по общему времени, а не по числу вызовов, и проверяется на всех ядрах: зависание ядра, где работает кормящий поток, заметит другое ядро.
- Авария всей системы (kernel_panic, фатальное исключение, watchdog) останавливает остальные ядра через NMI (smp_halt_others); второе падающее ядро молча встаёт.
- Блокирующий мьютекс ядра (kmutex.c): честная очередь, владение передаётся первому ожидающему, ожидающий спит (sched_block_and_unlock / sched_wake, без потерянных пробуждений). Им защищены: файловая система целиком (раньше была гонка уже на одном ядре) и операции блочного устройства (blk.c).
- Замки: потребители очередей ввода (поток дисплея и системный вызов окна в фокусе - на разных ядрах), занятие слота окна в gfxsrv. Фокус окна публикует поток дисплея (остальным ядрам порядок окон не читать). Кадр окна уже защищён счётчиком seq (композитор перечитывает).
- Сброс TLB между ядрами пока не нужен: у процесса один поток, он в каждый момент на одном ядре, при переезде CR3 загружается заново; общие отображения ядра не меняются после запуска. Понадобится вместе с потоками одного процесса и общей памятью (v22).
- Нагрузка организма считается по сумме бездействия всех ядер.
- Не сделано (v21e): реакция на падение отдельного ядра (изоляция сбоя, остальные продолжают), перенос прерываний устройств (IOAPIC) с ядра 0 на живое ядро, выбор «ведущего» ядра при отказе. Пока падение любого ядра в режиме ядра - авария всей системы (честно остановленной).
- Проверка: хост-тесты (общая очередь между ядрами, мьютекс). В QEMU не проверено: команда burn4 (четыре процесса, число итераций должно совпасть с одиночным burn), ps (колонка CORE), smptest.

## v21e: равноправные ядра (изоляция сбоя ядра)

- Сбой в режиме ядра разбирает corefault_decide (чистая функция, хост-тест). Три исхода: гибнет только виновный поток; отказавшее ядро выходит из работы; авария всей системы. Изолировать можно, только когда общие данные заведомо целы: ядро не держит спин-замков (счётчик locks_held на ядро, ведут spin_lock_*), поток не держит мьютексов ядра (mutexes_held, иначе ожидающие встали бы навсегда), сбой не в обработчике прерывания (irq_depth), первый на этом ядре, поток не служебный.
- Служебные потоки (создание через sched_create: core, дисплей, холостые и т.п.) помечены THREAD_F_SERVICE: сбой в них - авария (перезапуска служб пока нет, это v22). Потоки процессов (sched_create_proc) и потоки с явной маской (sched_create_on) изолируются: процесс завершается через proc_exit, поток - через sched_exit, ядро и остальные потоки живут. Память, выделенная погибшим потоком ядра, не возвращается.
- Отказ ядра (исключение #MC, вектор 18; проверяется командой smpcrash N через int $18): sched_core_fail выводит ядро из планирования (affinity у остальных потоков теряет его бит, привязанные только к нему завершаются, кроме ждущих в очереди мьютекса), таймер LAPIC этого ядра маскируется, прерывания устройств (IOAPIC) переносятся на живое ядро (irqmode_core_failed; байт, застрявший в 8042, забирается сразу). Стек виновного потока остаётся занятым навсегда (ядро стоит на нём). Если живых ядер нет, или APIC-режима нет и отказало ядро 0, - авария. При аварии причина отказа в изоляции печатается («Not isolated: ...»).
- Журнал: вывод идёт в построчные буферы по ядрам (отдельно для потоков и обработчиков прерываний, linebuf.c); строка уходит целиком по переводу строки, хвост без него - через два тика (приглашение командной строки). Строки разных ядер больше не перемешиваются. При аварии буферы всех ядер выводятся (uart_flush_all).
- Раннее GS: данные загрузочного ядра заданы статически, GS указывает на них с первой строки kernel_main (учёт замков работает с самого начала); gdt_init и smp_ap_main возвращают GS после перезагрузки сегментов.
- Команды: smp (состояние FAILED), smpcrash N | thread | lock. Ожидание: smpcrash thread - в журнале строка о гибели потока, система жива; smpcrash N - ядро N в состоянии FAILED, остальные работают, клавиатура работает; smpcrash 0 - то же для загрузочного ядра, если включён APIC-режим; smpcrash lock - полная авария с причиной «core holds spinlocks».
- Проверено: хост-тесты (решение, буферы строк, отказ ядра в планировщике, учёт мьютексов), сборка ядра. Не проверено в QEMU: всё перечисленное в предыдущем пункте.

## v21f: масштабирование по железу (аудит и исправления)

Аудит нашёл допущения «машина как у разработчика (4 ядра)»:
- таблица потоков была 32 слота: на 8 ядрах холостые потоки и службы занимали почти всё, на 32 и более ядрах ядра молча не включались;
- одновременно допускалось 4 программы вне зависимости от ядер и ОЗУ;
- команда burn4 и smptest (до 16 ядер) были подогнаны под тестовую машину; ps клал массив размера таблицы на стек ядра;
- каждое переключение просматривало всю таблицу потоков под общим замком;
- ipc.c был заглушкой (см. выше).

Исправлено:
- scale.c: единая политика размеров из найденного железа. Потоки: 24 + 12 на ядро, но не больше 1/16 ОЗУ на стеки и не меньше, чем нужно для холостых потоков всех ядер и служб. Программы: 4 на ядро (не меньше 8), не больше одной на 8 МБ ОЗУ, от 2 до 256. Предел архитектуры: 64 ядра (маска ядер потока - 64 бита); лишние ядра по MADT сообщаются в журнале и не используются.
- Таблицы потоков и процессов выделяются при старте (sched_init(cpus, ram_kb), proc_init(cpus, ram_kb)); обходы таблицы потоков идут по занятой части (thread_hi), а не по всей ёмкости. Команда ps показывает занято/ёмкость.
- Ядро, которому не хватило слота холостого потока, честно сообщает об этом и помечается FAILED (раньше молча зависало).
- burn4 заменён на burnall: по процессу на каждое включённое ядро (не больше лимита программ); smptest рассчитан на любое число ядер до 64.
- Хост-тесты: политика размеров для 1..64 ядер; планировщик на 1, 2, 3, 4, 8, 16 и 64 ядрах (у каждого ядра свой холостой поток, на каждом ядре кроме занятого критическим потоком работает свой поток, поток не на двух ядрах, лишнему потоку тоже достаётся время, таблица заполняется ровно до ёмкости).

Известные пределы масштабирования (план):
- Одна общая очередь готовых потоков под одним замком: до 8-16 ядер приемлемо, дальше упрётся в замок. Очереди по ядрам с кражей работы и предпочтением прежнего ядра - после v22 (нужны объекты ядра и потоки процессов, чтобы мерить на настоящей нагрузке).
- Единый замок кучи и менеджера страниц: кэши по ядрам - тоже после v22 (сама куча с v22a растёт с ОЗУ).
- Прерывания устройств направлены на одно ядро (при его отказе переезжают, v21e); распределение по ядрам - вместе с MSI-X в v23/v24.
- APIC ID в таблицах 8-битные (xAPIC): x2APIC для машин с ID выше 254 не поддержан.
- Не проверено в QEMU: SMP=2, 3, 8 (нужны запуски; хост-тесты логику проверяют, но не железо).

## v22a: глобальный аудит (одним обновлением вместе с v21f)

Найдено и исправлено:
- Куча ядра была фиксированными 2 МБ в BSS (первый подходящий блок, слияние обходом всего списка, выравнивание 8 байт). Из неё берутся стеки потоков, стеки и IST каждого ядра, таблицы - потолок около сотни потоков при любом объёме ОЗУ. Новая куча (heap.c): классы 16..2016 байт на страницах-плитах с битовой картой, крупные блоки - целыми страницами из PMM; таблица владения страниц (открытая адресация, растёт и сжимается) отличает выданный блок от чужого указателя и повторного освобождения. Выравнивание не меньше 16 байт, крупные - 4096. Предел кучи - вся ОЗУ. Хост-тест: 200 тыс. случайных операций с проверкой содержимого, нехватка памяти и восстановление, рост таблицы.
- MMIO устройств отображалось по физическому адресу: выше 512 ГБ оно попадало бы в пользовательскую половину и было видно только в одном адресном пространстве, видеопамять ниже 1 ГБ шла через кэш write-back. Теперь окно MMIO ядра PML4[510] (0xFFFFFF0000000000, 512 ГБ), таблица создаётся до первого процесса и общая для всех; LAPIC, IOAPIC, BAR PCI, видеопамять - через vmm_map_mmio (крупные области - страницами 2 МБ, видеопамять - write-combining).
- x2APIC: если прошивка включила x2APIC, у системы не было ни LAPIC, ни SMP. Теперь драйвер умеет оба режима (MSR, 32-битные ID, ICR одной записью), MADT type 9, ID в таблицах 32-битные. x2APIC включается, если его включила прошивка, если в MADT есть ID больше 254, или по параметру загрузки x2apic (второй пункт меню GRUB). Без переназначения прерываний IOAPIC адресует только ядра с ID до 254 - при отказе ядра прерывания переносятся на такое.
- ID загрузочного ядра в таблице ядер был жёстко 0: на машине, где у загрузочного ядра другой APIC ID, межъядерные прерывания к нему ушли бы не туда. Теперь берётся из LAPIC.
- Частота TSC измерялась за 100 мс по тикам 2 мс (ошибка до 2%: часы, кванты и тик LAPIC врали). Теперь: канал 2 PIT без прерываний, медиана трёх замеров по 50 мс (~20 ppm), сверка с CPUID 0x15; запасные пути - CPUID 0x15, 0x16, тики. Таймер LAPIC калибруется по TSC за 20 мс.
- Расхождение TSC между ядрами раньше не проверялось. Теперь при запуске каждого ядра - 8 обменов, в журнал идёт максимальное расхождение и точность замера, при расхождении больше 100 мкс - предупреждение.
- Тик планировщика на каждом ядре каждые 2 мс брал общий замок и просматривал всю таблицу потоков. Теперь спящие просматриваются только к ближайшему сроку пробуждения, а холостое ядро ищет работу, только если какой-то поток стал готовым (эпоха готовности).
- Файловые вызовы программ шли через один общий слот, который основной поток опрашивал раз в 10 мс: 10-20 мс на операцию и одна операция на всю систему. Теперь запрос выполняется в потоке самой программы под мьютексом сервиса (KiraFS и диск уже под своими).
- SYSRET с неканоническим адресом возврата (SYSCALL с последнего байта пользовательской половины) вызвал бы #GP в Ring 0 на пользовательском стеке - теперь такой процесс завершается до SYSRET. Номер процесса выдавался вне замка.
- Мёртвый код удалён: translator.c (фиктивный «транслятор драйверов Linux»: заголовок не совпадал с реализацией, никто не вызывал), graphics.c, cmos.c (не вызывались), ipc.c (v21f), run.sh.
- memcpy/memmove/memset были побайтовыми циклами - теперь rep movsb/stosb (быстрые на всех x86-64 последних лет; ядро без SSE).
- run_qemu.sh по умолчанию запускал 1 ядро - теперь столько, сколько у устройства (не больше 8).
- Консоль: проверки вынесены под команду test (test - список; test smp, crash, fpu, isolation, atk, mem, immune, starve, panic-*). Убраны burn2 (есть burn и burnall), отдельные atk-*, demo (стал test isolation), smptest/smpcrash (test smp / test crash).

Отложено (план): очереди готовых потоков по ядрам с кражей работы; кэши кучи и PMM по ядрам; MSI/MSI-X и распределение прерываний; virtio по прерываниям вместо опроса; основной поток ядра по событиям вместо опроса 10 мс; сброс TLB между ядрами (вместе с потоками процессов, v22); защитные страницы стеков ядра (сейчас - канарейка); переделка ИИ.

Проверено: сборка ядра без предупреждений, все хост-тесты (добавлены heap, mem, scale; расширены acpi, smp, sched, console, gfx). В QEMU не проверено ничего из этого раздела.

## v22b: исправления после первого запуска v22a в QEMU (8 ядер)

- Построчные буферы журнала были у ядра, а поток может переехать на другое ядро посреди строки: часть строки оставалась в буфере старого ядра, в буфер попадали знаки другого потока, эхо клавиш и Backspace выводились не в том порядке (на экране стирались не те знаки). Теперь при каждой смене потока хвост строки уходившего потока выводится сразу (uart_switch_flush из finish_switch), буфер ядра достаётся новому потоку пустым. Приглашение консоли выводится сразу, без ожидания тика.
- test mem освобождал «чужую» страницу 0x200000, считая её частью ядра. После переезда кучи из BSS в PMM ядро кончается раньше, и это могла быть живая страница (порча памяти) - отсюда PMM: FAIL. Теперь проверяется страница образа ядра (kernel_start); точный счёт свободных страниц не сравнивается (его меняют другие ядра; он проверен хост-тестом).
- Проверка таймера LAPIC при переходе на APIC делает до трёх замеров: на перегруженной машине-хозяине один провальный замер оставлял систему на PIC, а доп. ядра - без тика (smp: «-», test smp: «LAPIC timer is not the tick source»).
- test crash N отказывается, если ядро N не исполняет потоки (раньше поток навсегда оставался ready).
- clock_ns не переворачивается, если счётчик TSC ядра отстаёт от загрузочного.
- Отчёт watchdog: при срабатывании печатаются тик последней подкормки, что исполнялось на каждом ядре (приоритет, остаток кванта, глубина прерываний, замки) и состояние потока core.

## v22c: зависание при burnall на 8 ядрах

- Отчёт watchdog (v22b) показал: поток core 5 с исполнялся на ядре 2, держа 2 мьютекса (KiraFS и диск) - ждал ответа virtio-blk при запуске программы. Ожидание было чистым кручением: при всех ядрах в нагрузке процессоры эмулятора крутились на 100%, и потоку QEMU, который обрабатывает запрос диска, не хватало процессора телефона - запрос растягивался на секунды. Теперь после короткого кручения поток засыпает на тик между проверками (ядро уходит в hlt), срок ожидания - 10 с по времени. До запуска планировщика и с выключенными прерываниями - по-прежнему кручение.
- Чтение состояния и байта контроллера PS/2 под замком: два ядра в обработчике одновременно прочитали бы один байт дважды (двойное нажатие). Команда test keys показывает сырые байты клавиатуры с прошлого вызова - для проверки, приходит ли Backspace дважды от самого VNC-клиента.

## v22d: плавность при нескольких ядрах

- Простой без тика: холостое ядро выключает свой таймер LAPIC и спит в hlt до межъядерного прерывания (оно приходит, когда появляется готовый поток: при создании, пробуждении, вытеснении потока на другом ядре). Тикает всегда одно ядро - хранитель времени (загрузочное; при его отказе роль переходит живому ядру): общее время, пробуждение спящих, watchdog. Раньше каждое ядро, даже без работы, обрабатывало 500 прерываний в секунду: в эмуляторе на телефоне 8 таких ядер отнимали процессор у самого эмулятора, и экран VNC дёргался.
- Ожидание virtio: сначала кручение до 1 мс по TSC (обычный ответ - микросекунды), только потом сон по тику. В v22c сон начинался раньше, и чтение программы с диска (много запросов) растягивалось - приложения открывались с задержкой.
- Вывод программ собирается по строкам отдельно для каждого процесса (userlog): строка выводится целиком с одним префиксом, даже если процесс вытеснили посреди неё или две программы пишут на разных ядрах (было: «iterations [USER pid 2] 91725824»). Незаконченная строка завершившегося процесса выводится при выходе.
- run_qemu.sh по умолчанию: половина ядер устройства, не больше 4 (остальное - эмулятору и телефону). Для проверки масштабирования - явно SMP=8.

## v22: завершение многозадачности - потоки процессов, futex, порты, разделяемая память, сброс TLB

Потоки процесса
- SYS_THREAD_CREATE(rip, вершина стека, аргумент) создаёт поток в том же адресном пространстве (до 32 на процесс); стек даёт программа (обычно из кучи), аргумент приходит в rdi. Возврат из функции потока завершает поток (kira.h кладёт адрес возврата на вершину стека). SYS_THREAD_EXIT, SYS_GETTID.
- Завершение процесса: exit из любого потока или сбой ставит флаг dying и будит спящие потоки; каждый поток уходит сам на выходе из ядра - после системного вызова (syscall_handler) или прерывания, прервавшего Ring 3 (irq_dispatch/ipi_dispatch получают CS прерванного кода). Поэтому снимается и поток, который крутится без системных вызовов, и поток, спящий без срока. Перед уходом поток переключает ядро на пространство ядра; последний ушедший уничтожает пространство, отпускает дескрипторы и отображения, выводит итог. Пространство уничтожается, только когда ни одно ядро на нём не стоит.
- Рост кучи, отображение окна и разделяемой памяти - под мьютексом процесса (потоки меняют одни таблицы страниц).

Futex
- SYS_FUTEX_WAIT(адрес, ожидаемое, срок) / SYS_FUTEX_WAKE(адрес, n). Ключ - физический адрес слова: то же слово в разделяемой памяти разных процессов - один ключ. Проверка значения и постановка в очередь неделимы относительно wake (замок корзины), пробуждение делается под тем же замком - не теряется и не достаётся потоку, который уже ушёл по сроку. kira.h: мьютекс на futex (k_mutex_lock/unlock).

Объекты ядра и дескрипторы (kobj.c)
- Порты: именованные очереди сообщений (до 32 сообщений по 1024 байта), SYS_PORT_OPEN (флаги CREATE/EXCL), SEND (не ждёт, KE_FULL), RECV (срок, возвращает длину и pid отправителя). Разделяемая память: SYS_SHM_OPEN (страницы обнулены), MAP, UNMAP. SYS_CLOSE. Дескриптор - номер в таблице процесса (64). Объект живёт, пока есть ссылки: дескрипторы, отображения, идущие вызовы (вызов берёт ссылку на своё время, поэтому другой поток может закрыть дескриптор без порчи памяти). Прежний ipc.c (заглушка) заменён этим.
- Пространство имён общее для всех программ ([a-z0-9._-], до 31 знака); права на имена - вместе с правами программ (план).

Сброс TLB между ядрами
- vmm_tlb_shootdown(root, va, pages): локальный сброс и межъядерное прерывание 0xF2 ядрам, у которых загружено это пространство (active_cr3), ожидание ответа (200 мс на случай отказавшего ядра). Ядро объявляет active_cr3 до загрузки CR3, поэтому рассылка не пропускает ядро, переходящее в это пространство. Используется при снятии отображения разделяемой памяти; страницы отпускаются после сброса.

Прочее
- SYS_CLOCK_NS - монотонное время в наносекундах для программ. ps показывает PID у каждого потока; proc_dump - число потоков.
- Проверки: test threads (программа mt: 4 потока x 20000 инкрементов под мьютексом, потом exit при живом крутящемся и спящем потоках - после него в ps не должно быть mt), test ipc (две программы ipc: 200 обменов через порты, страница разделяемой памяти, futex через общую страницу, время обмена).
- Хост-тест kobj: имена, дескрипторы, порты (порядок, переполнение, ожидание, срок, пробуждение, завершение процесса), разделяемая память (обнуление, общие страницы, освобождение), futex.

Не сделано (план): очереди готовых потоков по ядрам; перезапуск служб ядра после сбоя (сейчас сбой службы - авария); права на имена портов и памяти; передача дескрипторов через порт.

## v23: Разум вместо «организма» и новая оболочка

Разум (mind.c - чистое ядро, проверяется на хосте; mind_sys.c - связь с системой)
- Убраны физиология (усталость, любопытство, стресс) и наблюдатель (physiology.c, observer.c, hud.c): числа, которые ничем не управляли. Вместо них раз в секунду - замер всей системы (нагрузка каждого ядра, очередь готовых, память, опоздания кадров, задержка диска, обмен сообщениями, сбои, системные вызовы, процессы).
- Нормы этой машины: для каждого сигнала - скользящее среднее и разброс; необычность - отклонение больше 4 разбросов 3 секунды подряд (не чаще раза в 30 с на сигнал). Здоровье = отклик + запас + равновесие + стабильность, настроение по нему.
- Решения (режим «действует»; в режиме «наблюдает» только записываются): программа в фокусе получает вес 6 (квант x1,5); фоновая программа, из-за которой опаздывает экран, - ограничение 50% ядра (настоящий лимит доли процессора: окно 100 мс, сверх доли поток спит), снятие после 10 спокойных секунд; самонастройка кванта планировщика по замерам (проба соседнего значения, сравнение, откат), лучший квант запоминается для числа ядер; уровень анимации фона по запасу кадра; давление памяти: 88% - вернуть запасы кучи ядра (heap_trim), 93% - только осторожный рост куч программ, 97% - остановить самую большую программу; голодание потока больше 2 с - вес 8 на 10 с; поведение программы сравнивается с её профилем прошлых запусков (/var/mind/<имя>).
- Журнал решений с причинами (ai why), нормы (ai norms), программы (ai procs), режим (ai act / ai observe), анимация (ai fx auto|0..3). Модель хранится в /var/mind.dat с CRC и переживает перезагрузку.

## v26: USB-хабы и флешки, FAT, единое дерево файлов

- **Дерево устройств USB** (`usb.c`): у устройства есть родитель-хаб, порт, корневой порт, глубина, строка маршрута
  (xHCI) и переводчик транзакций (TT) для LS/FS за хабом USB 2.0. Отключение рекурсивно: хаб уходит вместе со всем,
  что за ним. Драйвер класса выбирается по интерфейсу: 9 - хаб, 3 - HID, 8 - накопитель.
- **Хабы** (`usbhub.c`): дескриптор хаба, питание портов, точка «изменения» (битовая карта), сброс порта, скорость,
  адресация через контроллер (`enumerate`). До 5 уровней (предел USB). USB 3-хаб пока работает своей USB 2-частью.
- **Флешки** (`usbmsc.c`): Bulk-Only Transport + SCSI (INQUIRY, TEST UNIT READY с ожиданием, REQUEST SENSE,
  READ CAPACITY 10/16, READ/WRITE 10/16, SYNCHRONIZE CACHE). Восстановление по спецификации: STALL данных -
  CLEAR_FEATURE и CSW; ошибка фазы/испорченный CSW - Reset Recovery; «успех» с недостачей данных - повтор.
  Пустой кардридер, защита от записи, сектор не 512 байт, exFAT/NTFS - понятное сообщение в журнале.
- **Контроллеры**: UHCI - массовые передачи цепочками TD (до 16 КБ), остановка на коротком пакете (SPD), учёт
  DATA0/DATA1, адреса по битовой карте. xHCI - Address Device с маршрутом и TT, признаки хаба в контексте слота,
  массовые точки: один Normal TRB до 16 КБ (буфер не пересекает 64 КБ), STALL -> Reset Endpoint + переконфигурация,
  таймаут -> Stop Endpoint; при закрытии точка снимается (Configure Endpoint drop).
- **Один исполнитель**: всё железо USB трогает только поток `usb`; чтение/запись флешки из других потоков идут через
  `usb_call`. Вынули флешку - операции сразу получают ошибку, том снимается, как только его отпустит последний
  пользователь (`vfs_unmount_try`), без взаимных блокировок.
- **FAT12/16/32** (`fat.c`) с длинными именами (UTF-8, кириллица), разделы MBR/GPT/без таблицы (`part.c`).
  Подряд идущие кластеры читаются и пишутся одним запросом (до 128 КБ). Время файлов - по RTC в местном поясе.
- **VFS** (`vfs.c`): корень - KiraFS, флешки - `/usb0`..`/usb3`. Терминал (`ls`, `cat`, `cp`, `df`, `umount usbN`) и
  проводник работают с обоими; проводник обновляется сам при подключении и извлечении.
- **Проверка на хосте**: модели хаба и флешки (BOT/SCSI на RAM-диске с FAT16) в `tests/usbdev_model.h`; ядро стека,
  UHCI и xHCI проверяются на одном сценарии: хаб HS, хаб FS за ним, клавиатуры за хабами, флешка - монтирование,
  запись/чтение 100 КБ, сбои (не готова, STALL, ошибка фазы, короткие данные), горячее извлечение. FAT - сверка с
  dosfstools и mtools (fsck.fat чистый после наших записей).

## v27: диски NVMe и SATA (AHCI), несколько дисков, защита чужих данных

- **NVMe** (`nvme.c`): выключение/включение контроллера по CAP.TO, очереди администратора, Identify контроллера и
  активных пространств имён, Set Features (одна пара очередей), Create I/O CQ/SQ, чтение/запись/сброс кэша.
  Опрос по фазовому биту, звонки с шагом CAP.DSTRD, MDTS, список PRP для буфера 64 КБ. Блок 4 КБ поддержан:
  неполный блок пишется через чтение-изменение-запись. Пространства имён одного контроллера - под общим мьютексом.
- **AHCI/SATA** (`ahci.c`): передача от BIOS (BOHC), сброс контроллера, на порт - остановка, структуры (список команд,
  FIS, таблица команды), раскрутка, COMRESET при отсутствии связи, IDENTIFY, READ/WRITE DMA (EXT для LBA48),
  FLUSH CACHE (EXT). Ошибка (TFES) - восстановление порта; диск, который не восстанавливается, отключается.
  ATAPI и множители портов распознаются и пропускаются с сообщением. 32-битные контроллеры - DMA ниже 4 ГБ.
- **Несколько дисков** (`blk.c`): реестр до 16 дисков, у каждого свой мьютекс и короткое имя (`vda`, `nvme0n1`,
  `sata0`, `ata0`). ATA PIO опрашивается только при IDE-контроллере на шине: диск не появится дважды.
- **Системный диск выбирается только по данным Киры** (KiraFS или хранилище опыта; проверка - только чтением).
  Раньше хранилище опыта писалось в секторы 0-1 любого найденного диска - на настоящем ПК это стёрло бы таблицу
  разделов Windows. Теперь диски с таблицей разделов, загрузочным сектором или любыми данными в начале считаются
  чужими: Кира их не трогает. Сделать диск системным: `format ИМЯ yes` (пустой), `format ИМЯ стереть` (с данными).
- Команда `disk` - список дисков: размер, модель, роль (системный / данные Киры / чужие данные / пустой).
- QEMU: `./build_clang.sh --vnc --nvme` или `--sata` - системный диск на NVMe или AHCI.
- PCI: до 128 функций (у настоящих ПК их 40-80; прежний предел 32 мог скрыть контроллер диска).

## v28: аудит - граница ядра и программ, стеки, Разум в устройствах

- **Доступ ядра к памяти программ - только через `uaccess`** (`uaccess.s/.c`): `copy_from_user`, `copy_to_user`,
  `user_read32`. Раньше системные вызовы проверяли адрес и затем читали память программы напрямую: другой поток той
  же программы мог снять отображение между проверкой и чтением - страничная ошибка в ядре и авария всей системы
  (а в `write` - ещё и под спин-замком). Теперь ошибка внутри копирования перехватывается обработчиком #PF
  (таблица «откуда можно продолжить»), вызов возвращает ошибку, ядро живёт. Переведены: write, порты, имена
  объектов, futex (слово читается безопасно под замком корзины), файловый сервис, события окон.
- **SMAP** (где процессор умеет): ядру запрещено касаться страниц программ вне `uaccess` (stac/clac на время
  копирования). **UMIP**: программам запрещены SGDT/SIDT/SMSW/STR (адреса таблиц ядра). SMEP - как и раньше.
- **Стеки потоков ядра с защитной пустотой** (`vmm_kstack_alloc`): каждый стек - ячейка 64 КБ во втором окне
  PML4[510] (общем для всех адресных пространств), отображены верхние 16 КБ. Переполнение - #PF -> #DF на отдельном
  стеке с сообщением «stack overflow: guard area», а не тихая порча кучи (метка на дне ловила её только при
  переключении и уже после порчи). Ячейки переиспользуются без снятия отображения.
- **Разум видит все программы**: MIND_PROC_MAX = 256 (предел scale_procs), раньше 32 - на машинах с 8+ ядрами
  часть программ была вне его решений.
- **Разум и устройства** (`devhealth.c`): ошибки обмена дисков (все драйверы через реестр blk), флешек и USB-устройств
  идут в замер Разума - журнал с именем устройства, удар по стабильности, «сохраните данные» при 10 с подряд.
- **Иммунитет ввода (BadUSB)**: клавиатура, печатающая быстрее человека (> 24 нажатий за 200 мс, т.е. > 120/с),
  рефлекторно задерживается драйвером - нажатия копятся. Разум решает: в режиме действий - отключить, в режиме
  наблюдения - отпустить и отдать накопленное. `usb allow` - вернуть отключённые (сканеры штрихкодов).
- Проверки, останавливающие систему (`test panic-*`, `test starve`), требуют слова `yes`.
- Удалены остатки: `user_apps.s`, `user_programs.s` (программы давно собираются в ELF и лежат на диске).

## v29: границы определяет железо

- **KiraFS v2**: том - весь диск (до 16 ТБ), файлы любого размера (дважды и трижды косвенные блоки, до ~4 ТБ),
  каталоги без предела записей, таблица инодов сама добавляет участки, когда иноды кончаются; диск (образ, раздел)

  как есть и получают суперблок v2 (меняется один сектор, данные не трогаются).
- **Ядра**: до 256 (маска сродства `cpumask_t` вместо 64-битного числа; планировщик, рассылки, таблица ядер).
- **Программы и окна**: поверхность окна - до размера экрана (было 800x600), окно у каждой программы (до 256),
  консоль ядра - сетка под весь экран. Сегменты программы - до четверти ОЗУ, образ на диске - любой (буфер из кучи,
  не больше четверти свободной памяти; было 96 КБ), ELF - до 16 сегментов.
- **Процессы**: главный стек растёт по обращению (в том числе когда буфер системного вызова лежит на нетронутой части
  стека), потоков - сколько вмещает таблица планировщика, таблица отображений растёт вдвое.
- **Объекты ядра**: таблица дескрипторов и реестр имён растут по мере надобности, разделяемая память - до половины
  свободной ОЗУ, сообщение порта - 64 КБ. Файловый сервис: запрос - до четверти свободной ОЗУ, файлов - доля таблицы
  инодов, место - пока системе остаётся 1/16 тома.
- **Устройства**: контроллеров xHCI до 16 (раньше работал только первый - на ПК их часто 2-4) и UHCI до 8, их
  состояние выделяется по числу найденных; устройств USB до 255, хабов/клавиатур/флешек по 64, томов /usbN - 64,
  дисков - 256, NVMe - 16 контроллеров по 32 пространства, AHCI - 16 контроллеров, функций PCI - 1024,
  IOAPIC - 64, областей ОЗУ - 256, окон MMIO - 1024, разделов GPT - 128.
