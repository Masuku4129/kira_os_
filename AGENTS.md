# Обязательные инструкции для агентов KIRA OS

Перед ЛЮБОЙ задачей в этом репозитории сначала полностью прочитать:
0. `docs/PROJECT_CONTROL_CENTER.md` — единая навигация, live-state snapshot, обязательная матрица трассировки запроса и правила безопасной уборки.
1. `docs/architecture/CURRENT_STATE_AND_HANDOFF_2026-11-13.md` — актуальный снимок архитектуры, подтверждённые границы и точка продолжения (после сверки live GitHub SHA/CI).
2. `docs/MASTER_DEVELOPMENT_PLAN.md` — обязательный полный план проекта.
3. `docs/architecture/KIRA_OS_TARGET_ARCHITECTURE.md` — обязательная целевая архитектура и границы компонентов.
4. `docs/architecture/ARCHITECTURE_AUDIT_AND_EXECUTION_PLAN.md` — текущая последовательность аудита и интеграции.
5. `docs/architecture/SOURCE_LAYOUT_MIGRATION.md` — целевые каталоги, source ownership и gates физической миграции.
6. `docs/architecture/COMPONENT_INVENTORY.md`, `DEPENDENCY_MAP.md` и `CONTRACT_REGISTRY.md` — фактические компоненты, зависимости и обязательные интерфейсы.
7. `docs/architecture/OPEN_PR_ARCHITECTURE_TRACKER.md` и `SOURCE_AUDIT_FINDINGS.md` — открытая веточная работа и подтверждённые риски.
8. Профильные спецификации `docs/compat/` и `docs/virtualization/`, если задача касается этих направлений.
9. `docs/WORKLOG.md` — последняя точка продолжения, открытые ветки и подтверждённые/неподтверждённые проверки.
10. `README.md` — текущий способ сборки и тестирования.
11. `ARCHITECTURE.md` — текущая архитектура и исторические ограничения.
12. Документы подсистемы, которую затрагивает задача.

Не начинать анализ/кодирование/PR до чтения мастер-плана. Это обязательный gate, а не рекомендация.

## Правила работы
- Сохранять весь объём проекта: мастер-план содержит 14 областей A–N и 12 параллельных рабочих потоков в отдельном разделе 3. Не путать эти две классификации и не сужать проект до последнего CI-failure или одного PR.
- До начала нетривиальной задачи заполнить матрицу трассировки из `docs/PROJECT_CONTROL_CENTER.md`: требование пользователя → раздел A–N и поток 1–12 → контракт/компонент → изменение/проверка → команда/среда/exact SHA/результат. Если запрос не покрыт планом, явно предложить обновление плана, не терять требование.
- Перед любым отчётом выполнить независимую проверку соответствия исходному запросу и мастер-плану; каждому утверждению PASS требуется свежее прямое доказательство на проверяемом SHA.
- Перед изменениями сверять актуальные ветки, PR, commit SHA, тесты и состояние файлов.
- Не считать старые сообщения/память источником актуального состояния репозитория.
- Не добавлять заглушки, пустые функции, фиктивную production-логику и неподтверждённую поддержку.
- Исправлять первопричину; после исправления повторять релевантные тесты.
- Не заявлять PASS, пока тест реально не запущен и результат не получен.
- Разделять host tests, QEMU/эмулятор, Limbo и физическое оборудование.
- Не сливать PR и не выполнять разрушительные операции без явного разрешения владельца.
- Не перезаписывать чужие изменения; согласовывать границы параллельной работы.
- Каждая задача должна указывать разделы мастер-плана и зависимости.
- При физическом переносе исходников обновлять оба ISA build manifests, все include/consumer paths, source inventory и architecture guards; старые implementation files удалять только после проверки новых путей. Не оставлять параллельные копии реализации.
- Слой `services/` во время перехода может содержать in-kernel adapters, но это не считается user-mode service isolation; в отчётах явно различать source ownership, privilege level и IPC/process isolation.
- По завершении сессии обновлять журнал продолжения: commit SHA, файлы/подсистемы, команды и результаты тестов, оставшиеся задачи.
- Отчёт пользователю — только когда он запрошен или работа действительно завершена; без пустых промежуточных сообщений.

## Обязательная проверка перед ответом
Перед любым отчётом проверить, что описанное соответствует текущему GitHub состоянию и наблюдаемым результатам. Если проверка не выполнялась — прямо указать это.

## Обязательная проверка соответствия запросу и плану
- Не начинать нетривиальную работу, пока не прочитан `docs/PROJECT_CONTROL_CENTER.md` и не построена матрица трассировки требований.
- Не считать выполнение промежуточного технического шага выполнением всего запроса.
- Перед отчётом пройти все строки матрицы и присвоить только доказуемые статусы PASS / PARTIAL / FAIL / UNVERIFIED / BLOCKED.
- Если часть запроса не выполнена, назвать её явно; не скрывать пропуски за общим словом «готово».
- Проверить соответствие не только ближайшему PR, но и всем релевантным направлениям мастер-плана A–N и зависимым потокам.
- Для изменений кода требовать тесты, соответствующие рискам; для архитектурных изменений — обновлённые контракты, dependency map, inventory и architecture guards.
- Уборка не должна разрушать историю или зависимые ветки: массовое удаление/закрытие/слияние запрещено без отдельного подтверждения владельца.
